<objective>
Build the negative-path assurance suite — a separately runnable, criterion-traceable body of tests
whose only job is to prove the guarantees Phase 1 claims, by attacking them.

Purpose: CONTEXT names this a deliverable in its own right: "**A dedicated negative-path test suite
is a named Phase 1 deliverable**, not left to developer discretion," and then enumerates exactly
what it must do. It closes with: "These tests are the evidence for success criteria 1, 3, 4, and 5."

Feature plans already test their own happy and unhappy paths. This suite is different in three ways
that matter: it **bypasses the UI and the Nest testing module entirely**, issuing raw HTTP against
the running stack the way an attacker would; it talks to the database as `app_rw` through a raw
client so no ORM behavior can be mistaken for a guarantee; and every assertion is traceable to a
numbered success criterion, so "is Phase 1 done?" has an answer a reviewer can check rather than
infer.

Output: `apps/api/test/assurance/` with a harness and four criterion specs, a separate Jest runner,
`docs/ASSURANCE.md`, and a CI job.
</objective>

`harness.ts`:

  can forge credentials, not that the system is sound.
- `api` — a thin `fetch` wrapper against `https://judicialsync.localhost:8443/api/v1` returning

  `rejectUnauthorized` stays on; the CA is trusted via `NODE_EXTRA_CA_CERTS`.

**`criterion-1-scoped-access.assurance-spec.ts`** — ROADMAP criterion 1: "A user can log in via SSO
and complete MFA, and is granted only the access their role/court/division/case/proceeding/
party-role/security-designation scope allows — an unauthorized resource request is denied
server-side (403), not merely hidden in the UI."

Every case issues raw HTTP. State that in a file header comment: CONTEXT requires the suite "bypass
the UI entirely and issue direct API calls with lower-privileged tokens against forbidden
resources."

1. **MFA is required end to end.** A direct-access-grant token request **without** a TOTP code is
   rejected by Keycloak; with a valid code it succeeds and `POST /auth/login` returns a session.
2. **Cross-court isolation, every resource family.** With the NDCA `clerk_case_admin` token, request
   the SDNY case and each of its children — `GET /cases/{sdnyCaseId}`,
   `/cases/{sdnyCaseId}/proceedings`, `/parties`, `/docket-events`, `/document-references` — and
   assert each is denied. Then the mirror direction with the SDNY user against NDCA. Two courts
   exist in the seed precisely so this is demonstrable; assert on **both** directions so a
   one-sided configuration error cannot pass.
3. **Writes are denied too, not just reads.** `POST /cases` naming the other court's `court_id`,
   and `PATCH /cases/{otherCourtCaseId}/status` → denied. A read-only isolation test would miss a
   write path that trusts the body.
4. **Scope narrower than role.** `courtroom_deputy` holds `case_read` and a court scope but no
   case-level scope on a case outside their division — assert the division/case scope dimensions
   are enforced, not only `court_id`.
5. **`attorney_external` can never reach internal resources.** With that token: `/audit/explorer`,
   `/entitlements/requests`, `/retention/schedules`, `/security/policy-evaluate` → all denied,
   **even after** granting that user a `case` scope on an NDCA case. `FRD/F00` Validation:
   "regardless of any case association."
6. **Denial is server-side.** For one denied request, assert the response body carries the
   `{error_code, message}` envelope and contains **none** of the resource's data — not a redacted
   field, not an id, not a count.
7. **Session revocation is immediate.** Capture a valid token, have `system_admin` and
   `security_officer` approve a scope change for that user, then reissue the **same** token →
   `401 AUTH_SESSION_EXPIRED` on the next call. `FRD/F00` Process step 7.
8. **Every denial above produced an `access_attempt` audit event** — query `/audit/explorer` as
   `security_officer` filtered by `action_type=access_attempt` and the acting user, and assert a row
   per denial with the matching `reason_code`.

For each case record the expected status with a comment citing `FRD/Y2-errors.md` principle 3: 403

The cross-court cases are **403** (the requester is a legitimate court user hitting a scope boundary,
and the case is not designation-protected) unless the target is also sealed — in which case
criterion 4's spec covers it. Make that reasoning explicit in the file so the expected codes are not

  <name>Task 2: Prove audit immutability at the database grant level and chain-break detection (criterion 3)</name>
  <files>apps/api/test/assurance/criterion-3-audit-immutability.assurance-spec.ts</files>
  <action>
ROADMAP criterion 3: "Every status change, ruling, custody transfer, override, or approval produces
an immutable, hash-chained audit entry; an attempt to UPDATE or DELETE a past audit row fails **at
the database grant level, not merely via application convention**."

CONTEXT spells out the two required attacks: "Attempt direct SQL `UPDATE` and `DELETE` against
`audit_events` **as the application database role**, asserting a permission error," and
"Deliberately corrupt an audit row and assert the integrity job detects the chain break."

1. **Material actions produce audit entries.** Through the API, perform one of each available
   Phase 1 material action: a case status change, a security-designation change, a grant approval,
   a file upload, and a disposition confirmation. For each, assert exactly one `audit_events` row
   exists with the expected `action_type`, the correct `actor_id`, a populated `rule_version_ref`,
   and non-null `prev_hash`/`row_hash`. (`custody_transfer`, `ruling`, and `calculation_override`
   belong to Phases 5 and 7 — assert the `action_type` enum accepts them and note in the matrix
   that their producers arrive later, rather than skipping the criterion silently.)
2. **`UPDATE` refused as `app_rw`.** Through `appRwClient()`:
   `UPDATE platform.audit_events SET action_type='tampered' WHERE id=$1` → rejects with SQLSTATE
   **`42501`**. Assert on the SQLSTATE, not the message.
3. **`DELETE` refused as `app_rw`.** `DELETE FROM platform.audit_events WHERE id=$1` → `42501`.
4. **No path around it.** Also attempt, as `app_rw`: `TRUNCATE platform.audit_events`,
   `ALTER TABLE platform.audit_events DISABLE TRIGGER trg_audit_events_hash_chain`, and
   `DROP TRIGGER trg_audit_events_hash_chain ON platform.audit_events` → each rejected. An attacker
   with application credentials would reach for the trigger before the rows.
5. **`app_rw` holds no DELETE grant anywhere.** Query `information_schema.role_table_grants` for
   `grantee='app_rw' AND table_schema='platform' AND privilege_type='DELETE'` → zero rows. This
   generalizes case 3 to every table and is the assertion that catches a future migration widening
   the posture.
6. **Forged hashes refused.** As `app_rw`, INSERT an `audit_events` row with a syntactically valid
   but incorrect `row_hash` → rejected by the trigger with a message containing
   `AUDIT_CHAIN_BROKEN`. Then INSERT with a correct `row_hash` but a stale `prev_hash` → rejected.
   The application role *can* insert, so these prove the trigger, not the grant.
7. **Deliberate corruption is detected.** First re-assert that `app_rw` **cannot** corrupt a row
   (case 2), establishing that the corruption below requires owner privileges. Then, as
   `appDbaClient()`, mutate a past row's `after_state`. Trigger a verification via
   `POST /api/v1/audit/integrity/verify` as `security_officer` and assert: the result reports
   `verified: false` with a `row_hash_mismatch` naming that row; a `critical` `integrity_alerts` row
   exists with populated `expected_hash` and `actual_hash`; `GET /audit/integrity/status` reports
   `chain_verified: false`; and the alert is visible through `GET /audit/integrity/alerts`.
8. **Tail deletion is detected.** As `app_dba`, delete the newest `audit_events` row; verification
   reports `chain_head_mismatch`. This is the corruption a row-by-row check misses.
9. **Detection does not repair.** After cases 7 and 8, read the corrupted row back and assert it is
   still corrupted — the system reports, it never rewrites.
10. **The transactional outbox holds.** Force an audit-write failure during a domain mutation (point
    the actor at a nonexistent user via the internal endpoint, or temporarily break the FK target in
    a transaction) and assert the domain row did **not** persist and the response was
    `500 AUDIT_WRITE_FAILED`. `FRD/F02`: "the audit write and the domain write commit atomically, or
    neither does."

**Restore the chain after the destructive cases.** Corruption leaves the chain broken for every
subsequent run, so the spec must either run against a freshly seeded database (preferred — add a
`beforeAll` that recreates the stack's database via `appDbaClient()` plus `db:migrate`/`db:seed`) or
repair `audit_chain_head` and remove the corrupted rows **as `app_dba`** in an `afterAll`. Document
whichever is chosen; a suite that poisons the environment for the next run is a suite people stop
running.
  </action>

**`criterion-4-designation-denial.assurance-spec.ts`** — ROADMAP criterion 4: "A user lacking a
specific security-designation entitlement (sealed/restricted/grand-jury/juvenile/PII) is denied
access to a tagged record, and the denied attempt itself is logged as an audit event."

1. **403 branch.** `clerk_case_admin` holds `case_read` and NDCA scope but not `designation_sealed`.
   `GET /cases/{sealedCaseId}` → **403 `AUTH_DESIGNATION_DENIED`** (Y2 principle 3: parent access
   known). Same for its proceedings, parties, docket events, and document references.
2. **404 branch.** The SDNY `courtroom_deputy` has no access path to the NDCA sealed case.
   `GET /cases/{sealedCaseId}` → **404**, and the response body is **byte-identical** to
   `GET /cases/{randomUuid}`. Compare the serialized bodies directly. Also compare response times
   across ~20 paired requests and assert the medians are within a generous band — §7.6 requires that
   "response timing cannot be used to infer the existence of a sealed matter," and a band check is
   the honest version of that assertion (note the tolerance and its rationale in a comment rather
   than asserting a precision the environment cannot deliver).
3. **Restricted designation behaves the same way** against the seeded restricted case, with
   `designation_restricted`.
4. **Role existence does not imply access.** `jury_admin` holds a role and zero entitlements:
   `GET /cases/{ordinaryCaseId}` → 403. Name it
   `it('criterion 4: a role without entitlements grants nothing')`. CONTEXT calls this a hard
   constraint that "must be proven by test, not merely asserted in a document."
5. **Entitlement grants access.** `judge` holds `designation_sealed`: the same sealed case → 200.
   Without this the suite cannot distinguish "correctly denied" from "broken."
6. **Audit history inherits the designation.** A user with `audit_reader` but not
   `designation_sealed` querying `/audit/explorer?case_id={sealedCaseId}` → `403
   AUDIT_DESIGNATION_DENIED`; their unfiltered query returns zero rows belonging to that case.
7. **List endpoints omit entirely.** `GET /cases` for the unentitled user contains no sealed case
   and its count excludes it; the entitled user's list includes it. `UX-Mockup/Y0-patterns.md`:
   "omitted entirely — never shown as a greyed-out row, a 'restricted' placeholder, or a count that
   includes it."
8. **Every denial is logged.** For each of cases 1, 2, 3, 4, and 6, assert a corresponding
   `access_attempt` audit event exists with the actor, the resource, and the `reason_code`. This is
   the second half of criterion 4 and the half most likely to be quietly missing.
9. **Designation changes are themselves gated.** `courtroom_deputy` attempting
   `PATCH /cases/{id}/security-designations` → `403 CASE_DESIGNATION_DENIED`, logged.

**`criterion-5-upload-and-encryption.assurance-spec.ts`** — ROADMAP criterion 5: "An uploaded file
of a disallowed type or failing malware scan is rejected before storage, and all data is encrypted
in transit and at rest."

1. **Disallowed type rejected before storage.** Count objects in the bucket, upload an MZ-header
   executable → `422 SECURITY_FILE_TYPE_DENIED`, bucket count unchanged, no `file_references` row,
   and **no `malware_scan_results` row** (proving the scan was never attempted).
2. **Header spoofing does not help.** The same bytes with `Content-Type: application/pdf` → same
   rejection.
3. **EICAR rejected before storage.** Upload the EICAR string as an allowed `.txt` type →
   `422 SECURITY_MALWARE_DETECTED`, bucket count unchanged, no `file_references` row. Because the
   type is allowed, this case isolates the scanner as the thing that rejected it.
4. **Scanner outage fails closed.** `docker compose stop clamav`, upload a clean PDF →
   `503 SECURITY_SCANNER_UNAVAILABLE`, nothing stored; restart and confirm the same upload succeeds.
5. **Encrypted at rest.** The clean upload's object reports `ServerSideEncryption: 'AES256'` via
   `HeadObject`.
6. **Encrypted in transit.** Assert the stack publishes **no** plaintext HTTP path to the API: a
   `curl http://judicialsync.localhost:8443/api/v1/health` fails or is redirected to HTTPS, and

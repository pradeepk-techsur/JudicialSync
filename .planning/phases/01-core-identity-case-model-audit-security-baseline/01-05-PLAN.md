<objective>
Build the Audit Service: the single writer of `platform.audit_events`, the transactional-outbox
helper every state-changing feature in Phases 1–8 routes through, and the TypeScript side of the
hash chain.

Purpose: `FRD/F02` Validation is unambiguous — every status-changing operation "**must** emit a
corresponding audit event before the operation is considered complete (enforced via transactional
outbox pattern — the audit write and the domain write commit atomically, or neither does)," and
`TechArch/04-security.md` §7.3 adds "'the action happened but wasn't audited' is structurally
impossible, not merely discouraged." A helper that makes the atomic path the *easiest* path is how
that becomes true across eight phases of feature work; an audit call that a developer can simply
forget is not.

The subtle, high-risk piece is hash parity. Plan 01-03's `BEFORE INSERT` trigger rejects any row
whose supplied `row_hash` does not match its own recomputation. That check is only meaningful if
TypeScript and PL/pgSQL agree byte-for-byte on the canonical payload — including how `jsonb` is
serialized. A fixture corpus comparing both implementations is the only honest way to know they do.

Output: `AuditService`, `withAudit()`, the internal service-to-service write endpoint, and three
integration test files.
</objective>

`canonical-payload.ts` must reproduce the SQL function from plan 01-03 **exactly**:

```
actor_id | action_type | object_type | object_id | before_state | after_state |
rule_version_ref | calculation_version_ref | client_ip | session_id | occurred_at | prev_hash
```
joined with `|`, each null/undefined rendered as the empty string, `occurred_at` formatted as
`YYYY-MM-DDTHH:mm:ss.ffffffZ` in UTC with **six** fractional digits (matching
`to_char(... 'YYYY-MM-DD"T"HH24:MI:SS.US"Z"')`), then `sha256` hex.

The hard part is `before_state`/`after_state`: SQL renders them with Postgres' `jsonb::text`, not
`JSON.stringify`. Implement `canonicalJsonb(value)` replicating Postgres `jsonb` text output:
- Object keys are ordered **by key length first, then bytewise** (Postgres `jsonb`'s internal
  ordering), not lexicographically.
- Separators are `", "` between members and `": "` between key and value.
- Arrays preserve input order with `", "` separators.
- Duplicate keys collapse to the last occurrence (jsonb semantics).
- Numbers are rendered in Postgres `numeric` canonical form: no exponent for ordinary magnitudes,
  trailing zeros preserved as written. **Reject non-integer floats** at the boundary instead of
  guessing — `AuditService` should throw on a `before_state`/`after_state` containing a
  non-integer `number`, with a clear message telling the caller to pass a string. Guessing here
  would produce a hash mismatch at insert time, which surfaces as an opaque `AUDIT_CHAIN_BROKEN`
  rather than a usable error.
- `null` renders as `null`; strings use JSON escaping.

Export `buildCanonicalPayload(input, occurredAt, prevHash): string` and
`computeRowHash(...): string` (Node `crypto.createHash('sha256').update(payload,'utf8').digest('hex')`).

`AuditService.record(tx, input)` — note the signature: it takes a `Prisma.TransactionClient`, never
the root client. Making the transaction a **required parameter** means an audit write physically
cannot be issued outside a caller's transaction, which is what `FRD/F02` Validation's atomicity
requirement reduces to in code.

Implementation:
1. `occurred_at = new Date()`.
2. `SELECT last_row_hash FROM platform.audit_chain_head WHERE id FOR UPDATE` via `tx.$queryRaw` —
   this takes the row lock inside the caller's transaction, pairing with the trigger's advisory
   lock so concurrent writers serialize rather than racing to the same `prev_hash`.
3. `row_hash = computeRowHash(input, occurred_at, prev_hash)`.
4. `INSERT INTO platform.audit_events (...) VALUES (...) RETURNING id, row_hash` via
   `tx.$executeRaw`/`tx.$queryRaw` with **parameter binding only** — never string interpolation of
   `object_id`, `action_type`, or any caller-supplied value.
5. If the insert raises (trigger rejection, permission error, anything), let it propagate so the
   enclosing transaction aborts.

`actor_id` is a required field of `AuditWriteInput` and callers supply it **from the authenticated
session**, never from a request body. `FRD/F02` Inputs: "`actor_id` (UUID, required, system-supplied
from session — never client-supplied)." Document this on the interface and enforce it at the only
HTTP entry point (task 3).

`withAudit(prisma, audit, fn)` — the helper every feature uses:

```typescript
export async function withAudit<T>(
  prisma: PrismaService,
  audit: AuditService,
  fn: (tx: Prisma.TransactionClient) => Promise<{ result: T; audit: AuditWriteInput | AuditWriteInput[] }>,
): Promise<T> {
  try {
    return await prisma.$transaction(async (tx) => {
      const { result, audit: events } = await fn(tx);
      for (const e of Array.isArray(events) ? events : [events]) {
        await audit.record(tx, e);
      }
      return result;
    });
  } catch (err) {
    if (isAuditWriteFailure(err)) {
      throw new ApiException(500, 'AUDIT_WRITE_FAILED',
        'Action could not be completed; audit record failed');
    }
    throw err;
  }
}
```

The `AUDIT_WRITE_FAILED` code, HTTP 500, and message are copied verbatim from `FRD/F02` Error
States. `FRD/Y2-errors.md` principle 2 ("No silent partial success") is satisfied because the
rollback is the transaction's, not an application compensation step.

Add a JSDoc block on `withAudit` stating that **every** state-changing operation in every later
phase routes through it, and that calling `prisma.$transaction` directly for an audited object is a
review-blocking mistake.

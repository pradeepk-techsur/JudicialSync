<objective>
Build the complete upload pipeline — allowlist, malware scan, encrypted storage, reference record —
with a real ClamAV instance, and the authenticated download path that returns the bytes.

Purpose: Phase 1 success criterion 5 requires that "an uploaded file of a disallowed type or failing
malware scan is rejected **before storage**, and all data is encrypted in transit and at rest."
CONTEXT rejected the cheaper option explicitly: "A stubbed/no-op scanner was rejected — success
criterion 5 requires demonstrating that a disallowed-type file and a scan-failing file are both
rejected *before storage*, which a stub cannot prove." The order of operations is itself the
requirement: `FRD/F13` Process step 3 says the allowlist is "enforced at upload; disallowed types
are rejected **before scanning is even attempted**," and step 2 says no file is persisted until
scanning completes.

This is also the service Phase 5's exhibit intake (F15) calls instead of building its own, so the
interface matters beyond this phase.

Output: `/files/upload`, `/files/{id}`, `/files/{id}/content`, the scanner and store adapters, and
two integration test files including an EICAR case.
</objective>

`AllowlistService.check(buffer, declaredContentType, courtId)`:
- Read the allowlist from the court's effective `rule_package_versions.config_snapshot.file_type_allowlist`.
  CONTEXT: "Features must read configuration from the database from day one, never from hardcoded
  constants." Hardcoding the list here is exactly the thing Phase 2 would then have to hunt down.
- **Sniff the content**, do not trust the header. `TechArch/04-security.md` §7.5: "Enforced
  server-side against a configurable allowlist per court profile, **independent of client-supplied
  MIME type (content-sniffed, not trusted from the `Content-Type` header)**." Use `file-type` on the
  first bytes; for `text/plain` (which has no magic number) fall back to a UTF-8 validity check over
  the whole buffer, and treat anything that fails as not-allowed rather than guessing.
- If the sniffed type is absent from the allowlist → throw
  `ApiException(422, 'SECURITY_FILE_TYPE_DENIED', 'This file type is not permitted')`, the exact
  code and message from `FRD/F13` Error States.
- If the sniffed type disagrees with the declared `Content-Type`, still decide on the **sniffed**
  value, and include both in the audit event's `after_state` — a mismatch is a useful signal even
  when the file is allowed.
- Enforce `config_snapshot.max_upload_bytes` (seeded 52428800) and reject an oversized body with
  `422 SECURITY_FILE_TOO_LARGE`. Configure the multipart parser's own limit to the same value so an
  attacker cannot force unbounded buffering before the check runs.

`ClamAvScanner.scan(buffer)` — real `clamd` INSTREAM over TCP to `CLAMAV_HOST:CLAMAV_PORT`:
- Connect, write `zINSTREAM\0`, then length-prefixed chunks (4-byte big-endian length + data) of at
  most 8 KiB, then a zero-length terminator, then read the reply.
- `stream: OK` → `{result: 'clean'}`. `stream: <SIG> FOUND` → `{result: 'infected', signature}`.
  Anything else → `{result: 'error'}`.
- Connection failure, socket error, or a timeout of `CLAMAV_TIMEOUT_MS` (default 30000) →
  `{result: 'error'}`.
- **`error` is not `clean`.** `FilesService` must reject on `error` with
  `503 SECURITY_SCANNER_UNAVAILABLE` ("File scanning is temporarily unavailable; upload rejected"),
  following `FRD/Y2-errors.md` principle 1 and the §7.5 rule that "`infected`/`error` results are
  rejected and logged." Add a comment: treating a scanner outage as clean is the single most likely
  way this control gets quietly disabled.
- Add a `ping()` using `zPING\0` → `PONG` for the readiness probe.

Note in the module's README comment that ClamAV's first boot loads signatures for a few minutes and that the `clamav/clamav:1.3.1_base` image ships them baked in, so no outbound network is needed.

`dto/file.dto.ts` — `zod` schema for the multipart fields: `declared_purpose` constrained to
`"exhibit" | "custody_condition_note" | "package_artifact"` (`FRD/F13` Inputs), optional `case_id`
(UUID). Response shape from `TechArch/03a-api-shared.md` §6.9:
`interface FileUploadResponse { file_reference_id: string; scan_status: "pending" | "clean" | "rejected" }`.

- `ensureBucket()` on module init, idempotent (`HeadBucket`, create on 404).
- `put(key, body, contentType)` issues `PutObjectCommand` with
  **`ServerSideEncryption: 'AES256'`** — encryption at rest per `TechArch/04-security.md` §7.5,
  backed by the `MINIO_KMS_SECRET_KEY` configured in plan 01-04's compose file. Keys are
  `files/{yyyy}/{mm}/{fileReferenceId}` — derived from a server-generated UUID, never from the
  client-supplied filename, which removes path traversal and collision as concerns entirely.
- `getObjectStream(key)` returns a `Readable`.
- **No presign method exists.** Add a comment explaining why: a presigned URL would be generated
  against the store's internal address (`minio:9000`), which the browser cannot resolve and which
  would not carry the caller's `Authorization` header anyway. Bytes move through the API.

`FilesService.upload(principal, file, dto)` — the order is the requirement:
1. **Allowlist check** on the sniffed content. Reject `422 SECURITY_FILE_TYPE_DENIED`. Nothing has
   been scanned and nothing has been stored.
2. **Scan** the buffer. `infected` → reject `422 SECURITY_MALWARE_DETECTED` ("File rejected: failed
   security scan"). `error` → reject `503 SECURITY_SCANNER_UNAVAILABLE`.
3. **Only now** `objectStore.put(...)`.
4. Insert `file_references` (`storage_pointer`, `file_type` = sniffed type, `uploaded_by` =
   `principal.user_id`, `declared_purpose`, `scan_status: 'clean'`) and `malware_scan_results`
   (`result: 'clean'`), together with the audit event, inside one `withAudit` transaction. If the
   database write fails after the object was stored, delete the orphaned object in a `catch` — the
   reverse order (DB first, then store) would leave a `file_references` row pointing at nothing,
   which is worse.

For a **rejected** upload, write a `file_references` row? No — `FRD/F13` Validation says "No file is
persisted to the reference/storage layer until malware scan completes successfully," so a rejection
creates **no** `file_references` row. Record the rejection as an audit event only
(`action_type: 'access_attempt'`, `after_state: {outcome:'rejected', reason: <code>, sniffed_type,
declared_type, size_bytes, signature?}`). §7.5 requires rejections be "rejected and logged"; the
audit trail is where that log lives. Note this reasoning in a comment — the `scan_status: 'rejected'`
enum value exists in the schema for a future asynchronous-quarantine model (the `pending` state),
and Phase 1 deliberately uses the synchronous path.

- `POST /files/upload` — multipart, `@Resource({type:'file', action:'upload'})`. Returns

- `GET /files/{id}` — metadata, `@Resource({type:'file', action:'read', idParam:'id'})`.
- `GET /files/{id}/content` — `@Resource({type:'file', action:'read', idParam:'id'})`, streams the

  event with outcome `granted` — `FRD/F13` and `FRD/F02` both treat access to a security-controlled
  artifact as material.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | Multipart upload bodies: attacker-controlled bytes, filenames, and declared content types. |
| API→scanner | The buffer crossing into ClamAV, and the scanner's verdict crossing back. |
| API→object store | Server-side writes and reads of file content. |
| API→browser | Download responses, which must carry bytes and never a store URL. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|

<objective>
Build the shared case/docket model API — the one representation of court, division, case,
proceeding, hearing, party, docket event, and document reference that both domain modules will read
through for the rest of the project.

Purpose: Phase 1 success criterion 2 requires that "there is no duplicate, module-specific case
representation for Evidentiary vs. Speedy Trial to later diverge from," and `FRD/F01` opens by
naming module-specific case models as "a core root cause of tool fragmentation." CONTEXT adds why
manual create/read/update is Phase 1 work rather than Phase 3 scaffolding: "`F01` describes manual
clerk entry as a permanent fallback ('when sync is unavailable or case predates sync'), not
temporary scaffolding."

The structural commitment in this plan is the absence of something: **no DELETE endpoint, anywhere.**
CONTEXT: "No hard deletes anywhere in the case model. No `DELETE` endpoints. Removal is always a
status transition … Soft-delete columns were rejected as a competing second meaning of 'gone.'"
Plan 01-03 already removed the database grant; this plan makes sure the API never pretends to offer
one.

Output: the `/cases` family of endpoints, `CaseContextService`, and three integration test files.
</objective>

<feature_dependencies>
Implements: F1: Core Case and Docket Data Model (entity hierarchy, source-identifier preservation, security-designation tagging, shared case-context API)
Depends on: F0: Identity and Access Management — the PDP guard from plan 01-07 scopes every read and write; F2: Audit Trail and Audit Explorer — `withAudit` for every mutation
Enables: F1 — Phase 3's CM/ECF adapter (F10) writes through these same records; Phases 5–8 read case context exclusively through `CaseContextService`
</feature_dependencies>

Do not rename fields to camelCase in the wire contract — the generated TypeScript client in plan

`CasesService.create(principal, dto)`:
- Validate `division_id` belongs to `court_id`; otherwise `422 CASE_INVALID_DIVISION`.
- **Require at least one `defendant` party** → `422 CASE_MISSING_DEFENDANT` ("At least one defendant
  party is required"), the exact code and message from `FRD/F01` Error States. `US-1.2` ties this to
  the Phase 7 tracker precondition.
- Set `source_system: 'manual'`, `source_identifier: null`, `locally_modified: false` — `FRD/F01`
  Validation: "manually entered events are flagged `source_system = 'manual'`."
- On the `UNIQUE (division_id, case_number)` violation, translate Postgres `23505` into
  `409 CASE_DUPLICATE_NUMBER` ("A case with this number already exists in this division"). Catch the
  constraint violation rather than pre-checking — a pre-check races, the constraint does not.
- Insert the case and its parties, and emit **one** `status_change` audit event for the case plus one
  per party, all inside a single `withAudit` call (the helper accepts an array).

`CasesService.get(id)` returns the `Case` shape. The ABAC guard has already authorized it; the
service must not re-filter by court, or a scope bug would be masked in one place and live in another.

`CasesService.updateStatus(principal, id, status)` — `PATCH /cases/{id}/status` accepting
`'open' | 'closed' | 'superseded'`. This is the **only** removal mechanism. Reject an invalid
transition with `409 CASE_INVALID_TRANSITION`. Set `locally_modified = true` on any local edit of a
sync-eligible record — CONTEXT requires the flag be "set correctly for manual entry
(`source_system = 'manual'`) and flipped on local edit," because Phase 3's conflict logic will read
it and a Phase 3 backfill "would leave pre-backfill edits with unknowable provenance."

**Court/division immutability.** `FRD/F01` Process step 2: "Court/division association is assigned
at case creation and is immutable thereafter (a case does not move between courts)." There is no
endpoint that changes them, and `CasesService` must reject any attempt — add an explicit guard in
the update path and a comment, because the natural next feature request is "move this case."

`CaseContextService` — the single shared read surface, and the structural answer to criterion 2:
- `getCaseContext(caseId)` returns case + proceedings + hearings + parties + designations in one
  object.
- `listCasesForPrincipal(principal, filter)` returns cases the principal may see. Scope filtering
  here is a **pre-filter for list endpoints**, not a substitute for the PDP: the guard authorizes
  the *route*, and this filters the *collection*, since a list cannot be a single PDP decision.
  Build the filter from the principal's court/division/case scopes, and **exclude** cases carrying a
  designation the principal lacks the entitlement for. Per `TechArch/04-security.md` §7.6 the
  exclusion must be a pre-filter, not a post-hoc redaction, "so result counts, ranking positions,
  and response timing cannot be used to infer the existence of a sealed matter," and per
  `UX-Mockup/Y0-patterns.md` "Non-Disclosure of Sealed/Restricted Existence" the record is "omitted
  entirely — never shown as a greyed-out row, a 'restricted' placeholder, or a count that includes
  it."
  Write an `access_attempt` audit event when the filter actually excludes rows, recording the count
  — the attempt is invisible to the requester but visible later to an authorized auditor.
- Add a class-level JSDoc quoting `FRD/F01` step 8: "Both domain modules read case/proceeding/party/
  docket-event context exclusively through the shared case-context API — no module maintains a
  shadow copy of this data." Phases 5–8 will read this comment.

**Provenance rules** (`FRD/F01` Validation, `US-1.3`, and CONTEXT's "Full provenance fields ship in
Phase 1"):
- Manual creation sets `source_system: 'manual'` and generates a deterministic
  `source_identifier` of the form `manual:{caseId}:{uuid}` — `docket_events` has
  `UNIQUE (source_system, source_identifier)` and the column is `NOT NULL`, so a manual event still
  needs one. Document the format.
- A request that declares a non-`manual` `source_system` but omits `source_identifier` →
  `422 CASE_EVENT_MISSING_SOURCE` ("Imported docket events must include a source identifier"), the
  exact code from `FRD/F01` Error States. The rule exists for Phase 3's adapter; enforce it now so
  the adapter inherits it.
- Any PATCH to a record whose `source_system !== 'manual'` sets `locally_modified = true`.
  Do **not** detect, flag, or queue a conflict — Phase 3 owns that.

**Proceeding closure, not deletion.** `FRD/F01` Validation: "A proceeding cannot be deleted once it
has associated exhibit or Speedy Trial activity — it may only be marked `closed`." In Phase 1
neither activity table exists, so implement the rule in its final form and have the
"has activity" predicate consult a `ProceedingActivityProbe` interface with a Phase 1 implementation
that returns `false` and a comment naming Phase 5 (`exhibits`) and Phase 7 (`defendant_trackers`) as
the future contributors. The `409 CASE_PROCEEDING_IN_USE` path must exist and be reachable in tests
via a stubbed probe — writing the rule now and the probe later is what keeps Phase 5 from having to
rediscover it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | Case creation and mutation payloads naming courts, divisions, and designations. |
| db→render | Case collections returned to a caller, where a sealed record's mere presence is itself sensitive. |
| client→list endpoint | Query parameters influencing which rows a collection endpoint returns. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-35 | Information disclosure | A sealed case leaking through `GET /cases` as a redacted row, a placeholder, or an inflated total | mitigate | `CaseContextService.listCasesForPrincipal` applies designation and scope exclusion as a SQL **pre-filter**, so excluded rows never enter the result set or the count; asserted by the list test comparing `clerk_case_admin` and `judge` results. (`TechArch/04-security.md` §7.6, `UX-Mockup/Y0-patterns.md`) |
| T-01-36 | Tampering | A caller escalating across courts by supplying another court's `court_id`/`division_id` on create | mitigate | `CasesService.create` validates that `division_id` belongs to `court_id` and plan 01-07's `ResourceLoaderService` validates body-supplied ids against the database before the PDP decision; court/division are immutable after creation and no endpoint changes them. |
| T-01-37 | Tampering | Destruction of docket-sourced or audit-feeding records | mitigate | No `@Delete(` route and no Prisma delete call exists under `modules/case-context/`; `app_rw` holds no DELETE grant (plan 01-03); `apps/api/test/case-no-delete.e2e-spec.ts` asserts both the HTTP and SQL layers refuse. |
| T-01-38 | Elevation of privilege | An unauthorized user altering a case's security designation, downgrading protection for everything downstream | mitigate | `designations.controller.ts` carries `@Resource({type:'security_designation', action:'update'})`, which plan 01-02's `action_entitlement_map` row `security_designation / update` binds to `case_security_admin`; denial returns `403 CASE_DESIGNATION_DENIED` and writes an `access_attempt` audit event. The sibling case-model routes are bound by their own rows in that same table (`case`, `proceeding`, `hearing`, `party`, `docket_event`, `document_reference` × `read`/`create`/`update`), not by this one. |
| T-01-39 | Repudiation | A designation or status change with no record of who made it | mitigate | Every mutation routes through `withAudit`; designation changes use `action_type: 'designation_change'` with full before/after sets and the session-derived actor. |

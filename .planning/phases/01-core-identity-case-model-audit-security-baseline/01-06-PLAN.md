<objective>
Implement real identity: an OIDC exchange with the Keycloak court IdP, MFA assertion verification,
session issuance with rotating refresh tokens and immediate revocation, and the entitlement
resolution that produces the `Principal` every authorization decision consumes.

Purpose: CONTEXT locks this harder than any other area. "Real OIDC against a local Keycloak
container … not a stub, not a parallel dev-login code path." "No stub/bypass authentication path
exists. A second 'dev login' route was explicitly rejected because the stub becomes the
daily-exercised path and the real integration rots." "MFA is real TOTP … No dev bypass flag."
Those are not style preferences — an authentication layer that has never been exercised against a
real IdP is an authentication layer nobody has tested.

The second half of this plan is quieter but just as load-bearing: entitlement resolution must read
`entitlement_grants` and **nothing else**. The moment entitlements are derived from `user_roles`,
CONTEXT's hard constraint ("Role existence must never imply access") is dead, and no later test can
resurrect it.

Output: `/auth/*` endpoints, a working `SessionAuthGuard`, `EntitlementResolverService`, and three
integration test files that drive a real token out of a real Keycloak.
</objective>

`oidc.provider.ts` — a genuine `openid-client` implementation:
- Discover the issuer at `OIDC_ISSUER_URL`
  (`https://judicialsync.localhost:8443/auth/realms/judicialsync`) on module init, with retry and
  backoff. If discovery never succeeds, the provider must **throw on use**, surfacing
  `503 AUTH_IDP_UNAVAILABLE` ("Authentication service temporarily unavailable" — exactly as
  `FRD/F00` Error States specifies). `TechArch/04-security.md` §7.1: "Fail-closed: if the IdP is
  unreachable, authentication fails with `503 AUTH_IDP_UNAVAILABLE`; the system never falls back to
  an unauthenticated or degraded-trust mode."
- Authorization Code flow **with PKCE** (`S256`), `state` and `nonce` generated per attempt and
  held in Redis with a short TTL; reject a callback whose `state` is unknown, already consumed, or
  expired (replay protection), and reject a token whose `nonce` does not match.
- Validate the ID token signature against the issuer JWKS, plus `iss`, `aud`
  (must equal `OIDC_CLIENT_ID`), and `exp`. An invalid or expired assertion yields
  `401 AUTH_INVALID_ASSERTION` ("Authentication failed; please sign in again").
- **MFA derivation — the piece with no bypass.** Set
  `mfa_satisfied = (Number(claims.acr) >= 2) || (Array.isArray(claims.amr) && claims.amr.includes('otp'))`.
  The realm from plan 01-04 maps `acr.loa.map {"otp": 2}` and makes the OTP form REQUIRED. If
  `mfa_satisfied` is false, the caller rejects with `401 AUTH_MFA_FAILED` ("Multifactor verification
  failed"). Write an explicit comment: *there is deliberately no environment flag that can make this
  return true; CONTEXT rejected an MFA bypass.*
- Request `openid profile email` scopes; map `sub → subject`, `name → display_name`,
  `email → email`.

TLS trust: the provider uses Node's default agent, which trusts the Caddy internal CA via
`NODE_EXTRA_CA_CERTS` set in plan 01-04's compose file. **Never** set
`NODE_TLS_REJECT_UNAUTHORIZED=0` or pass `rejectUnauthorized: false` — add a grep assertion for this
in the task `<verify>`.

`identity.module.ts` provides `IdpProvider` via a factory token bound to `OidcProvider`, so a future
SAML provider is a one-line binding change — which is what CONTEXT means by "Build the IdP
integration so SAML can be added behind the same abstraction."

`SessionService` backed by the `platform.sessions` table from plan 01-03
(`refresh_token_hash`, `mfa_satisfied`, `issued_at`, `expires_at`, `revoked_at`).

- `issue(userId, mfaSatisfied)` — creates a `sessions` row and returns a signed JWT access token
  carrying `{sub: userId, sid: sessionId, mfa: mfaSatisfied}` plus a refresh token. Per
  `TechArch/04-security.md` §7.1: access token **5–15 min**, refresh token longer-lived and
  **rotating**, and "refresh tokens are stored hashed (`sessions.refresh_token_hash`), never in
  plaintext" — hash with SHA-256 before storing, compare with `crypto.timingSafeEqual`. Read the
  TTLs from the seeded `rule_package_versions.config_snapshot.session` values
  (`access_token_ttl_seconds: 900`, `refresh_token_ttl_seconds: 604800`), **not** from constants —
  CONTEXT: "Features must read configuration from the database from day one, never from hardcoded
  constants."
- `validate(bearer)` — verifies the JWT, then loads the `sessions` row and rejects if
  `revoked_at IS NOT NULL` or `expires_at < now()`, with `401 AUTH_SESSION_EXPIRED`. §7.1 requires
  this be "enforced via a revocation check on every token validation, **not merely token expiry**."
  The revocation check is a database/Redis read on every request — do not cache the revocation
  state longer than the configured `claim_cache_seconds`, and invalidate the cache key on revoke.
- `rotate(refreshToken)` — validates the hash, marks the old session revoked, issues a new one.
  Detect reuse of an already-rotated refresh token and, on detection, revoke **all** sessions for
  that user and emit an `access_attempt` audit event: refresh-token reuse is the classic signal of a
  stolen token.
- `revoke(sessionId)` and `revokeAllForUser(userId)` — the latter is what `FRD/F00` Process step 7
  requires: "On role or scope-attribute change … active sessions are invalidated and the user must
  re-authenticate to receive updated entitlements."
- Enforce `concurrent_session_limit` (seeded value `3`): issuing beyond the limit revokes the
  oldest active session for that user.

Decorators: `/auth/login`, `/auth/mfa-challenge`, `/auth/refresh` are `@Public()`; `/auth/logout`
and `/auth/entitlements` are `@SelfScoped()` (session required, no resource ABAC — they address
only the caller's own identity; plan 01-01 defines and justifies this marker). Add the
authorization-URL helper route `GET /auth/authorize-url` (`@Public()`) returning the Keycloak
redirect, which the frontend in plan 01-13 uses to start the flow.

On `/auth/login`: exchange the assertion, reject non-MFA sessions with `401 AUTH_MFA_FAILED`,
upsert the `users` row by `external_idp_subject` (a first-time user gets **zero** roles and **zero**
entitlements — `FRD/F00` Sub-features: "Least-privilege default (new accounts start with zero module
access until explicitly role-assigned)"), issue the session, and return the computed entitlements
for UI gating. Mark clearly in the response DTO comment that entitlements are **for UI gating only
and never trusted as the authorization decision** (`TechArch/03a-api-shared.md` §6.1).

`/auth/mfa-challenge` exists because the API contract lists it. In this deployment Keycloak owns the
OTP form, so the endpoint accepts an `mfa_challenge_response` only for an IdP that returns a
`mfa_required` interim state; against the Phase 1 realm it returns
`422 AUTH_MFA_NOT_REQUIRED_AT_THIS_STEP` with a message explaining the IdP completed MFA inline.
Document this in `docs/IDP-INTEGRATION.md`. Do **not** implement a parallel application-side OTP
verifier — that would be exactly the second authentication path CONTEXT rejected.

**Audit every authentication event** (`FRD/F00` Process step 8: "All authentication events (success,
failure, MFA challenge outcome, session termination) are emitted as audit events"). Route each
through `withAudit` with `action_type: 'access_attempt'`, `object_type: 'session'`,
`object_id: sessionId`, `client_ip` from the request, and an `after_state` recording the outcome.
For a *failed* login where no user resolves, use the resolved-subject user if one exists; if the
subject is unknown, record against the reserved unattributed actor that plan 01-04 seeds —
`external_idp_subject = 'system:unattributed'`, exported from `SEED_IDS` as
`UNATTRIBUTED_ACTOR_USER_ID`. Never skip the audit: `actor_id` is `NOT NULL`, and dropping the event
because attribution is awkward would lose exactly the records an intrusion investigation needs.
Resolve the id by querying `users` for that subject at startup and fail fast if it is absent, rather
than creating it here — plan 01-04 owns `prisma/seed/identity.ts` and this plan must not write to it.

Replace plan 01-01's `SessionAuthGuard` stub body: read the `Authorization: Bearer` header, call
`SessionService.validate`, attach the resolved `Principal` to `request.principal`, and throw
`401 AUTH_SESSION_EXPIRED` on any failure. Keep the `@Public()` short-circuit exactly as written.

`apps/api/test/auth-login.e2e-spec.ts`:
- Password + valid TOTP via the realm's direct-access grant → `/auth/login` returns 200 with

`apps/api/test/auth-session.e2e-spec.ts`:
- A valid session reaches a `@SelfScoped()` route; after `/auth/logout`, the **same** token is

- `revokeAllForUser` causes an active token to be rejected on the next request without waiting for
  expiry.
- `/auth/refresh` rotates: the old refresh token no longer works, the new one does.
- Replaying a rotated refresh token revokes all of that user's sessions and writes an
  `access_attempt` audit event.
- Issuing a fourth concurrent session revokes the oldest (seeded limit is 3).
- The stored `sessions.refresh_token_hash` never equals the plaintext refresh token.

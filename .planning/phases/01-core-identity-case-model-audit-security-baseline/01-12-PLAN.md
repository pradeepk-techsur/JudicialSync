<objective>
Build the read half of the audit feature — the Audit Explorer query API with its separation-of-duties
and designation gating — and the scheduled hash-chain verification job that makes "tamper-evident"
an observed property rather than a claim.

Purpose: `FRD/F02` Validation requires that "Audit read access requires a distinct `audit_reader`
entitlement, never implied by operational edit roles alone," and that "Hash-chain verification
failures must raise a P0 exception-queue item, not merely a log line." CONTEXT resolves the timing
problem that the Exception Queue is Phase 3: "The BullMQ hash-chain verification job is built in
Phase 1. Writing a chain but never checking it leaves 'tamper-evident' unproven for two phases. A
detected break writes a persistent **`integrity_alert` record**, logs at critical severity, and
surfaces in the Audit Explorer. Log-only was rejected as too easy to miss and leaving no
audit-visible trace of detection. Phase 3 routes those existing `integrity_alert` records into the
Exception Queue — an addition, not a rewrite."

Output: `GET /audit/explorer`, the integrity status and alert endpoints, `ChainVerifierService`, the
BullMQ processor, and two integration test files — one of which deliberately corrupts a row.
</objective>

`explorer.dto.ts` — `zod` schema matching `AuditExplorerQuery` from

The response item is the `AuditEvent` shape from §6.3 **plus** two derived fields `Screen-17`

`AuditExplorerService.query(principal, filter)`:
- **Separation of duties** is enforced by the route's `@Resource({type:'audit_event', action:'read'})`,
  which plan 01-02's map binds to `audit_reader`. Denial surfaces as `403 AUDIT_READ_DENIED`
  ("You do not have audit explorer access") via plan 01-07's resource-type → error-code table.
  Deliberately do **not** add a second check in the service: one enforcement point, and it is the
  PDP. `US-2.3` is satisfied by the seeded grant distribution (`security_officer` holds
  `audit_reader` without `case_read`; `clerk_case_admin` holds edit entitlements without
  `audit_reader`) plus the tests below.
- **Designation scoping.** `FRD/F02` Validation: "Sealed/restricted-case audit entries are
  themselves access-restricted — viewing them requires the same security-designation entitlement as
  viewing the underlying record." Join each audit row to its underlying case
  (via `object_type`/`object_id` → the case graph, reusing plan 01-07's resolution logic) and
  **exclude** rows whose case carries a designation the principal lacks, as a SQL pre-filter.
  `TechArch/04-security.md` §7.6 requires the exclusion be pre-ranking so counts and timing cannot
  leak existence; a post-filter over a fetched page would also break pagination in a
  privilege-dependent way.
- **The denied attempt is itself logged.** When the filter excludes rows, or when the caller
  explicitly filtered by a `case_id` they cannot see, write an `access_attempt` audit event
  (`object_type: 'audit_event'`) recording the attempted filter. `FRD/F02` Validation: "the
  *attempt* to view a sealed audit entry without entitlement is itself logged as an audit event
  (access_attempt)." When the caller named a specific sealed `case_id` **and** holds case-level
  access to it, return `403 AUDIT_DESIGNATION_DENIED` ("This case's audit history requires
  additional authorization") rather than an empty list — `FRD/Y2-errors.md` principle 3, the
  parent-access branch. When they have no access path to that case at all, return an empty result
  set indistinguishable from "no matching events."
- **Denied attempts appear as rows.** `Screen-17` States: "Denied access attempt in results — Row
  shown with 'denied' Tag, **not omitted** … Distinguishes 'tried and was told no' from records that
  simply don't exist." So `access_attempt` events must be first-class results, not filtered out of
  the default view. Expose `object_type=access_attempt`… no — `access_attempt` is an `action_type`,
  not an `object_type`. Add an `action_type` filter to the query DTO (it is absent from the FRD's
  listed filters but required by the screen) and include `access_attempt` rows by default. Note the
  addition in the SUMMARY as a spec gap closed by the mockup.

  <name>Task 2: Implement the chain verifier, its BullMQ schedule, and integrity_alert records</name>
  <files>apps/api/package.json, apps/api/src/modules/audit/integrity/chain-verifier.service.ts, apps/api/src/modules/audit/integrity/integrity.processor.ts, apps/api/src/modules/audit/integrity/integrity.controller.ts, apps/api/src/modules/audit/audit.module.ts, .env.example</files>
  <action>
Plan 01-01 already installed `bullmq@^5` and `@nestjs/bullmq@^10` — the version `TechArch/05-tech-stack.md` §8.2 names, Redis-backed, with "audit hash-chain verification job" listed among its purposes — and declared `AUDIT_INTEGRITY_INTERVAL_MS` and `AUDIT_INTEGRITY_SCHEDULE_ENABLED` in `.env.example`. **Do not modify `apps/api/package.json` or `.env.example`.**

`ChainVerifierService.verify({fromOccurredAt?})` — re-walks the chain and checks three things:
1. **`row_hash_mismatch`** — recompute each row's hash with `computeRowHash` from plan 01-05 and
   compare to the stored `row_hash`. Use the TypeScript implementation rather than calling
   `platform.compute_audit_row_hash`, so the verifier is **independent of the database function the
   trigger uses**. If both sides were the same code, a compromised function would validate its own
   forgeries. Plan 01-05's parity suite is what keeps the two implementations honest.
2. **`prev_hash_mismatch`** — each row's `prev_hash` equals the preceding row's `row_hash` in
   `(occurred_at, id)` order; the first row's `prev_hash` is the 64-zero genesis value.
3. **`chain_head_mismatch`** — `audit_chain_head.last_row_hash` equals the final row's `row_hash`.
   This is the check that catches a *deleted tail*: removing the last N rows leaves a chain that is
   internally consistent but no longer matches the recorded head.

Process in batches of 1000 ordered by `(occurred_at, id)`, streaming rather than loading the table.
Support an incremental window via `fromOccurredAt` (default: since the last successful verification,
tracked in Redis) **and** a full re-walk mode — `TechArch/04-security.md` §7.3 says the job
"re-walks the entire chain (or an incremental window)." Schedule incremental frequently and full
rarely.

On **any** break:
- Insert an `integrity_alerts` row: `alert_type: 'audit_integrity_break'`, `severity: 'critical'`,
  `audit_event_id`, `expected_hash`, `actual_hash`, `detail` JSONB with the break kind and
  surrounding row ids, `status: 'open'`. CONTEXT: "A detected break writes a persistent
  `integrity_alert` record … Log-only was rejected."
- Log at `error`/critical with `AUDIT_CHAIN_BROKEN` — the code from `FRD/F02` Error States,
  described there as "500 (internal alert, not user-facing)".
- **Do not stop at the first break.** Collect all breaks in the window so an operator sees the full
  extent; a single-break report invites the assumption that one row was touched.
- Never attempt repair. There is no code path that rewrites an audit row — the database would
  refuse it anyway (plan 01-03), and a "self-healing" audit trail is a contradiction.

`IntegrityProcessor` — a BullMQ worker on queue `audit-integrity` with a repeatable job every
`AUDIT_INTEGRITY_INTERVAL_MS` (default 900000 / 15 min) for the incremental window and a daily full
re-walk. Register the queue in `AuditModule`. Make the schedule disableable **for tests only** via
`AUDIT_INTEGRITY_SCHEDULE_ENABLED=false`; the verifier itself remains callable, so this is a
scheduling switch, not a verification bypass — state that distinction in a comment, because it is
the kind of flag that gets mistaken for one.

Persist `last_verified_at` and the last result summary in Redis so `/audit/integrity/status` can
answer without re-walking.

`integrity.controller.ts`:
- `GET /audit/integrity/status` → `{chain_verified, last_verified_at, open_alert_count}`. This backs
  `Screen-17`'s always-visible "🔒 Chain verified ✓" badge and its "Chain broken" critical-alert
  state. `@Resource({type:'audit_event', action:'read'})` — the badge is part of the Explorer, so it
  carries the same `audit_reader` requirement.
- `GET /audit/integrity/alerts` → open `integrity_alerts`, same resource descriptor. CONTEXT
  requires a detected break "surfaces in the Audit Explorer."
- `POST /audit/integrity/verify` → runs an on-demand verification. `@Resource({type:'audit_event',
  action:'approve'})` so it needs `audit_reader`; rate-limit it to one concurrent run via a BullMQ
  job id, since a full re-walk is expensive and an unbounded trigger is a denial-of-service lever.

Do **not** create `exceptions` rows, a queue UI, or a resolution workflow — Phase 3 owns those and
will read `integrity_alerts` as-is.

`apps/api/test/audit-integrity-job.e2e-spec.ts` — the test CONTEXT named explicitly ("Deliberately
corrupt an audit row and assert the integrity job detects the chain break"):
1. **Clean chain verifies.** Write a handful of audit events, run `verify()` → `verified: true`,
   zero breaks, zero `integrity_alerts` rows. `GET /audit/integrity/status` reports
   `chain_verified: true`.
2. **`row_hash` corruption detected.** Using the **`app_dba`** connection — `app_rw` cannot UPDATE
   `audit_events`, which is itself the point, so assert that first: an `app_rw` UPDATE fails with
   SQLSTATE `42501`, and only then corrupt the row as `app_dba`. Mutate one past row's
   `action_type`. Run `verify()` → `verified: false` with a `row_hash_mismatch` break naming that
   `audit_event_id`, and one `critical` `integrity_alerts` row exists with `expected_hash` and
   `actual_hash` populated.
3. **`prev_hash` corruption detected.** As `app_dba`, alter a middle row's `prev_hash` → a
   `prev_hash_mismatch` break is reported.
4. **Tail deletion detected.** As `app_dba`, delete the last row → `chain_head_mismatch` is
   reported. This is the case a naive "each row hashes correctly" verifier misses entirely.
5. **Multiple breaks all reported.** Corrupt two rows → both appear in `breaks`.
6. **Alert surfaces in the Explorer.** `GET /audit/integrity/alerts` as `security_officer` returns
   the alert; `GET /audit/integrity/status` reports `chain_verified: false` and
   `open_alert_count >= 1`. A user without `audit_reader` → 403.
7. **No repair.** After detection, the corrupted row is still corrupted — the system reports, it
   does not rewrite. Assert the row's stored values are unchanged.
8. **The scheduled job actually runs.** With `AUDIT_INTEGRITY_SCHEDULE_ENABLED=true` and a short
   interval, wait for one cycle and assert `last_verified_at` advanced without an explicit call.
9. **Verification runs do not themselves break the chain** — running `verify()` twice in a row on a
   clean chain yields `verified: true` both times and adds no audit rows.

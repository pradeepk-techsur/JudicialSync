**The single-origin decision.** Keycloak must be reachable at the *same* URL from the browser
(redirect flow) and from the API container (discovery + token validation), or the `iss` claim will
not match and every login fails. Solve it with one TLS origin in front of everything:

Hostname: `judicialsync.localhost`. Browsers resolve `*.localhost` to loopback; inside the Compose
network a network alias on the proxy service makes the same name resolve to Caddy. Caddy's
`tls internal` CA certificate is shared into the API container so Node trusts it — this is a trust
anchor, not a verification bypass. Never set `NODE_TLS_REJECT_UNAUTHORIZED=0`.

`Caddyfile`:

```
{
  auto_https disable_redirects
}

judicialsync.localhost:8443 {
  tls internal
  encode gzip
  handle /auth/* {
    reverse_proxy keycloak:8080
  }
  handle /api/* {
    reverse_proxy api:3000
  }
  handle {
    # plan 01-13 replaces this with: reverse_proxy web:5173
    respond "JudicialSync Platform Core. UI ships in plan 01-13. API: /api/v1/health" 200
  }
}
```

MINIO_ROOT_USER: ${S3_ACCESS_KEY_ID}

`MINIO_KMS_KEY_B64` is a base64 32-byte value in `.env`; document in `.env.example` that production

The Caddy internal CA lives at `/data/caddy/pki/authorities/local/root.crt` inside the `caddydata`
volume. Add a tiny `init-ca` step in the api service's command that copies it to
`/caddy-ca/root.crt` before Node starts (`mkdir -p /caddy-ca && cp /caddy-ca-src/caddy/pki/authorities/local/root.crt /caddy-ca/root.crt`),
and order `proxy` ahead of `api` with `depends_on: proxy: {condition: service_started}` so the CA
exists. If the copy fails, fail the container — a silently untrusted CA would surface much later as
an inscrutable OIDC error.

CONTEXT: "Real OIDC against a local Keycloak container. Keycloak acts as the stand-in court IdP with
a seeded realm… Swapping in a court's real IdP must be a configuration change." And: "MFA is real
TOTP, enforced in Keycloak. The OTP policy is enabled for internal-role users; the application reads
the `amr`/`acr` claim from the assertion and rejects sessions where MFA was not satisfied. No dev
bypass flag."

Author `infra/keycloak/realm-judicialsync.json` as a full realm import:

```json
{
  "realm": "judicialsync",
  "enabled": true,
  "sslRequired": "external",
  "otpPolicyType": "totp",
  "otpPolicyAlgorithm": "HmacSHA1",
  "otpPolicyDigits": 6,
  "otpPolicyPeriod": 30,
  "attributes": { "acr.loa.map": "{\"otp\":2}" },
  "browserFlow": "browser-mfa",
  "clients": [ ... ],
  "authenticationFlows": [ ... ],
  "users": [ ... ]
}
```

**Client** `judicialsync-internal`: confidential (`publicClient: false`), `standardFlowEnabled: true`,
`directAccessGrantsEnabled: true` (needed so integration tests can obtain a token with a computed
TOTP code without driving a browser), `serviceAccountsEnabled: false`,
`redirectUris: ["https://judicialsync.localhost:8443/*"]`,
`webOrigins: ["https://judicialsync.localhost:8443"]`,
`secret: "${OIDC_CLIENT_SECRET}"` (literal value in the file for local dev; `.env.example` documents
that production resolves it from the secrets manager),
and `attributes: { "default.acr.values": "2", "minimum.acr.value": "2" }`.

**Audience separation** per `TechArch/04-security.md` §7.1: declare the internal client with an
explicit audience mapper emitting `aud: judicialsync-internal`. Do **not** create the external
attorney portal client — that is `F12`, Phase 4 — but leave a comment in the file noting the realm
is structured so a second client with a distinct audience can be added without reshaping the realm.
CONTEXT: "the Phase 1 abstraction should not preclude that."

**MFA enforcement.** Copy Keycloak 24's built-in `browser` flow to `browser-mfa` and make the OTP
form **REQUIRED** (not CONDITIONAL) for this realm, so there is no path to a session without TOTP.
Combined with `acr.loa.map {"otp": 2}` and the client's `minimum.acr.value: 2`, a successful
authentication yields `acr: "2"` in the token; plan 01-06 rejects any session whose `acr` is below
2 or whose `amr` lacks `otp`. There is deliberately **no** bypass flag, per CONTEXT.

**Users — exactly one per role, all ten.** Each with:
- `username` = the role name (e.g. `judge`, `law_clerk`, … `security_officer`)
- `enabled: true`, `emailVerified: true`, `firstName`/`lastName` drawn from
  `PERSONAS-JudicialSync.md` where a persona exists
- a password credential (`type: "password"`, `temporary: false`) — value per role, documented
- a **pre-provisioned TOTP credential**: `{"type":"otp","userLabel":"seed-totp","secretData":"{\"value\":\"<BASE32_SECRET>\"}","credentialData":"{\"subType\":\"totp\",\"digits\":6,\"counter\":0,\"period\":30,\"algorithm\":\"HmacSHA1\"}"}`
  with a distinct, documented Base32 secret per user.
- `attributes: { "court_code": ["NDCA"] }` for the first eight users and `["SDNY"]` for two, so
  cross-court isolation is demonstrable at the IdP level too.

Pre-provisioning the TOTP secret is what makes MFA testable: Playwright and the integration suite
compute the current code with `otplib` instead of needing a human with a phone. A human *can* still
scan the same secret into any authenticator app, which is what CONTEXT means by "demonstrable
end-to-end with any authenticator app."

`docs/SEED-CREDENTIALS.md` — a table of role · username · password · TOTP Base32 secret · court,
prefixed with a bold warning that these are local-development credentials only and that the realm
file must never be used in any environment reachable from outside the developer's machine. Add a row
note for `jury_admin`: **"holds the role and zero entitlements — this user exists to prove CONTEXT's
hard constraint that role existence never implies access."**

`KEYCLOAK_ADMIN_PASSWORD`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `MINIO_KMS_KEY_B64`, `S3_ACCESS_KEY_ID`, and `S3_SECRET_ACCESS_KEY` are already declared in `.env.example` by plan 01-01 — set their local values in `.env` only (which is gitignored); **do not modify `.env.example`**.

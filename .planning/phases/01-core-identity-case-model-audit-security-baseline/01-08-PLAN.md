<objective>
Implement the two-step grant workflow — request, then approval by a *different* person — and the
narrowly constrained bootstrap mechanism that exists only because an empty system has no second
person.

Purpose: CONTEXT is explicit about both the rule and the reason. "Two-step request → approve,
enforced server-side at the API layer. A grant is a record with a requester and a distinct approver;
the API rejects any approval where `approver == requester` with `403 AUTH_SOD_VIOLATION`. **'The
audit trail will catch it' is explicitly not sufficient — the API must refuse.**" `US-0.3` makes it
an acceptance criterion, and `TechArch/04-security.md` §7.2 adds that it must be "enforced as a
policy rule … not an application-layer `if` statement that a future refactor could drop."

Both are satisfied here, in three independent layers: the Rego rule from plan 01-02, a service-layer
check, and the table-level `CHECK (decided_by IS NULL OR decided_by <> requested_by)` from plan
01-03. Defense in depth is warranted because this is the control that keeps a single compromised
administrator from granting themselves the entire system.

Bootstrap gets equal care in the opposite direction: it is the one hole in the two-person rule, so
every constraint CONTEXT placed on it is implemented and tested, and it closes itself.

Output: the grant lifecycle API, the bootstrap mechanism, and two integration test files.
</objective>

  <files>apps/api/src/modules/entitlements/dto/grant.dto.ts, apps/api/src/modules/entitlements/grants.service.ts, apps/api/src/modules/entitlements/grants.controller.ts, apps/api/src/modules/entitlements/entitlements.module.ts</files>
  <action>
`grant.dto.ts` — `zod` schemas for the request bodies. `justification` is required and at least 10
characters, matching `FRD/Y2-errors.md`'s rationale convention ("Rationale must be at least 10
characters") with code `GRANT_RATIONALE_TOO_SHORT` (422). A grant of standing authority over court
records is exactly the "legally significant action" that convention exists for.

`GrantsService`:

**`request(principal, dto)`** — inserts an `access_grant_requests` row with
`requested_by = principal.user_id`, `status = 'pending'`, `is_bootstrap = false`. Validate that:
- the subject user exists and is `active`;
- for `grant_type: 'role'`, `role_id` resolves in `roles`; for `'entitlement'`, `entitlement_key`
  resolves in `entitlement_definitions` (a request for an entitlement that does not exist in the
  catalog is `422 GRANT_UNKNOWN_ENTITLEMENT`, not a silently created one);
- an identical non-revoked grant does not already exist → `409 GRANT_DUPLICATE`.
Write the row and its `approval`-type audit event atomically via `withAudit`, with `after_state`
recording subject, grant type, scope, and justification.

**`approve(principal, requestId)`** — the control that matters:
1. Load the request `FOR UPDATE` inside the transaction (two approvers clicking simultaneously must
   not both succeed).
2. **If `request.requested_by === principal.user_id`, throw
   `ApiException(403, 'AUTH_SOD_VIOLATION', 'Separation-of-duties violation: cannot approve your own request')`.**
   The code and message are verbatim from `FRD/F00` Error States. Write a comment stating this
   check is deliberately redundant with the Rego rule and the table CHECK, and that **none of the
   three may be removed** — each covers a different failure mode (a bypassed guard, a direct
   service call, a raw SQL path).
3. Reject a non-`pending` request with `409 GRANT_INVALID_TRANSITION`.
4. Set `status='approved'`, `decided_by=principal.user_id`, `decided_at=now()`.
5. Materialize the grant: for `'entitlement'`, insert `entitlement_grants` with
   `granted_by = principal.user_id`, `granted_at = now()`, `request_id`; for `'role'`, insert
   `user_roles` with `granted_by`, `granted_at`, `request_id`. Both tables are append-only except
   for `revoked_at`/`revoked_by` (plan 01-03's column-level grants), so this is an INSERT.
6. Audit with `action_type: 'approval'`, `after_state` naming **both** identities —
   `US-0.3`: "All role-grant creation and approval actions are captured as audit events, including
   both the requester and approver identities."
7. **After the transaction commits**, call `EntitlementResolverService.invalidate(subjectUserId)`
   and `SessionService.revokeAllForUser(subjectUserId)`. `FRD/F00` Process step 7 requires the
   session invalidation; the cache invalidation is its necessary partner — doing only one leaves a
   window in which the cached `Principal` is stale. Order matters: invalidate the cache first, so a
   request racing the revocation cannot repopulate the cache from pre-change data.

**`deny(principal, requestId, rationale)`** — same SoD check (a requester must not be able to
quietly withdraw-by-denying their own request to mask it), `status='denied'`, audited.

**`revoke(principal, grantId, rationale)`** — sets `revoked_at`/`revoked_by` (the only columns
`app_rw` may update on these tables), audited, followed by the same invalidate + revoke-sessions
pair. Never deletes the grant row: the historical fact that access was once held is part of the
record.

**`listPending(principal)`** — returns pending requests the caller is scoped to see. Shape the
response so Phase 3's Work Queue can consume it directly: include `object_reference:
{object_type: 'access_grant_request', object_id: id}` and `priority`, mirroring the `Task` shape in
`TechArch/03a-api-shared.md` §6.6. CONTEXT requires this plug in "without rework"; matching the
field names now is the cheapest way to make that true.

`grants.controller.ts` — routes per the provides contract, each with exactly one descriptor. Every
pair below exists in plan 01-02's `action_entitlement_map`; do not invent a pair outside that table,
because an unmapped pair denies silently:

| route | descriptor | why |
|---|---|---|
| `POST /entitlements/requests` | `{type:'access_grant_request', action:'create'}` | — |
| `GET /entitlements/requests` | `{type:'access_grant_request', action:'read'}` | — |
| `GET /entitlements/catalog` | `{type:'access_grant_request', action:'read'}` | knowing which entitlements exist is itself privileged reconnaissance |
| `POST /entitlements/requests/{id}/approve` | `{type:'access_grant_request', action:'approve', idParam:'id'}` | — |
| `POST /entitlements/requests/{id}/deny` | `{type:'access_grant_request', action:'approve', idParam:'id'}` | **deliberately `approve`, not a `deny` action** — plan 01-02's `sod_deny` rule keys on `action == "approve"`, and a requester quietly denying their own request must be refused exactly as self-approval is. A separate action value would escape the rule |
| `POST /entitlements/grants/{id}/revoke` | `{type:'entitlement_grant', action:'revoke', idParam:'id'}` | the target is a materialized grant, not the request that produced it, so it resolves through a different loader path. `requested_by` stays `null`, so the SoD rule deliberately does **not** fire — revocation is single-step by design |

The descriptors put the Rego `sod_deny` rule *before* the handler runs; the service check in task 1
then catches any path that bypassed the guard.

`entitlements.module.ts` imports `IdentityModule` (for `SessionService` and
`EntitlementResolverService`) and `AuditModule`.

  <name>Task 3: Implement the constrained, self-closing bootstrap mechanism</name>
  <files>apps/api/src/modules/entitlements/bootstrap.service.ts, apps/api/src/modules/entitlements/bootstrap.controller.ts, apps/api/test/bootstrap.e2e-spec.ts, docs/ASSUMPTIONS.md, .env.example</files>
  <action>
CONTEXT permits a bootstrap mechanism "**only** because an empty system cannot satisfy the
two-person approval rule," and then constrains it tightly. Implement every constraint literally:

**Environment-supplied identities, never derived from the first authenticated user.**
Read `BOOTSTRAP_ADMIN_SUBJECTS` and `BOOTSTRAP_APPROVER_SUBJECTS` — comma-separated
`external_idp_subject` values — at startup. If either is empty, bootstrap is simply unavailable; the
system does not fall back to "promote whoever logs in first." Write that as a comment: deriving the
admin from the first login is the single most common way a bootstrap becomes a privilege-escalation
vector, and CONTEXT forbids it by name.

**Non-self-approved.** The two lists must be disjoint. If they intersect, fail startup with a clear
error rather than silently proceeding — a bootstrap that self-approves is not a bootstrap, it is a
backdoor. The bootstrap grant path writes an `access_grant_requests` row with
`requested_by` = a subject from the admin list and `decided_by` = a subject from the approver list,
so the table CHECK and the Rego rule both still hold. **The bootstrap path does not bypass SoD; it
supplies the second person from configuration.**

**Clearly marked and fully audited.** Every bootstrap row sets `is_bootstrap = true` on both the
request and the resulting grant, and every bootstrap action writes an audit event whose
`after_state` includes `{"bootstrap": true}`. A later auditor must be able to list exactly what was
granted outside the normal flow: expose that as part of the pending/grant listing filters.

**Temporary, with an explicit completion step.**
`POST /api/v1/bootstrap/complete` (`@Resource({type:'access_grant_request', action:'approve'})`,
callable only by a principal holding `access_admin` that was **not** itself bootstrap-granted —
otherwise the bootstrap closes itself using the very authority it created) sets
`bootstrap_state.completed_at` and `completed_by`. After completion:
- `BootstrapService` refuses every operation with `403 BOOTSTRAP_CLOSED`;
- startup logs a warning if `BOOTSTRAP_ADMIN_SUBJECTS` is still set, instructing the operator to
  remove it (CONTEXT: "An explicit bootstrap-completion step must disable or rotate them before
  normal operation");
- `GET /api/v1/bootstrap/status` (`@SelfScoped()`) reports `{completed: bool, completed_at}` so the
  operator and the UI can see the system is no longer in bootstrap mode.

Bootstrap runs **at application startup**, idempotently: if `bootstrap_state.completed_at` is null
and the env lists are present, ensure each admin subject has a `user` row and an `access_admin`
entitlement grant created through the normal `access_grant_requests` → `entitlement_grants` path
with `is_bootstrap = true`. Re-running must not duplicate grants.

**Assumption registration.** Append to `docs/ASSUMPTIONS.md` under ASM-03, refreshing it with the
implemented shape: the env var names, the disjointness requirement, the completion endpoint, and the
sentence CONTEXT demands — *this is a development-constraint workaround requiring security and
stakeholder validation before production; it is not production bootstrap policy.* Status stays
`OPEN — requires stakeholder validation`.

`BOOTSTRAP_ADMIN_SUBJECTS` and `BOOTSTRAP_APPROVER_SUBJECTS` are already declared in `.env.example` by plan 01-01 — do not modify it. Expand their inline comments only if the implemented constraints differ from what is written there.

   grants for the admin subjects, each with `is_bootstrap = true` and `decided_by` drawn from the

2. Running the bootstrap twice creates no duplicate grants (idempotent).
3. With the two lists **intersecting**, application startup fails with a descriptive error.
4. With both lists empty, no bootstrap grant is created and **no user is promoted** — in particular,

5. `POST /bootstrap/complete` called by a bootstrap-granted principal → 403; called by a

6. After completion, re-running the startup bootstrap grants nothing and the service reports

7. After completion, **normal grants still require two distinct people** — repeat the self-approval
   case and assert `403 AUTH_SOD_VIOLATION`. CONTEXT: "The bootstrap path **must not bypass SoD for
   any subsequent grant**."
8. Every bootstrap action left an audit event with `after_state.bootstrap === true`.

| Boundary | Description |

| environment→application | `BOOTSTRAP_*` variables determining who receives initial administrative authority. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-31 | Elevation of privilege | A single administrator granting themselves authority by approving their own request | mitigate | Three independent layers: the Rego `sod_deny` rule evaluated by `AbacGuard` before the handler; the explicit check in `GrantsService.approve` throwing `403 AUTH_SOD_VIOLATION`; and the `CHECK (decided_by IS NULL OR decided_by <> requested_by)` constraint on `platform.access_grant_requests`. Cases 2, 4, and 5 of `apps/api/test/grants-sod.e2e-spec.ts` exercise each layer separately. |
| T-01-32 | Elevation of privilege | Two concurrent approvals of the same request both materializing grants | mitigate | `GrantsService.approve` loads the request `FOR UPDATE` inside the transaction and rejects a non-`pending` status with `409 GRANT_INVALID_TRANSITION`. |
| T-01-33 | Elevation of privilege | A revoked entitlement still honored from a cached `Principal` or an unexpired session | mitigate | `GrantsService.revoke` and `.approve` call `EntitlementResolverService.invalidate` then `SessionService.revokeAllForUser` after commit, in that order; case 6 and case 7 of the SoD suite assert the next request is rejected. |
| T-01-34 | Elevation of privilege | Bootstrap promoting whoever authenticates first, or closing itself with the authority it created | mitigate | `BootstrapService` reads identities only from `BOOTSTRAP_ADMIN_SUBJECTS`/`BOOTSTRAP_APPROVER_SUBJECTS`, fails startup when the lists intersect, and `POST /bootstrap/complete` rejects a principal whose `access_admin` grant is `is_bootstrap = true`. Case 4 asserts a brand-new user is not promoted; case 5 asserts the self-closing path is refused. |

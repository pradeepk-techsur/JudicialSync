<objective>
Build the configuration read path that every other Phase 1 feature already depends on, plus the
retention/disposition surface and the guard that makes automated deletion impossible.

Purpose: CONTEXT resolves the awkward dependency that `F13` needs `F3`, which is Phase 2: "Phase 1
creates the configuration tables with seeded per-court defaults … and a read path. **Features must
read configuration from the database from day one, never from hardcoded constants.** Phase 2 adds
rule-package versioning, the maker-checker approval flow, and the admin UI on top of these tables.
… Hardcoded constants were rejected: `F13` states designation policy must live in the configuration
engine and not in ad hoc code paths, and constants force revisiting every call site in Phase 2."

For retention, CONTEXT applies its "build the dangerous guard first, the convenience later"
principle: "Phase 1 ships `retention_schedules` + `disposition_log` schema, seeded defaults per
record category, and the hard no-auto-purge guard … The dangerous capability — anything
auto-deleting — must be impossible from day one. The scheduled sweep that generates
due-for-disposition tasks waits for the Work Queue in Phase 3."

Output: `CourtConfigService`, the config and retention endpoints, the disposition guard, the
key-access control, and the manual-fallback runbook.
</objective>

**`DispositionGuard` — the dangerous-capability guard.** `FRD/F13` Validation: "Retention schedule
disposition actions require human confirmation via a task (F06); **no automated hard-delete of any
record category is permitted** without this gate," and `FRD/Y2-errors.md` lists
`SECURITY_DISPOSITION_UNCONFIRMED` as a `403` **internal guard**.

Implement `assertHumanConfirmed(confirmation)` which throws
`ApiException(403, 'SECURITY_DISPOSITION_UNCONFIRMED', 'Disposition requires human confirmation')`
unless **all** of the following hold:
- `confirmation.confirmed_by` is present, resolves to an active user, and **equals the authenticated
  principal** — a confirmation naming someone else is not a confirmation;
- `confirmation.rationale` is at least 10 characters (the `FRD/Y2-errors.md` rationale convention);
- the calling principal is a human session, not the internal service token — assert
  `request.principal` exists and no `x-service-token` header is present. A batch identity must never
  be able to dispose of a record; this is the same reasoning `TechArch/04-security.md` §7.4 applies
  to calculation overrides ("No batch/cron identity has `INSERT` privilege with
  `triggering_reason = 'override'`").

`POST /retention/dispositions` is the **only** disposition path. It calls `assertHumanConfirmed`
first, then writes a `disposition_log` row (`object_type`, `object_id`, `disposition_action`,
`confirmed_by`, `confirmed_at`) together with its audit event in one `withAudit` transaction.

**What it does not do: delete anything.** In Phase 1 every seeded `disposition_action` is
`review_required` or `retain_permanent`, and the endpoint records the human decision. Add an
explicit comment and a runtime check: if a `disposition_action` resolving to a destructive operation
is ever introduced, this endpoint must refuse until a destructive-action implementation is reviewed
— throw `501 SECURITY_DISPOSITION_ACTION_UNSUPPORTED` for any action outside the known non-destructive
set. `disposition_log` is append-only at the grant level (plan 01-03), so the record of the decision
is itself immutable.

**`docs/MANUAL-FALLBACK.md`** — `FRD/F13` Sub-features list "Documented manual-fallback and recovery
procedures for courtroom or integration disruption," and `US-13.3` requires the runbook exist and
be exercisable. This is a documentation deliverable, not a software feature. Cover:
1. **Scope and triggers** — what counts as a disruption (API unavailable, IdP unavailable, CM/ECF
   adapter down in Phase 3, object store unavailable), and who declares one.
2. **Identity outage.** The system fails closed with `503 AUTH_IDP_UNAVAILABLE` by design; there is
   deliberately no offline credential. Procedure: escalate to the court's IdP operator; courtroom
   work continues on paper per step 4.
3. **Policy engine outage.** `503 SECURITY_POLICY_UNAVAILABLE`; the system denies rather than
   degrades. Restart/verification steps for the OPA service.
4. **Courtroom paper fallback.** The paper exhibit log sheet and the manual Speedy Trial worksheet,
   what fields must be captured so they can be re-entered without loss, and who holds them.
   Mark clearly: **the offline draft buffer and automatic resync described in `US-13.3` belong to
   F17, Phase 5** — Phase 1 documents the paper procedure and the re-entry path only.
5. **Re-entry procedure** — using the Phase 1 manual-entry API (`POST /cases`,
   `POST /cases/{id}/docket-events`) to reconcile after an outage, and why `source_system='manual'`
   plus `locally_modified` matter for later provenance.
6. **Recovery verification** — the checks to run before declaring the system usable again:
   `docker compose ps` health, `/api/v1/health`, an OIDC discovery fetch, an audit chain
   verification run (plan 01-12's job), and an upload round-trip.
7. **Exercise record** — a table for logging each tabletop exercise, since `FRD/F13` Process step 6
   requires the procedures be "exercised and validated during pilot scenario testing."

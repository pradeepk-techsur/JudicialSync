<objective>
Turn plan 01-02's Rego bundle into the live, mandatory enforcement point: replace the `AbacGuard`
stub with a guard that loads the target resource's real attributes, asks OPA for a decision, and
applies it — including the 403-vs-404 distinction and the `access_attempt` audit entry.

Purpose: Phase 1 success criterion 1 requires that "an unauthorized resource request is denied
server-side (403), not merely hidden in the UI," and criterion 4 requires that "the denied attempt
itself is logged as an audit event." CONTEXT locks the mechanism: "One global NestJS guard is the
authoritative enforcement point, intercepting every request, building the resource scope … and
calling the OPA container for an allow/deny decision. Per-route opt-in guards were rejected."

The guard's job is deliberately narrow — assemble input, call the PDP, apply the verdict. Every
*decision* lives in Rego. If a reviewer finds a comparison of entitlements, courts, or designations
inside this guard, the OPA investment has been undone.

Output: `PdpClient`, `ResourceLoaderService`, the `@Resource()` route descriptor, the real
`AbacGuard`, the internal `/security/policy-evaluate` endpoint, and two integration test files.
</objective>

`pdp.client.ts` — `POST ${OPA_URL}/v1/data/judicialsync/authz/decision` with
`{"input": <PdpInput>}`:
- Hard timeout of `PDP_TIMEOUT_MS` (default 2000, from `.env.example`) using `AbortController`.
- On timeout, connection error, non-200 status, or a response body missing a boolean `result.allow`:
  throw `ApiException(503, 'SECURITY_POLICY_UNAVAILABLE', 'Access cannot be evaluated at this time; request denied')`.
  The code and message are verbatim from `FRD/F13` Error States, and the behavior is
  `FRD/Y2-errors.md` principle 1 and CONTEXT's "Fail closed. If OPA is unreachable or evaluation
  errors, deny the request and return `503 SECURITY_POLICY_UNAVAILABLE`."
  **There is no cached-last-known-good fallback and no allow-on-error path.** Write that as a
  comment — a well-meaning future "availability improvement" here would silently convert the system
  to fail-open.
- Log every PDP error at `error` level with the route and resource type, but **never** log the
  principal's entitlement list or token.

`resource-descriptor.decorator.ts` — `@Resource({type, action, idParam?, caseIdParam?})`. Every
protected route in plans 01-08 through 01-12 carries exactly one. A route that is neither
`@Public()`, nor `@SelfScoped()`, nor `@Resource(...)` must be **denied** by the guard with
`503 SECURITY_POLICY_UNAVAILABLE` and an error-level log naming the route — the same deny-by-default
posture plan 01-01 established, now with a diagnostic. Never infer a resource type from the URL
path: inference would quietly assign the wrong policy to a mistyped route.

`resource-loader.service.ts` — this is the part `TechArch/04-security.md` §7.2 calls the
"fine-grained, resource-specific checks that require loading the actual object's attributes."
Given `(type, id, caseId)` it returns the resource's **real** attributes read from the database,
never attributes supplied by the client:

| type | how attributes are resolved |
|---|---|
| `case` | `cases` row → `court_id`, `division_id`, `case_id = id`; designations from `security_designations WHERE object_type='case' AND object_id=id` |
| `proceeding` | `proceedings` → owning `cases` row for court/division; designations from the owning case |
| `party`, `docket_event`, `document_reference` | owning `cases` row; `document_reference` additionally merges its own `security_designations` rows |
| `security_designation` | the target case's attributes |
| `audit_event` | the audited object's owning case, so sealed-case audit rows inherit the case's designations (`FRD/F02` Validation) |
| `file` | `file_references` row; `court_id` from the uploading user's court when the file is not yet case-bound |
| `retention_schedule` | `retention_schedules.court_id` |
| `access_grant_request` | the request row, exposing `requested_by` for the SoD rule |

For a `create` action where no object exists yet, resolve court/division/case from the **validated
request body** and mark the descriptor `id: null`. Validate those ids against the database before
passing them to the PDP: an unvalidated body-supplied `court_id` would let a caller nominate a court
they are scoped to while writing into another.

If the target row does not exist, return `null` and let the guard produce the resource's
`*_NOT_FOUND` 404 — never a 500, and never a different latency profile than a designation denial
(§7.6 requires that "response timing cannot be used to infer the existence of a sealed matter").

`policy.module.ts` exports `PdpClient` and `ResourceLoaderService` so `AbacGuard` can inject them;
mark the module `@Global()` because the guard is global.

`OPA_URL` and `PDP_TIMEOUT_MS` are already declared in `.env.example` by plan 01-01 — do not modify it.

Replace plan 01-01's stub body. Flow, in order:

1. `@Public()` → allow immediately (no session, no resource).
2. `@SelfScoped()` → allow (the `SessionAuthGuard` already proved a valid session; there is no
   target resource to evaluate). Do not call the PDP.
3. No `@Resource()` metadata → **deny** `503 SECURITY_POLICY_UNAVAILABLE`, log at error level with
   the controller and handler name. This is the "forgot the decorator" case, and it must fail loudly
   rather than open.
4. Read `request.principal` (attached by `SessionAuthGuard`). Absent → `401 AUTH_SESSION_EXPIRED`.
5. `ResourceLoaderService.load(...)`. A `null` result → treat as absent: deny with the resource's
   404 code (see mapping below) **and** still write the `access_attempt` audit event.
6. Read the court's effective `security_policies` rows (via the config read path; until plan 01-11
   lands, query `security_policies` joined to the court's effective `rule_package_versions` row
   directly) and include them as `input.security_policies` — plan 01-02's Rego prefers them over its
   built-in defaults, which is what keeps designation policy configuration-driven per `FRD/F13`.
7. `PdpClient.evaluate(input)`.
8. Apply the decision:
   - `allow: true` → proceed.
   - `hide_existence: true` → throw `404` with the resource's not-found code and the message
     "{Resource} not found or not accessible" (`FRD/Y2-errors.md`).
   - otherwise → throw `403` with `decision.reason_code` and the matching message from the FRD
     Error States tables.

Reason-code → HTTP mapping (all drawn from `FRD/F00`, `FRD/F01`, `FRD/F02`, `FRD/Y2-errors.md`):

| `reason_code` | HTTP | message |
|---|---|---|
| `AUTH_SCOPE_DENIED` | 403 | "You do not have access to this record" |
| `AUTH_DESIGNATION_DENIED` | 403 | "This record requires additional authorization" |
| `AUTH_MFA_FAILED` | 401 | "Multifactor verification failed" |
| `AUTH_SOD_VIOLATION` | 403 | "Separation-of-duties violation: cannot approve your own request" |
| `RESOURCE_NOT_FOUND` / `hide_existence` | 404 | "{Resource} not found or not accessible" |

Per-resource 404 codes: `case → CASE_NOT_FOUND`, `audit_event → AUDIT_NOT_FOUND`,
`file → SECURITY_FILE_NOT_FOUND`, and so on — derive `{TYPE}_NOT_FOUND` from the resource type,
uppercased.

**`access_attempt` auditing.** `TechArch/04-security.md` §7.6: "Every such denied/hidden attempt is
itself logged as an `access_attempt` audit event," and `FRD/F02` Validation says the same for sealed
audit entries. On every denial (403 **and** 404), write through `AuditService` inside its own
transaction:

```typescript
await withAudit(prisma, audit, async () => ({
  result: undefined,
  audit: {
    actor_id: principal.user_id,
    action_type: 'access_attempt',
    object_type: descriptor.type,
    object_id: resource?.id ?? NIL_UUID,   // audit_events.object_id is NOT NULL
    after_state: { outcome: 'denied', reason_code: decision.reason_code,
                   hide_existence: decision.hide_existence, route, method },
    client_ip: request.ip,
    session_id: principal.session_id,
    rule_version_ref: effectiveRulePackageVersionId,
  },
}));
```

Two details that are easy to get wrong and both matter:
- The audit write must **not** be inside the request's own transaction (there isn't one — the
  handler never ran), and its failure must not convert a 403 into a 500 that leaks a different
  signal to the caller. Catch and log an audit-write failure, then still throw the original
  denial. Raise an `integrity_alert`-style error log so the gap is visible.
- `rule_version_ref` links the entry to the rule package in effect, which is `FRD/F02`'s
  "Linkage of every audit entry to the specific configuration/rule-package version … in effect at
  action time."

**What must not appear in this file:** any comparison of `principal.entitlements` against a required
entitlement, any `court_id` equality check, any `designation` lookup, any `requested_by ===
user_id` test. Those are all Rego's. Add the `<verify>` grep that asserts their absence.

`FRD/Y1a-api-shared.md` §Security Baseline and `TechArch/03a-api-shared.md` §6.9 both specify
`POST /security/policy-evaluate` → `{allow|deny}`, marked **Internal** — "the ABAC PDP call itself
(§7.2)". Implement it with the exact shapes from §6.9:

```typescript
interface PolicyEvaluationRequest {
  object_type: string;
  object_id: string;
  requester_scope: ScopeAttribute[];
}
interface PolicyEvaluationResponse {
  decision: "allow" | "deny";
  reason_code?: string;
}
```

Guard it with the same `ServiceTokenGuard` plan 01-05 created for `/audit/events` — it is an
internal service-to-service call, and exposing a decision oracle to end users would let a caller
enumerate which case ids exist by probing reason codes. Reuse the guard rather than writing a second
one.

Resolve the *subject* principal from `x-service-actor-id` and load the real resource attributes
through `ResourceLoaderService`; **ignore any `requester_scope` the caller supplies for the actual
decision** and instead resolve it from the database via `EntitlementResolverService`. Accepting
caller-supplied scope would make the endpoint an authorization bypass. Echo the supplied
`requester_scope` back in a `detail` field if it differs from the resolved scope, so a mismatch is
diagnosable rather than silent.

The response collapses `hide_existence` into `deny` with `reason_code: "RESOURCE_NOT_FOUND"` —
callers of this endpoint are services, which need the reason, not an HTTP status.

`apps/api/test/abac-fail-closed.e2e-spec.ts` — the proof that the system is fail-closed, which is

- With the OPA container **stopped** (`docker compose stop opa`), an authenticated request to a
  protected route that previously returned 200 now returns **503 `SECURITY_POLICY_UNAVAILABLE`** —
  not 200, not 500. Restart OPA and confirm the same request returns 200 again, so the test proves
  the failure was the PDP and not an unrelated breakage.
- With OPA reachable but returning a malformed body (point `OPA_URL` at a local stub server that

- With OPA reachable but slower than `PDP_TIMEOUT_MS` (stub that sleeps) → 503, and the request does
  not hang beyond the timeout plus a small margin.
- `POST /security/policy-evaluate` without `x-service-token` → 403.
- `POST /security/policy-evaluate` with a valid service token returns `{"decision":"deny","reason_code":"AUTH_SCOPE_DENIED"}`
  for `jury_admin` against a seeded case, and `{"decision":"allow"}` for `clerk_case_admin` against
  an NDCA case.
- A caller-supplied `requester_scope` claiming court access the subject does not hold does **not**
  change the decision to allow.

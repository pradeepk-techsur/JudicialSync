<objective>
Build the real CM/ECF adapter: one polling ingestion path, idempotency by recorded payload hash, per-record
mapping into Phase 1's shared case model with lineage preserved, health monitoring with a sustained-failure
alert, and an outbound endpoint that is a provable refusal.

Purpose: F10 calls this adapter "the enforcement point for the system's authoritative-source discipline"
and says it is "architecturally impossible for JudicialSync to silently overwrite docket data because this
adapter is the only inbound path". CONTEXT makes that literal: **polling is the only path authoritative
data enters**, and `POST /integrations/cmecf/sync` exists but is a zero-data wake-up signal whose body is
never trusted as records. One ingestion code path means idempotency, conflict detection,
`locally_modified_fields` checking and source-lineage stamping cannot diverge between two implementations
— and an inbound endpoint accepting authoritative docket records would be the highest-value injection
target in a system whose first principle is that the docket is authoritative and never silently
overwritten.

Outbound is the inverse decision: **build the refusal, not the capability.** Writing to a federal court's
authoritative docket is the most dangerous thing this system could do, it has no v1 consumer, and no
court-validated contract exists. Plan 03-02 made the policy deny unconditional; this plan makes the
endpoint exist so Screen-18 can say "Outbound filings: disabled" truthfully and the assurance suite can
prove it.

Output: the `CmecfSyncProvider` interface and its HTTP implementation, the record mapper, the ingest
service, the BullMQ poller over durable Postgres cursor state, the health service, the four endpoints, and
three test files driven by plan 03-04's scenario control.
</objective>

`cmecf-sync-provider.interface.ts` declares the abstract provider `TechArch/06-integrations.md` §9.1 names
by contract. Head it with that citation and the note that a court's real transport and schema land behind
this interface as a provider plus mapper swap, not a rewrite. Export a `CMECF_SYNC_PROVIDER` injection
symbol so the implementation is swapped by DI configuration.

`http-cmecf.provider.ts` implements it against `docs/CMECF-FIXTURE-CONTRACT.md` with **real HTTP**:
- `fetch(`${CMECF_BASE_URL}/cmecf/v1/records?court_code=..&since=..&limit=..`)` with
  `Authorization: Bearer ${CMECF_API_TOKEN}` and a fresh UUID `X-Idempotency-Key` per request.
- Validate the response body with `zod` before it becomes a `CmecfPage` — an untrusted external payload
  never enters a typed sink unvalidated. A shape failure is a page-level failure (the feed is broken), not
  a record-level rejection.
- Map HTTP failures: non-2xx or a network error → throw a typed `CmecfFeedUnavailableError` carrying the
  status. The poller turns that into `503 CMECF_UNAVAILABLE` on the status endpoint and into the
  failure counters.
- A bounded timeout and no retry here — retry and backoff belong to the poller over durable state, the
  shape Phase 2 proved, not to the HTTP client.

`record-mapper.ts` maps a validated `CmecfRecord` onto Phase 1's model, per the fixture contract's
per-type tables:
- **Namespacing.** `source_identifier` is stored as `${court_code}:${record.source_identifier}` because
  `docket_events` carries `UNIQUE (source_system, source_identifier)` **globally** while CM/ECF ids are
  unique only within a court. Without this two courts' dockets collide and merge. Record it as the
  adapter's convention (plan 03-14 registers it) and apply it uniformly to all five types.
- `source_system` is always `'CM/ECF'`.
- `order` → a `document_references` row (`document_title`, `source_identifier`) plus its `docket_events`
  row, per the mapping the fixture contract marks `[ASSUMPTION]`.
- A record whose `source_identifier` is absent or blank → reject with `CMECF_MISSING_SOURCE_ID`, F10's
  422. **Never persisted**, per F10 validation.
- A record whose payload fails its per-type zod schema (e.g. an unparseable `event_date`) → reject with
  `CMECF_MALFORMED_RECORD`. Rejection is **per record**: the rest of the page still ingests.
- `superseded: true` → the record is **not deleted**. Phase 1's no-hard-delete invariant is absolute.
  Mark the internal record's status as superseded where the model has one, otherwise record only the
  delivery-log row with disposition `superseded` and raise a `missing_metadata` exception for human
  review. Comment the decision and its reason.

`ingest.service.ts` — `ingestRecord(courtId, courtCode, pollCycleId, record)`, all inside **one
transaction** so a crash cannot leave a record applied with no delivery-log row:
1. Compute `payload_hash = sha256(canonical_json(record.payload))`. Reuse plan 01-05's
   `canonical-payload.ts` canonicaliser rather than writing a second JSON canonicaliser — two
   canonicalisers that disagree would make the hash comparison unreliable in exactly the duplicate case
   it exists to catch.
2. **Idempotency.** Look up the most recent `cmecf_delivery_log` row for
   `(source_system, namespaced source_identifier)`. If its `payload_hash` matches, write one new log row
   with `disposition: 'no_op_duplicate'` and return `{disposition:'no_op_duplicate'}`. No record write,
   no conflict evaluation, **no exception**. This is what makes F10's "no duplicate internal records or
   duplicate conflict exceptions" provable rather than asserted.
3. Map the record. A rejection writes a log row with `disposition:'rejected'` and the error code in
   `detail`, and returns the rejection. It also raises a `missing_metadata` exception (severity `medium`,
   `dedupe_key` on the source identifier) so a persistently malformed feed is visible rather than a
   silent counter.
4. **New `source_identifier`** → create the internal record with lineage (`source_system`,
   `source_identifier`, `locally_modified_fields = '{}'`), write the audit event through `withAudit`,
   log `disposition:'created'`.
5. **Known `source_identifier`** → call plan 03-07's
   `ConflictDetectorService.reconcileFields(tx, ...)`. Apply **only** the `auto_apply` decisions, write
   one audit event for the applied set, and log `disposition:'updated'` with `applied_fields` in
   `detail`. If any decision is `conflict_raised`, log `disposition:'conflict_raised'` with the conflict
   and exception ids. If every decision is `no_change` or `no_op_already_rejected`, refresh
   `last_synced_at` and log `disposition:'updated'` with an empty `applied_fields` — F10 step 3's
   "no action is taken (or a `last_synced_at` timestamp is refreshed)".

`poller.service.ts` — a BullMQ repeatable job over **durable Postgres state**, the same shape Phase 1's
hash-chain verifier and Phase 2's escalation sweeper took, and chosen for the same reason: the decision is
derivable from durable rows at any instant, so a Redis flush, a worker crash or a multi-hour outage loses
nothing. Read plan 02-11's `escalation-sweeper.service.ts` and follow its structure.

`pollCourt(courtId)`:
- Reads `cmecf_policy` through `ConfigResolver`: `poll_interval_seconds`, `max_records_per_poll`,
  `sustained_failure_consecutive_cycles`, `sustained_failure_minutes_without_success`.
- Reads `last_cursor` from the latest `adapter_health_log` row for the court. **Backlog catch-up
  (discretion resolved):** the cycle fetches pages from the cursor until either `has_more` is false or
  `max_records_per_poll` records have been ingested, whichever comes first, then persists the cursor it
  reached and records the remaining count as `backlog_count`. A long outage therefore drains over
  successive cycles at a bounded rate instead of one unbounded catch-up request.
- Generates one `poll_cycle_id` per cycle and passes it to every `ingestRecord` call, so the delivery log
  can reconstruct a cycle.
- Each record ingests in its **own** transaction. One malformed record must not roll back the page.
- Writes one `adapter_health_log` row per cycle with `last_successful_sync_at`, `error_count`,
  `backlog_count`, `consecutive_failure_count`, `last_cursor`, and the last error code and message.
- On a feed failure: increments `consecutive_failure_count`, leaves `last_cursor` untouched so nothing is
  skipped, and records the error.
- Uses plan 02-11's `ClockService` for every time comparison so tests can inject a clock.
- Guarded by `CMECF_POLL_ENABLED` so a test can run the cycle manually without the scheduler racing it.

`health.service.ts`:
- `status(courtId)` → `{last_sync, error_rate, backlog, consecutive_failure_count, outbound_enabled:
  false, duplicate_deliveries}` where `error_rate` is errors over deliveries across the configured
  window, and `duplicate_deliveries` is the recent `cmecf_delivery_log` rows with
  `disposition:'no_op_duplicate'` — Screen-18's "Duplicate Delivery Log (informational, no action
  needed)" panel, with real data rather than a log line.
- **Sustained failure (discretion resolved):** `consecutive_failure_count >=
  sustained_failure_consecutive_cycles` **OR** `now - last_successful_sync_at >
  sustained_failure_minutes_without_success`. On crossing it:
  - raise a `critical` exception `cmecf_sustained_failure` (plan 03-09's catalog routes it to
    `cmecf_admin`), with a `dedupe_key` on the court so a week-long outage is one exception with a
    climbing occurrence count rather than one per cycle;
  - send a critical notification **through Phase 2's `NotificationsService`**, never a parallel alerting
    path — this is the consumer relationship CONTEXT requires;
  - both are idempotent: crossing the threshold again while the exception is still open merges.
  - A successful cycle resets `consecutive_failure_count` to zero. It does **not** auto-resolve the
    exception — a critical exception requires individual human review (plan 03-01's trigger would reject
    an automated close anyway, which is the guard working).

`cmecf.module.ts` (extending plan 03-07's fill): registers `CMECF_SYNC_PROVIDER` → `HttpCmecfProvider`,
provides `IngestService`, `CmecfPollerService`, `CmecfHealthService`, the BullMQ queue and processor, and
the controller; imports `NotificationsModule`, `ExceptionsModule`, `AuditModule`, `ConfigModule`,
`CaseContextModule`.

2. The cursor advances across cycles and no record is ingested twice when the feed paginates.
3. `setScenario('outage')`, run three cycles with the configured threshold at 3 → exactly one `critical`

4. A fourth failed cycle → still one exception, with `occurrence_count` incremented; still one

5. `setScenario('healthy')`, one successful cycle → `consecutive_failure_count` is 0, the exception is

6. Backlog: append more records than `max_records_per_poll`, run one cycle → exactly
   `max_records_per_poll` ingested and `backlog_count` reports the remainder; a second cycle drains the
   rest.

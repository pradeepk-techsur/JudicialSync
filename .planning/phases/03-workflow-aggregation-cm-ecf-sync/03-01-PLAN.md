<objective>
Create every database object Phase 3 needs — in one plan — so the fourteen plans that follow each work
inside their own module directory and never contend for `schema.prisma`, `app.module.ts` or `.env.example`.

Purpose: three of Phase 3's five guarantees are *"never"* claims, and CONTEXT locks all three to the
database rather than to application convention, following `TechArch/04-security.md` §7.3's stance that
PostgreSQL "will reject the statement regardless of which code path generated it". Those three are: a
critical exception can never be auto-closed; a task can never be closed without its evidence; and the
reporting tier can never reach a base table. Phases 5–8 will add producers and batch jobs this phase
cannot see, so an application guard is not sufficient — it binds only code that goes through the service.
This plan also takes the field-level provenance migration now, while the system is pre-pilot, for exactly
the reason Phase 1 took `source_system`/`source_identifier`/`locally_modified` early: deferring it would
force a later migration and backfill across live court records.

Output: three migrations, the Prisma models, the reporting database role and its aggregate-only
functions, four NestJS module placeholders on the composition root, the complete Phase 3 environment
surface, and a test proving the four structural guarantees hold at the database level.
</objective>

**Prohibition 1 — critical exceptions cannot be auto-closed (`FRD/F07` Validation, ROADMAP criterion 2).**
A `BEFORE UPDATE` trigger. It enforces the HARD FLOOR only (>=10 characters AND >=2 words); a court may
configure a tighter bar, which plan 03-09 enforces in the application. The floor is what configuration can
never weaken:

```sql
CREATE OR REPLACE FUNCTION platform.exceptions_resolution_requires_human()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.status = 'resolved' AND OLD.status IS DISTINCT FROM 'resolved' THEN
    IF NEW.reviewer_user_id IS NULL THEN
      RAISE EXCEPTION 'EXCEPTION_CRITICAL_MANUAL_ONLY: exception % cannot be resolved without an individual reviewer', NEW.id
        USING ERRCODE = 'check_violation';
    END IF;
    IF NEW.resolution_action IS NULL OR btrim(NEW.resolution_action) = '' THEN
      RAISE EXCEPTION 'EXCEPTION_ACTION_TYPE_MISMATCH: exception % cannot be resolved without a resolution action', NEW.id
        USING ERRCODE = 'check_violation';
    END IF;
    IF NEW.rationale IS NULL
       OR length(btrim(NEW.rationale)) < 10
       OR coalesce(array_length(regexp_split_to_array(btrim(NEW.rationale), '\s+'), 1), 0) < 2 THEN
      RAISE EXCEPTION 'EXCEPTION_RATIONALE_TOO_SHORT: exception % rationale is below the hard floor of 10 characters and 2 words', NEW.id
        USING ERRCODE = 'check_violation';
    END IF;
    IF NEW.resolved_at IS NULL THEN NEW.resolved_at := now(); END IF;
  END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER trg_exceptions_resolution_requires_human
  BEFORE UPDATE ON platform.exceptions
  FOR EACH ROW EXECUTE FUNCTION platform.exceptions_resolution_requires_human();
```

Add a SQL comment above it stating why it is `FOR EACH ROW`: a bulk `UPDATE ... WHERE severity='critical'`
issued by a future batch job fires the trigger once per row and is rejected on the first one.

**`resolved` is terminal.** Also reject any transition OUT of `resolved` in the same trigger
(`IF OLD.status = 'resolved' AND NEW.status <> 'resolved' THEN RAISE ... 'EXCEPTION_INVALID_TRANSITION'`).
A recurrence raises a NEW exception; `dedupe_key` merges only while a row is still open. This is the
"a resolution that re-litigates itself is not a resolution" decision applied to reopening.

<objective>
Build the de-identified operational reporting feed on top of a database role that cannot reach case data,
and make the human-in-command label travel with every artifact it produces.

Purpose: ROADMAP criterion 4 requires a dashboard that "contains no path back to an individual judicial
determination". CONTEXT makes that a property rather than a promise in three independent ways. The
**enforcement is at the grant level** — Phase 2's structural content policy combined with Phase 1's
grant-level audit immutability — so a leaking join fails with a Postgres permission error rather than
being caught in review, and the runtime assertion is an unreachable tripwire. **There is nothing to drill
through** — the payload carries no object identifiers at all, so drill-through is not blocked by a guard,
it is structurally absent. And **small cells are suppressed with ages bucketed**, because `reporting_viewer`
does not imply case access, so a within-court viewer may hold no case entitlements at all — which is
exactly the person a count of 1 leaks to.

The label gets the same treatment. F09 step 5 says "UI label", but an exported CSV forwarded into a
chambers email has left the UI and lost it, and the export is the artifact most likely to travel. The
scenario the label exists to prevent is far likelier downstream of an export than in front of the
dashboard, and PROJECT.md calls human-in-command non-negotiable — so the label is embedded in the bytes,
and the assurance suite asserts it there.

Output: the restricted database handle, metric dispatch, dashboard and export endpoints, and two test
files — one asserting a permission error, one asserting bytes.
</objective>

`reporting-db.service.ts` creates a `pg` `Pool` against `DATABASE_URL_REPORTING` — the `app_reporting`
login role plan 03-01 created, which inherits `reporting_ro`. Head the file with the reason, from
`TechArch/04-security.md` §7.3's own logic applied to reads: PostgreSQL will reject the statement
regardless of which code path generated it.

Three constraints on this file, each enforceable by grep and asserted in `<verify>`:
- It is the **only** database handle the reporting module uses. No file under
  `apps/api/src/modules/reporting/` may import `PrismaService`.
- `query(sql, params)` is **parameterised only** — no string interpolation of any caller value into SQL.
  Scope ids arrive as `$1`, `$2`.
- Every statement it issues targets `reporting.<function>(...)`. A grep asserts the string `platform.`
  does not appear in `metrics.service.ts`.

Pool sizing is small (max 4) with a short `statement_timeout`; reporting is a low-frequency admin read and
must never be able to starve the operational pool. Implement `OnModuleDestroy` to end the pool.

`metrics.service.ts`:
- `ADMIN_METRICS_LABEL` is the F09 step 5 string **verbatim**, including the em dash:
  `"Administrative metrics — not for use in case determinations"`. Everything that renders or exports the
  label imports this constant; no second copy of the string exists in the codebase.
- `dashboard(principal, q)`:
  1. **Scope authorization.** The route already required `reporting_viewer` through the global guard.
     Additionally confirm the requested `scope`/`scope_id` lies within the principal's authorized
     aggregation level; above it → `403 REPORT_SCOPE_DENIED` with F09's message verbatim. Cross-court
     (AO-level) aggregation is **not implemented in v1** and a request for it returns the same 403 —
     F09's cross-court tier has no v1 consumer and CONTEXT's deferred list keeps the second identified
     tier out.
  2. **Metric-set validation.** Any requested set outside `V1_METRIC_SETS` → `422
     REPORT_INVALID_METRIC_SET` with F09's message and a `detail` naming the supported sets. In
     particular `alert_effectiveness` returns 422 with the explanation that it arrives in Phase 8 — never
     an empty section, which a reader would misread as "no alerts failed". Record this as the
     **discretion resolved**: v1 ships four of F09's five sets because `reconciliation_runs` does not
     exist until Phase 6 and alert effectiveness is Phase 8.
  3. **Resolve k.** `min_cell_count` through `ConfigResolver` from the operational package
     (`reporting_policy.min_cell_count`, floored by plan 03-03's schema at 5). Pass it to each function
     as `p_min_cell`. Plan 03-01's functions clamp it again with `GREATEST(p_min_cell, 5)`, so a bug in
     this service cannot weaken suppression.
  4. **Dispatch** one `SELECT * FROM reporting.<fn>($1,$2,$3,$4)` per requested set, on the reporting
     pool, and assemble the payload.
  5. **The unreachable tripwire.** Before returning, assert the serialised payload matches no UUID and
     contains no key named `*_id`, `case_number` or `caption`. A hit throws
     `500 REPORT_DEIDENTIFICATION_VIOLATION` and raises a `critical` exception through
     `ExceptionsService.raise`. Comment it as CONTEXT describes: *the runtime assertion stays as an
     unreachable tripwire* — the grants are the control, this is the alarm that the control failed.
  6. Return `{label: ADMIN_METRICS_LABEL, scope, generated_at, min_cell_count, metrics}`.

**Refresh cadence (discretion resolved):** computed on demand, with no precomputation and no cache. The
functions aggregate court-scoped rows over indexed columns and this is an administrative screen, not a
hot path; a precomputed snapshot would be a second representation that can drift, which Phase 2 rejected
twice. Record the decision and the revisit condition (measured slowness) in the SUMMARY.

`reporting.module.ts` fills plan 03-01's placeholder: provides `ReportingDbService`, `MetricsService`,

`export.service.ts` — **the label travels with the artifact**, in three places, because an export leaves
the UI:

**CSV** (`format=csv`, the default). Emit, in order:
```
# Administrative metrics — not for use in case determinations
# Scope: {court_code}{ / division_name}
# Generated: {RFC3339}
# Minimum cell count applied: {k}. Cells below it are reported as SUPPRESSED.
# Ages are reported as buckets (0-2d, 3-7d, 8-30d, 30d+), never as exact values.
metric_set,dimension,bucket_or_key,value,suppressed
...
```
The first line is the label, unprefixed by anything that would break a grep for the exact string. A
suppressed cell renders the literal `SUPPRESSED` in the `value` column, never a blank and never a zero —
a blank reads as "no data" and a zero is a false statement.

**JSON** (`format=json`). A top-level
`"disclaimer": "Administrative metrics — not for use in case determinations"` as the **first** key, plus
`"artifact_class": "administrative-metrics"`, `"min_cell_count"`, `"generated_at"`, `"scope"` and
`"metrics"` in the same shape as the dashboard payload.

**Filename and headers.** `Content-Disposition: attachment; filename="administrative-metrics_{court_code}_{YYYYMMDD}.{csv|json}"`,
`Content-Type` set correctly, and a response header
`X-JudicialSync-Artifact-Class: administrative-metrics`. The filename convention marks the artifact
administrative even when the file is detached from its headers.

**Export limits (discretion resolved):** aggregate output is inherently small; cap at 10,000 rows and
return `422 REPORT_INVALID_METRIC_SET` with a `detail` asking for a narrower date range if a request
would exceed it. No pagination — a paginated export whose label lives only on page one is the exact
failure this plan exists to avoid.

The export streams through this API route, generated in-process from the reporting pool. It is never
written to the object store and no URL to any store appears in any response.

`dto/reporting.dto.ts` — zod request DTOs with `additionalProperties:false`, and response DTOs with
OpenAPI decorators so plan 03-14 emits them. `label` is a **required** property of the dashboard response,
so a client cannot render the payload without it being present.

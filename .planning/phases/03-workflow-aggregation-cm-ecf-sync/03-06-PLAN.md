<objective>
Build the Case Timeline as a provider registry queried at request time, with two deliberately opposite
absence semantics in the same response.

Purpose: ROADMAP criterion 3 requires docket events and hearings merged into one filterable chronological
view with deep links. CONTEXT locks the composition to a **registry, not a denormalized store** — a
timeline is a low-frequency single-case read, and a briefly-stale timeline misrepresents a case history to
a judge, which is a worse failure than a slightly slow page. It also takes Phase 2's inversion-of-control
pattern so Phase 5 registers exhibits and Phase 7 registers clock segments as pure additions.

The subtlest requirement in the phase lives here. **Designation-excluded entries are SILENT** — per F08
validation and `TechArch/04-security.md` §7.6 they are "fully excluded, not redacted": no placeholder, no
count, no hint. **Provider-unavailable is LOUD** — a `206` with a per-provider status block naming exactly
which sources answered, rendered later as a prominent Alert. An authorized user must never mistake a
partial timeline for a complete one; an unauthorized user must never learn that something was withheld.
This is the same fork Phase 2 resolved with `unsupported_filters[]` alongside a byte-identical empty
state, and the assurance suite asserts both directions.

Output: the provider contract, the registry, the docket-event and hearing providers, the merge service
with deterministic same-day ordering, the endpoint, and a test file that exercises both absence semantics
in one response.
</objective>

Two contract rules carry the whole security property, and must appear as comments on the interface, not
only in this plan:
1. **A provider applies designation exclusion itself and returns the surviving entries.** It never returns

2. **A provider throwing means UNAVAILABLE, never UNAUTHORIZED.** Authorization denial is expressed as

   detectable through a provider status block.

`TimelineService.getTimeline(principal, caseId, filters)`:

1. **Case-level authorization first.** The route carries `@Resource({type:'timeline', action:'read',
   caseIdParam:'id'})`, which plan 03-02 mapped to `case_read`, so the global guard already denied an
   unauthorized caller. Additionally resolve the case to confirm it exists within scope; a miss returns
   `404 TIMELINE_CASE_NOT_FOUND` with F08's message verbatim — never a 403, because a direct-by-id lookup
   of a case the requester has no other path to is a blind-discovery path under `Y2` principle 3.
2. **Validate filters.** `date_from > date_to` → `400 TIMELINE_INVALID_RANGE`. An `event_type[]` value not
   in `registry.declaredEntryTypes()` is **dropped silently from the filter**, not rejected — a Phase 5
   entry type requested before Phase 5 ships must not 400 a judge's timeline. Record the dropped values
   nowhere in the response: unlike search, an unknown entry type carries no capability information a user
   needs, and an extra notice here would compete with the partial-data Alert for attention.
3. **Fan out with `Promise.allSettled` over `registry.all()`**, filtered by the `module[]` filter. Each
   provider gets its own `TimelineProviderContext`. Apply a per-provider timeout (default 5s, from the
   same `ConfigResolver`-read operational package as the rest of Phase 3) so one slow module cannot hold
   the request.
4. **Build the status block.**
   - fulfilled → `{source_module, status: "ok", entry_count: entries.length}` where `entries` is the
     **post-exclusion** array the provider returned. **The count is computed after exclusion by
     construction**, because the provider never returns excluded rows. Put that sentence in a comment —
     it is the single line that keeps the status block from becoming a side channel.
   - rejected or timed out → `{source_module, status: "unavailable", entry_count: 0, reason: "PROVIDER_UNAVAILABLE"}`.
     Log the underlying error server-side; never place an exception message in `reason`.
5. **Merge deterministically.** Sort by `timestamp ASC`, then `sequence_at ASC`, then `entry_id ASC`. The
   third key exists so two entries created in the same transaction still order identically on every
   request — F08 requires same-day entries be "secondarily ordered by entry creation sequence", and a
   non-deterministic tail would make a judge's timeline change between refreshes.
6. **Candidate toggle.** When `include_candidates` is false (the default), drop entries with
   `state: "candidate"`. Phase 3's two providers emit only `"confirmed"`, so the filter is a no-op today —
   build it anyway, because F08 validation requires the view reflect confirmed state by default and
   Phase 7's provider must inherit the behaviour rather than reimplement it.
7. Return `{ timeline_entries, providers, partial }` where `partial` is true iff any status is
   `"unavailable"`.

`timeline.controller.ts` sets HTTP **206** with `error_code: "TIMELINE_PARTIAL_DATA"` and F08's message
verbatim when `partial`, and **200** otherwise. Add a comment recording why neither alternative was taken,
from CONTEXT: a `503` on any provider failure kills the whole view during a live proceeding because one
module is flaky; a `200` with a footnote tells every client the response is complete.

`dto/timeline.dto.ts` declares the request query DTO (`event_type[]`, `date_from`, `date_to`, `module[]`,
`include_candidates`) with `zod`, and the response DTOs, with OpenAPI decorators so plan 03-14 emits both
the 200 and the 206 response shapes. `providers` and `partial` are **required** properties of both — a
client must never have to infer completeness from their absence.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | A case-scoped read whose response shape must not reveal the existence of entries the viewer may not see |
| provider→service | Independently-failing module providers whose failures must be reported without leaking their internals |
| db→render | Stored designation tags deciding which entries reach the response |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-30 | Information disclosure | A viewer inferring that a sealed docket entry exists from a count, a gap, or a placeholder | mitigate | Providers return only surviving entries, so `TimelineProviderStatus.entry_count` in `timeline.service.ts` is post-exclusion by construction; `timeline-absence-semantics.e2e-spec.ts` asserts the serialised unentitled body contains none of `sealed`/`restricted`/`excluded`/`redacted`/`withheld` nor the excluded entry id |
| T-03-31 | Information disclosure | An authorization denial surfacing as a provider status, turning exclusion into a detectable event | mitigate | The `TimelineProvider` interface comment forbids throwing for authorization; a throw means unavailability only.

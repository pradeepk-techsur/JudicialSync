<objective>
Build one periodic sweeper that ages and escalates both queues through the shared Notifications Service,
and a second that detects the one inconsistency service-only completion makes possible.

Purpose: F06 step 6 says tasks beyond a configured age are flagged "and optionally via F04 escalation
notification", and F07 step 6 says unresolved exceptions beyond a threshold escalate to a supervisory
role. CONTEXT removes the "optionally": a signal that reaches no one is close to a signal that does not
exist, a shape Phase 1 rejected twice. It also locks the mechanism — **one periodic BullMQ sweeper over
durable Postgres state**, the same shape Phase 2 proved for notification escalation and chose explicitly
because *an alert is never silently dropped*. A per-item delayed job would hold the pending escalation in
Redis, where losing it is precisely the silently-dropped outcome.

The second sweeper exists because of a consequence CONTEXT named when it removed the user-facing
completion endpoint: **an open task whose underlying object is already resolved is now a detectable
inconsistency**, and a reconciliation sweeper should surface it rather than let it sit. That is a
producer that forgot to call `completeForAudit`, which is a defect — so it raises an exception rather
than quietly closing the task.

Output: the aging sweeper over both queues, the reconciliation sweeper, their BullMQ processor, and two
test files driven by backdating and an injected clock.
</objective>

`AgingSweeperService.sweep(courtId?)` runs per court (or all courts when the argument is omitted):

1. Resolve `queue_policy` through `ConfigResolver`: `task_aging_threshold_hours`,
   `exception_aging_threshold_hours_by_severity` and `escalation_recipient_role`. Never a constant.
2. **Flag pass, tasks.** `UPDATE platform.tasks SET aging_flagged_at = now() WHERE status IN
   ('open','in_progress') AND aging_flagged_at IS NULL AND created_at < now() - interval
   '<threshold> hours'` — scoped by `court_id`. The `aging_flagged_at IS NULL` predicate is what makes
   the pass idempotent: a second sweep flags nothing new and does not move the timestamp.
3. **Flag pass, exceptions.** The same, per severity band, against
   `detected_at` and `status IN ('open','in_review')`. **Critical exceptions are flagged and escalated
   like any other, and never closed** — the sweeper contains no status transition to `resolved` at all.
   State that in a comment and let plan 03-01's trigger be the thing that would stop it if someone added
   one.
4. **Escalation pass.** For each newly flagged row — and for each already-flagged row whose
   `escalated_at` is null, so an escalation lost to a crash is retried — resolve the supervisory
   recipient through plan 02-10's `RecipientResolverService` using `escalation_recipient_role`, and
   trigger a notification through **`NotificationsService`**. Set `escalated_at` in the same transaction
   as the trigger, so the row and the notification commit together.
   - `notification_type`: `queue_item_aged` for tasks, `exception_aged` for exceptions — the two
     templates added at the top of this task. They render against the same closed context (type,
     severity, generic description, deep link, court name) with **no case substance**, which is also
     why the sweeper never dereferences `object_id`.
   - `severity` maps from the item: an aged `critical` exception escalates at `critical`, `high` at
     `warning`, everything else at `info`.
   - `object_reference` is the task or exception id, so the notification's deep link lands on
     `/go/task/{id}` or `/go/exception/{id}` — Phase 2's route again.
5. **No configured recipient** → do not swallow it. Count it in
   `escalation_recipients_unresolved` and raise a `notification_no_recipient_configured` exception
   through `ExceptionsService.raise` with a per-court `dedupe_key`. This is the exception type plan 02-11
   already defined; reuse it rather than inventing a parallel one.
6. Use plan 02-11's `ClockService` for every time comparison, so a test injects a clock instead of
   waiting.
7. Return `SweepResult` and log it at info, as plan 02-11 does.

CONTEXT names this directly as a consequence worth planning for: with no user-facing completion endpoint,
a producer that resolves its object but forgets to call `completeForAudit` leaves an open task pointing at
a resolved thing. The user cannot close it — correctly, by design — so it would sit in the queue forever,
degrade the age metrics F09 reports, and erode trust in the queue. That is a **defect**, so the sweeper
surfaces it; it does not quietly tidy it away.

`QueueReconciliationSweeperService.sweep(courtId?)`:
- Scans `platform.tasks` with `status IN ('open','in_progress')` and resolves the state of the referenced
  object through a small **resolver map**, keyed by `object_type`, declared in this file:
  | object_type | "already resolved" predicate |
  |---|---|
  | `exception` | `platform.exceptions.status = 'resolved'` |
  | `rule_package_version` | the package is published |
  | `entitlement_grant` | the grant request is approved or denied |
  | `retention_record` | a `disposition_log` row exists for it |
  Each entry is one line; an `object_type` with no entry is **skipped and counted**, never guessed at.
  Add a comment naming Phases 5–8 as the owners of their own entries, following the same
  declare-your-own-behaviour pattern the three registries in this phase use.
- For each inconsistency: raise **one** exception per task through `ExceptionsService.raise`:
  `exception_type: 'task_object_already_resolved'`, `severity: 'medium'`, `source_module: 'tasks'`,
  `object_type: 'task'`, `object_id: <task id>`, `dedupe_key: task:<id>`, and a `detail` naming the
  referenced object, its resolved state and the producing module. The catalog entry (plan 03-09) routes
  it to `platform_ops`.
- **It does not complete the task.** Completing it would require fabricating a
  `completing_audit_event_id`, which is the exact thing the whole design forbids. A human resolves the
  raised exception, and the remedy is a fix in the producing module.
- Runs on the same BullMQ schedule as the aging sweeper, as a second job, so there is one scheduling
  mechanism rather than two.
- Returns `{scanned, inconsistent, raised}` and logs it.

`apps/api/test/queue-reconciliation-sweeper.e2e-spec.ts`:

2. Create an exception with its linked task, then mark the exception `resolved` via raw SQL **with** a

4. A task whose `object_type` has no resolver entry is counted in `scanned`, never in `inconsistent`, and

5. The raised exception itself gets a linked task (it is an ordinary exception), routed to
   `platform_ops`, and that task does **not** then appear as its own inconsistency on the next sweep.

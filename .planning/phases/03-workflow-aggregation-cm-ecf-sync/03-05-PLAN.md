<objective>
Build the Work Queue service: the one write path into `platform.tasks`, an entitlement-based eligibility
model with a terminating loop guard, a role-scoped queue read, rationale-gated dismissal, and a completion
path no user can reach.

Purpose: ROADMAP criterion 1 requires a user to see their role-scoped open tasks in one place and to be
unable to dismiss a legally significant one without a rationale. CONTEXT adds two structural constraints
behind that. First, **eligibility resolves by entitlement, not role** — F06 says "resolve to at least one
user with that role", but Phase 1 locked "role existence must never imply access", so routing by role
sends tasks to people the global guard then denies, the task sits open, age metrics degrade, and the user
cannot discharge it. Second, **there is no user-facing completion endpoint** — `Y1a` documents
`{completing_audit_event_id}` in the request body, a client-supplied value standing in for a guarantee,
which is the exact shape Phase 2 rejected on config publish. Phase 1's stance was "prefer 'the API
refuses' over 'the audit catches it'", so a quiet completion becomes structurally impossible and F06's
`TASK_MISSING_AUDIT_REF` becomes the unreachable 500 tripwire it reads like.

Output: `TasksService` with `completeForAudit` as the only completion path, a task-type registry Phases
5–8 extend without editing this code, the queue and history reads, dismissal, and three test files — one
of which exists only to prove a route cannot be reached.
</objective>

<feature_dependencies>
Implements: F6: Work Queue and Task Management

Enables: F6; F7's exception-backed tasks (plan 03-09); F13's retention disposition tasks (plan 03-12); Phases 5–8 register their review and approval task types through `TaskTypeRegistry` with no edit here
</feature_dependencies>

**The loop guard, and why it is mandatory.** Exceptions now create tasks (plan 03-09), so a
`TASK_NO_ELIGIBLE_OWNER` exception could itself produce a task with no eligible owner, which would produce
another exception, forever. Implement it as follows and test it explicitly:
- `TasksService.create` asks `countEligible`. If zero, it does **not** insert a task.
- It calls `ExceptionsService.raise` with `exception_type: 'task_no_eligible_owner'`, `severity: 'high'`,
  `source_module: 'tasks'`, a `dedupe_key` of `${task_type}:${required_entitlement}:${court_id}`, and
  `detail` naming the task type, the entitlement nobody holds, and the object reference.
- That raise is made with **`link_task_on_no_owner: false`** — plan 03-09's `raise()` extension honours
  the flag and creates no linked task for this one exception type. The recursion terminates in one step.
- The exception's `required_entitlement` is `platform_ops`, the guaranteed-staffed `system_admin` surface
  plan 03-02 declared, so the signal reaches somebody rather than becoming a second orphan.
- The HTTP surface returns `422 TASK_NO_ELIGIBLE_OWNER` with F06's message verbatim: *"No user holds the
  required role to receive this task"*.

1. Revoke/omit an entitlement so no user in court A holds it; attempt `TasksService.create` for a task

4. Grant the entitlement to one user, retry → the task is created and appears in that user's queue.

`TasksService` is the only write path into `platform.tasks`, mirroring the narrowness plan 02-01 gave

**`create(tx, input)`** — resolves `required_entitlement` from the registry when not supplied, resolves
`priority` from the registry default unless overridden, calls the loop guard from task 1, then inserts.
It relies on plan 03-01's `uq_tasks_open_per_object` partial unique index for idempotency: on conflict it
returns `{ id, created: false }` rather than raising, so plan 03-09's one-time backfill and any producer
retry are both safe. Accept an optional `tx` exactly as `ExceptionsService.raise` does, so a producer can
create the task inside its own transaction.

**`completeForAudit(tx, ref, completingAuditEventId)` — the only completion path.** Signature takes the
transaction client **first and non-optional**, because the whole point is that the task closes in the same
transaction that wrote the audit event. It updates every open task matching `ref` to `completed` with
`completing_audit_event_id` set, and returns the count. Put the reasoning in a comment, from CONTEXT: the
source feature completes the task inside the SAME transaction that writes its audit event, passing the
event it just created; a crash between the two cannot leave a resolved object with an open task.

**`tasks-internal.controller.ts`** carries `POST /tasks` and `POST /tasks/{id}/complete` and is decorated
at the class level with Phase 1's `ServiceTokenGuard` — the identical pattern plan 01-05 used for
`audit-internal.controller.ts`. Both routes are excluded from the public OpenAPI tag by plan 03-14. Add a
file-head comment: *"`Y1a-api-shared.md` documents `/tasks/{id}/complete` with a client-supplied
`{completing_audit_event_id}`. Phase 3 deviates: that body is a client-supplied value standing in for a
guarantee. Registered as a deviation by plan 03-14."*

**`dismiss(principal, taskId, rationale)`** —
- Loads the task; a task not `open`/`in_progress` → `409 TASK_INVALID_TRANSITION`.
- Reads `queue_policy.legally_significant_task_types` and `queue_policy.rationale_bar` through
  `ConfigResolver` (never a constant, never a second copy of the bar).
- If the task type is legally significant, calls the shared `validateRationale(rationale, bar)` from
  `@judicialsync/config-schema`. `RATIONALE_REQUIRED` → `422 TASK_RATIONALE_REQUIRED`;
  `RATIONALE_TOO_SHORT` → `422 TASK_RATIONALE_TOO_SHORT` with `detail` carrying the bar and the actuals so
  the UI can render a precise message. **No length check is written in this file** — a grep in `<verify>`
  asserts that.
- Writes through plan 01-05's `withAudit` so the dismissal and its audit event commit atomically, with
  `action_type: 'status_change'`, `object_type: 'task'`, before/after state, and the resolved
  `rule_package_version_id` stamped per Phase 2's version-stamping decision.
- Sets `dismissed_by` from the authenticated session, never from the body.

`tasks.module.ts` fills plan 03-01's placeholder: provides `TasksService`, `TaskTypeRegistry`,
`OwnerResolverService`; imports `AuditModule`, `ExceptionsModule`, `ConfigModule`, `PolicyModule`;
**exports `TasksService` and `TaskTypeRegistry`** so plans 03-09, 03-11 and 03-12 inject them.

`GET /api/v1/tasks/my-queue` — self-scoped, carrying Phase 1's `@SelfScoped()` decorator rather than a
`@Resource()` descriptor (plan 03-02 recorded it in the undescriptored list). It returns open and
`in_progress` tasks where **all** of the following hold:

- `court_id` is within the principal's court scope (or null for platform-wide tasks, which additionally

**Sort (discretion resolved).** `ORDER BY priority DESC (urgent, high, normal, low), created_at ASC` —
F06's "priority then age", with oldest first inside each priority band. ROADMAP criterion 1's "oldest items
visibly flagged by age" is satisfied by the `aging_flagged` field, which is a separate visual signal, not
the sort. Record that reading in the SUMMARY so the UI plan does not re-litigate it. Offer
`?sort=age|priority` so a user can override; `age` sorts purely `created_at ASC`.

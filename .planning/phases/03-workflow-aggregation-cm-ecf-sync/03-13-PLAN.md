<objective>
Extend the idempotent seed so every Phase 3 configuration key is published, every Phase 3 entitlement is
held by somebody, and every Phase 3 guarantee is demonstrable by clicking rather than by writing a test
first.

Purpose: Phase 1 built an idempotent seed with two courts, sealed and restricted cases and one user per
role, and gave the reason — it makes the success criteria demonstrable by clicking and gives every
downstream phase a scenario-complete starting point instead of each phase inventing its own fixtures.
Phase 3 has four things that are invisible without fixtures: a **locally-modified field** for the
criterion-5 conflict demonstration, **aged** tasks and exceptions for the sweeper and the age flag, enough
**volume** for small-cell suppression to be observable rather than theoretical, and the Phase 3
**configuration keys** without which `ConfigResolver` throws `CONFIG_NOT_FOUND` on every Phase 3 read —
because Phase 2 locked "never substitutes a default".

The conflict fixture has to line up with plan 03-04's mock on both sides: the seeded party must be the one
the mock's `conflict` scenario targets, matched on the shared `source_identifier` constant, or the
demonstration quietly does nothing.

Output: the Phase 3 operational-package keys, the six entitlement grants, the fixture module, and a test
proving three consecutive seed runs converge.
</objective>

<feature_dependencies>
Implements: F6: Work Queue (aged tasks, the queue policy), F7: Exception Queue (aged exceptions of every severity), F9: Operational Reporting Feed (volume on both sides of k, the reporting policy), F10: CM/ECF Integration Adapter (the locally-modified conflict fixture, the adapter policy)
Depends on: F0: Identity and Access Management (plan 01-04's users and plan 01-08's grant model), F3: Configuration Engine (plan 02-06's v1 package seed, which this extends rather than replaces)
Enables: F6, F7, F8, F9, F10 — the three UI plans and the assurance suite all run against these fixtures
</feature_dependencies>

`phase3-fixtures.ts` exports `PHASE3_SEED_IDS` with **deterministic UUIDs** (literal constants, not

regenerated id breaks every one. Plan 01-04 established the pattern; follow it.

Every write is an upsert or an `ON CONFLICT DO NOTHING`, because compose volumes persist and the seed
re-runs on every boot. State that at the top of the file.

**A. The conflict demonstration (ROADMAP criterion 5).**
- A case in court A sourced from CM/ECF, with a party whose `source_identifier` equals the mock's
  `CONFLICT_DEMO_SOURCE_IDENTIFIER` constant exported by `apps/api/test/mock-cmecf.ts`. **Import the
  constant; do not retype the literal** — a divergence here makes the demonstration silently do nothing.
  Apply plan 03-10's `{court_code}:` namespacing so the stored value matches what the adapter will look
  up.
- Set that party's `locally_modified_fields` to `['party_name']` and its `party_name` to a value
  distinct from the mock's baseline, so the mock's `conflict` scenario presents a genuinely differing
  value against a locally-modified field. Write the array, never the boolean — plan 03-01's trigger
  derives it, and this is also a small test that the trigger fires during seeding.
- A short comment naming the demonstration: *set the mock to the `conflict` scenario, trigger a poll, and
  the conflict appears in the Exception Queue while this party's name stays unchanged.*

**B. Aged queue items.**
- Three open tasks in court A with `created_at` backdated to 1 hour, 50 hours and 200 hours ago, so one
  is inside the 48-hour threshold and two are past it, with `aging_flagged_at` left **null** so the
  sweeper has work to do on first run rather than the fixture pre-flagging it.
- Four open exceptions, one per severity, each backdated past its own band — including a **critical**
  one, which is the row the assurance suite tries and fails to batch-close.
- Each exception gets its linked task through the normal `ExceptionsService.raise` path if the seed can
  reach it; if the seed runs outside the Nest context, insert the exception and the task together in one
  transaction with the same column values `raise()` would produce, and add a comment saying so. Do not
  leave an exception without its task — that would make the backfill's first run look like a defect.

**C. Reporting volume (so suppression is observable).**
- In court A, one division with **2** open exceptions of a single type — below the default k of 5, so the
  dashboard renders it suppressed.
- A second division with **9** of another type — comfortably above k, so a real number renders beside the
  suppressed cell and the contrast is visible on screen.
- Enough completed and dismissed tasks across both divisions for `adoption_rate` to produce a
  non-degenerate rate rather than 0 or 1.
- Spread `created_at`/`detected_at` across all four age buckets so `backlog_age` shows four rows, not one.

**D. Delivery-log and health fixtures.** One `cmecf_delivery_log` row with `disposition:'no_op_duplicate'`
and one `adapter_health_log` row with a recent successful sync, so Screen-18 renders populated panels
before the first poll ever runs. Both upserted on a deterministic id.

`seed.ts` calls `seedPhase3Fixtures(prisma)` after the identity and configuration seeds, inside the same
top-level transaction boundary plan 01-04 established.

<objective>
Turn Phase 2's exceptions table and its narrow write path into the Exception Queue: triage, the rationale
gate, the critical auto-close prohibition at the API layer, per-type resolution actions, and the 1:1 task
link that makes the Work Queue the single entry point.

Purpose: ROADMAP criterion 2 has three parts — one cross-module queue, a critical exception that can never
be auto-closed, and no resolution without a rationale meeting the minimum bar. Plan 03-01 put the second
and third at the database. This plan puts them at the API, where a user gets `403` and `422` with F07's
own codes rather than a raw constraint violation, and the database stays the backstop for code that never
reaches the service.

The highest-leverage line in the phase is here: **extending `ExceptionsService.raise()` to create the
linked task in the same transaction is ONE edit that covers every existing and future producer.** Phase 2
built a single narrow write path for exactly this. Every Phase 1 and Phase 2 producer — `integrity_alert`,
notification delivery failures, missing recipient configuration, content-policy violations, search
projection failures — and every Phase 5–8 producer gets a task automatically, with no producer code
change. The alternative CONTEXT rejected, scheduled projectors per producer, loses the task when a crash
lands between the condition and the projection.

Output: the extended `raise()`, the exception-type catalog, the resolution-action registry with
sync-conflict resolution registered rather than reimplemented, the queue and resolve endpoints, the
idempotent backfill, and three test files.
</objective>

**Route the row first.** In `exceptions.service.ts`, `raise()` now writes
`required_entitlement = requiredEntitlementForExceptionType(input.exception_type)` onto the exception
row itself, in the same insert. This is load-bearing and easy to miss: plan 03-01 added the column
with **no default**, and plan 03-02's `resource_declared_entitlement` **denies** a row whose
`required_entitlement` is null. An exception that reaches the table without it is invisible in the
queue and unresolvable by anyone — the precise opposite of what raising it was for. The column is
written on the insert path only; a dedupe merge leaves the existing value alone.

**One edit, every producer.** Then, after the insert or dedupe-merge, and **inside the same
transaction**, call `TasksService.create(tx, {...})` with:
- `task_type: 'exception_resolution'`,
- `object_type: 'exception'`, `object_id: <the exception id>`,
- `exception_id: <the exception id>` (the `UNIQUE` column that enforces 1:1),
- `court_id` and `source_module` copied from the exception,
- `required_entitlement` from `requiredEntitlementForExceptionType(exception_type)`,
- `priority` derived from severity: `critical`→`urgent`, `high`→`high`, `medium`→`normal`, `low`→`low`.

Rules that make this safe:
- **Only on `created === true`.** A dedupe merge bumps `occurrence_count` on an open exception that
  already has its task; creating a second would violate `tasks.exception_id UNIQUE` anyway, but returning
  the existing `task_id` is the correct behaviour rather than relying on the constraint to catch it.
- **Honour `link_task: false`.** Default true. The only Phase 3 caller passing false is plan 03-05's
  no-eligible-owner path; add an assertion that `link_task === false` is accepted only for
  `exception_type === 'task_no_eligible_owner'`, so the escape hatch cannot be reused casually.
- `raise()` now returns `{ id, created, task_id }`. Existing Phase 2 callers destructure `{id, created}`
  and are unaffected — verify by running Phase 2's tests unmodified.
- **Replace plan 02-01's scope comment.** It says the queue, triage, aging, the critical auto-close
  prohibition and rationale-gated resolution "are all F07, all Phase 3". Phase 3 is here: replace it with
  a comment naming this module's new surface and keep the "single write path" statement intact.

`exception-type.catalog.ts` maps each `exception_type` to its required entitlement, default severity and
module, per the contract above. Two notes belong in the file:
- Entitlements are **reused, not invented** — `audit_reader` for `audit_integrity_break` (Phase 1),
  `config_admin` for `unmapped_docket_event` (Phase 2, and the type whose resolution routes a standing
  mapping rule through the Configuration Engine per Screen-13), and the three Phase 3 entitlements plan
  03-02 declared for the rest.
- An unknown `exception_type` falls back to `exception_resolve` **and logs a warning**, so a Phase 5 type
  that forgets to register is actionable by someone rather than silently unroutable. Do not fail closed
  here: an unroutable exception is worse than a broadly-routed one, because the condition it reports is
  real either way.

`backfill.service.ts` — `backfillLinkedTasks()` does **two** things, because rows that predate Phase 3
are missing both:
1. **Backfills `required_entitlement`** on every `platform.exceptions` row where it is null, from
   `requiredEntitlementForExceptionType(exception_type)`. This runs **first**, in its own statement,
   because the task's `required_entitlement` is derived from it — and because without it Phase 1's
   `integrity_alert` rows and Phase 2's delivery-failure rows stay permanently fail-closed.
2. **Creates the missing linked tasks**: selects rows with `status IN ('open','in_review','escalated')`
   and no row in `platform.tasks` with that `exception_id`, then creates each through
   `TasksService.create` in batches, inside a transaction per batch.

- It is **idempotent three times over**: the entitlement backfill is predicated on `IS NULL`, the task
  pass on `WHERE NOT EXISTS`, and `uq_tasks_open_per_object` / `tasks.exception_id UNIQUE` sit
  underneath both. Re-running must change nothing.
- Returns `{ scanned, created, skipped, entitlement_backfilled, no_eligible_owner }`.
- Exposed as a service-token-guarded `POST /api/v1/internal/exceptions/backfill-tasks` on a **new
  `exceptions-internal.controller.ts`**, decorated at class level with Phase 1's `ServiceTokenGuard` —
  the identical pattern plan 03-05 used for `tasks-internal.controller.ts` and plan 01-05 for
  `audit-internal.controller.ts`. It must **not** hang off the public `exceptions.controller.ts`:
  plan 02-01's own verify asserts the exceptions module had no controller at all, and a service-token
  route on the public controller would be emitted into `openapi/openapi.json` by plan 03-14. Plan
  03-14 excludes this controller from the document and asserts the path's absence.
- It is **also** invoked once at module init behind an `EXCEPTIONS_BACKFILL_ON_BOOT` flag defaulting
  to true, so a deployment that never calls the endpoint still converges. Log the result.
- An exception whose entitlement nobody holds hits plan 03-05's loop guard: it is counted in
  `no_eligible_owner` and skipped, not retried forever. Note that it still got its
  `required_entitlement` written in step 1, so it is **visible** to a holder of that entitlement the
  moment one exists — a missing owner must not also mean a hidden row.

**Close the module cycle safely — this wave, not later.** Plan 03-05 (wave 2) had `tasks.module.ts`
import `ExceptionsModule`. This task makes `exceptions.module.ts` import `TasksModule`, which
**closes the cycle**, and NestJS fails at bootstrap on an unguarded mutual module reference. So both
sides are wrapped here, in the wave that creates the problem:
- `exceptions.module.ts`: `imports: [forwardRef(() => TasksModule), ...]`
- `tasks.module.ts`: change plan 03-05's direct `ExceptionsModule` import to
  `forwardRef(() => ExceptionsModule)`
- Any constructor injection across the boundary uses `@Inject(forwardRef(() => TasksService))`.

This is the only reason `apps/api/src/modules/tasks/tasks.module.ts` appears in this plan's
`files_modified`. Plan 03-11 (wave 4) adds providers to the same file and must leave the `forwardRef`
intact. Plan 01-01's `context-boot.e2e-spec.ts` is the test that catches this, and it must pass in
**this** wave — every `<verify>` block in this plan starts the stack, so a bootstrap failure here
fails the plan rather than silently deferring to wave 4.

`exceptions.module.ts` imports `forwardRef(() => TasksModule)` and `ConfigModule`, provides the catalog,

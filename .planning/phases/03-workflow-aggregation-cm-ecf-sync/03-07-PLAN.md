<objective>
Make the no-silent-overwrite rule precise at field granularity, and give conflict resolution a memory so a
kept-local decision is not re-litigated on every poll.

Purpose: ROADMAP criterion 5 is the phase's sharpest success criterion — an incoming field that conflicts
with a local value must route to human review rather than silently overwrite either value, *confirmed by
deliberately creating a conflicting field*. Phase 1 shipped a row-level `locally_modified` boolean and
explicitly left conflict detection to Phase 3. CONTEXT takes the richer version now, while the system is
pre-pilot, for Phase 1's own stated reason: deferring the columns would force a later migration and
backfill across live court records. The argument for field granularity is operational rather than
aesthetic — a clerk correcting a party's phone number flags the whole row, so a later CM/ECF correction to
the party *name* raises a false conflict, and false conflicts compound into alert fatigue, which trains
staff to click through and defeats the control entirely.

The second half of this plan is the loop breaker. Without recording the CM/ECF value that was rejected,
keep-local re-raises forever: every poll sees a differing field on a locally-modified field. Merging via
`dedupe_key` would only make a counter climb, which is not resolution and turns `resolved` into a status
that does not mean resolved.

Output: a provenance service every case-context write path calls, the authoritative-field map, the
four-way per-field decision, the two resolution semantics with both values audited, and two test files.
</objective>

`conflict-detector.service.ts` exposes `reconcileFields(tx, input)` where
`input = { table, internalId, courtId, sourceIdentifier, incoming: Record<string, string|null> }`.
It runs **inside the ingest transaction** (plan 03-10 supplies the client) and, for each field in
`CMECF_AUTHORITATIVE_FIELDS[table]` present in `incoming`, evaluates in this order:

1. **Values equal** (after normalising: trim, and compare dates as instants rather than strings) →
   `{action:"no_change"}`. F10 step 3: no action, or a refreshed `last_synced_at`.
2. **Differ and the field is NOT in `locally_modified_fields`** → `{action:"auto_apply", field, newValue}`.
   F10 step 4 is explicit that this "is not an overwrite-of-local-edit, merely applying a fresh
   authoritative value". The detector returns the decision; **plan 03-10 performs the write**, so the
   detector has no write path of its own and a future caller cannot use it to mutate records sideways.
3. **Differ, field IS locally modified, and the most recent *resolved* conflict for
   `(table, internalId, field)` has `resolved_source = 'manual_override'` and
   `rejected_cmecf_value` equal to the incoming value** → `{action:"no_op_already_rejected", field}`.
   This is the loop breaker. Comment it with CONTEXT's sentence: *a conflict re-raises only when CM/ECF
   presents a genuinely NEW value; the next poll seeing the already-rejected value is a no-op.*
4. **Differ, field IS locally modified, value is new** → create or reuse the conflict and raise:
   - `INSERT INTO platform.sync_conflicts (object_type, object_id, field_name, cmecf_value, local_value,
     court_id, source_system, source_identifier, status) VALUES (..., 'open')`
     with `ON CONFLICT ON CONSTRAINT uq_sync_conflicts_open_field DO UPDATE SET cmecf_value = EXCLUDED.cmecf_value`
     — one open conflict per field, ever, so a redelivery cannot stack duplicates.
   - Call `ExceptionsService.raise(tx, {...})` with `exception_type: 'sync_conflict'`,
     `severity: 'high'`, `object_type: table`, `object_id: internalId`, `source_module: 'cmecf'`,
     `court_id`, `dedupe_key: ${table}:${internalId}:${field}`, and a `detail` carrying
     `{field_name, cmecf_value, local_value, source_identifier, sync_conflict_id}`. The dedupe key means
     a redelivery merges into the same exception rather than creating a second — which is what makes
     "no duplicate conflict exception was created" provable.
   - Write `sync_conflicts.exception_id` back from the raise result.
   - Return `{action:"conflict_raised", field, conflictId, exceptionId}`.

`ConflictResolutionService.resolve(tx, {conflictId, choice, reviewerUserId, rationale})`. It is invoked by
plan 03-09's exception resolution-action registry, **not by an endpoint of its own** — CONTEXT locks
sync-conflict resolution to being built ONCE, as an exception `resolution_action`, with Screen-18's
conflict list a filtered view that deep-links into that same UI. F10 step 5 routes conflicts into F07, so
this is the spec's own structure. Head the file with that note so nobody adds a second route later.

Both branches run inside the caller's transaction and inside plan 01-05's `withAudit`, so the resolution
and its audit event commit atomically:

**`accept_cmecf`** —
- Write `cmecf_value` onto the live record's field (the only place in the adapter that writes a
  conflicted field).
- `ProvenanceService.clearField(tx, table, id, field)` — the field returns to normal automatic sync. Every
  other locally-modified field on the row stays flagged, which is the entire point of field granularity.
- `sync_conflicts`: `status='resolved'`, `resolved_value = cmecf_value`, `resolved_source = 'CM/ECF'`,
  `rejected_cmecf_value = NULL`, `resolved_by`, `resolved_at`.

**`keep_local`** —
- Leave the live record untouched.
- Leave the field in `locally_modified_fields` — clearing it would let the next CM/ECF change silently
  overwrite the clerk's deliberate choice, which is the exact outcome criterion 5 exists to prevent.
- `sync_conflicts`: `status='resolved'`, `resolved_value = local_value`,
  `resolved_source = 'manual_override'`, **`rejected_cmecf_value = cmecf_value`**, `resolved_by`,
  `resolved_at`.

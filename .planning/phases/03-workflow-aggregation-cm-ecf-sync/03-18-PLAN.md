<objective>
Build the named Phase 3 assurance suite: eleven proofs plus a machine-checked traceability map, mirroring
plan 01-14 and plan 02-16.

Purpose: CONTEXT makes this an **explicit, named deliverable, not left to developer discretion**, and
gives the reason — Phase 3's guarantees are almost entirely *"never"* claims, which are exactly what
quietly stop being true. Three of them are enforced at the database precisely because a future phase's
batch job could otherwise walk around the service, and a guarantee enforced at the database must be
tested at the database: plan 01-14 established that an immutability claim is proven by issuing raw SQL
**as the application role** and asserting a Postgres error, not by asserting a 403 from a handler that
might simply not have been called.

Four of the eleven restate a ROADMAP success criterion in its own words. Proof 5 is criterion 5
verbatim — *"a deliberately conflicting CM/ECF field lands in the conflict queue and the local value is
unchanged"* — which is why plan 03-04's mock had to be drivable and plan 03-13's seed had to leave a
field deliberately modified.

Output: the shared harness with its raw-SQL clients, eleven proof files, the traceability spec that
fails if a guarantee has no proof, the appended `docs/ASSURANCE.md` matrix, and the CI job that runs them.
</objective>

**Proof 1 — a critical exception cannot be batch-closed.** CONTEXT: *attempted as `app_rw` via raw SQL,
asserting a **database** error, not an application error.*
1. `rawAppRw("UPDATE platform.exceptions SET status='resolved' WHERE id=$1", [criticalId])` → rejects,
   and the error is a `pg` error whose message names `EXCEPTION_CRITICAL_MANUAL_ONLY`. Assert the
   rejection is a database error — not an HTTP status, not a Nest exception.
2. The same with a `reviewer_user_id` but no rationale → rejects.
3. The same with a reviewer and a 6-character rationale → rejects.
4. A **bulk** update, `UPDATE platform.exceptions SET status='resolved' WHERE severity='critical'`,
   touching more than one row → rejects, and **no** row changed. This is the "batch process" of the
   criterion's own wording.
5. Through the API as a service token with no individual reviewer →
   `403 EXCEPTION_CRITICAL_MANUAL_ONLY`.
6. Through the API as an entitled human with a valid rationale → 200, and the row is `resolved`. The
   guarantee is that only this path works, not that nothing works.
7. Assert the application exposes **no bulk-resolve route**: enumerate the OpenAPI paths and assert none
   matches `/exceptions/(bulk|batch)/i` and that `/exceptions/{id}/resolve` is the only resolve operation.

**Proof 2 — the rationale floor holds, and configuration cannot weaken it.**
1. Resolve with no rationale → `422 EXCEPTION_RATIONALE_REQUIRED`.
2. With `"too short"` (9 characters) → `422 EXCEPTION_RATIONALE_TOO_SHORT`.
3. With `"supersedingvalue"` (16 characters, one word) → `422 EXCEPTION_RATIONALE_TOO_SHORT`. The
   two-word rule is independent of length.
4. `publishOperationalPackage(court, {queue_policy:{rationale_bar:{min_characters:1,min_words:1}}})` →
   **rejected at publish** with `CONFIG_INVALID_STRUCTURE`, and the court's effective bar is unchanged.
5. Publish a **tightening** bar of 40 characters → accepted; a 20-character rationale that passed in
   step 3's baseline now returns `422`. A court may tighten.
6. With the tightened bar still in force, `rawAppRw` resolving with a 12-character, 2-word rationale →
   **permitted by the database**, because the database enforces only the floor. Assert this explicitly:
   the two layers enforce different bars on purpose, and a reader must not conclude the trigger is
   redundant. (Perform this on a `low`-severity row and roll it back.)

**Proof 3 — a legally-significant task cannot be dismissed without a rationale.**
1. Dismiss a `config_approval` task with no rationale → `422 TASK_RATIONALE_REQUIRED`; the task is still
   `open`.
2. With a 9-character rationale → `422 TASK_RATIONALE_TOO_SHORT`.
3. With a valid rationale → 200, `dismissed`, `dismissed_by` equals the **session** user, and exactly one
   audit event was written.
4. `rawAppRw("UPDATE platform.tasks SET status='dismissed' WHERE id=$1")` with no rationale → rejects
   with a database error naming `TASK_RATIONALE_REQUIRED`.
5. A task type **outside** the configured legally-significant set dismisses with no rationale → 200,
   proving the gate is targeted rather than universal.

**Proof 4 — there is no user-facing task-completion path.** CONTEXT: *a user citing a valid audit event
cannot close a task.*
1. Create a genuinely valid `audit_events` row through the normal path and capture its id.
2. `POST /api/v1/tasks/{id}/complete` with a **session** token and that real id → refused by the service
   token guard; the task is still `open` afterwards.
3. The same as a `system_admin` holding every Phase 3 entitlement → still refused. Authorization is not
   the control.
4. The same with a **service token** → 200. The route works for its intended caller.
5. `rawAppRw("UPDATE platform.tasks SET status='completed' WHERE id=$1")` with a null
   `completing_audit_event_id` → rejects with a database error naming `TASK_MISSING_AUDIT_REF`.
6. The emitted OpenAPI document contains **no** `/tasks/{id}/complete` path, so no generated client can
   even offer it.

**Proof 5 — criterion 5, verbatim.** *"Inbound CM/ECF case/party/docket-event/order data appears with
source identifiers preserved, and when an incoming field conflicts with an existing local value, the
conflict routes to a human-review queue instead of silently overwriting either value — confirmed by
deliberately creating a conflicting field and observing it land in the conflict queue, not get silently
applied."* Structure the test to mirror that sentence:
1. `drivePoll('healthy')` → records exist with `source_system = 'CM/ECF'` and a court-namespaced
   `source_identifier`. **Source identifiers preserved.**
2. Read and record the seeded conflict party's current `party_name` — the clerk's local correction, which
   plan 03-13 left deliberately in `locally_modified_fields`.
3. `drivePoll('conflict')` → the feed presents a different `party_name` for that record.
4. Assert **the conflict routed**: exactly one open `sync_conflicts` row for
   `(party, id, 'party_name')` carrying both values and the source identifier, exactly one open
   `sync_conflict` exception linked to it, exactly one linked `exception_resolution` task, and a
   `cmecf_delivery_log` row with `disposition: 'conflict_raised'`.
5. Assert **the local value is unchanged** — re-read the party row and compare to the value captured in
   step 2, byte for byte. This is the single most important assertion in the phase.
6. Assert **neither value was silently applied**: the CM/ECF value appears only in `sync_conflicts`, not
   on the live record.
7. Assert the conflict is reachable by a human: `GET /exceptions` as the entitled user returns it with
   `available_actions` containing `accept_cmecf` and `keep_local`, and `GET
   /integrations/cmecf/conflicts` returns it with its `exception_id`.
8. **A field that was never locally modified is auto-applied** in the same poll, proving the rule is
   field-level and not a blanket refusal to update.

**Proof 6 — duplicate redelivery is idempotent.**
1. `drivePoll('healthy')`; snapshot counts of `cases`, `parties`, `docket_events`,
   `document_references`, `exceptions`, `sync_conflicts`.
2. `drivePoll('duplicate')` → **every one of those counts is unchanged**.
3. One `cmecf_delivery_log` row per redelivered record with `disposition: 'no_op_duplicate'`.
4. Redeliver the **conflicting** record after a conflict is already open → still exactly one conflict row
   and exactly one exception; the exception's `detail->>'occurrence_count'` may rise, but the row count
   does not. *"No duplicate conflict exception was created"*, proven.
5. A third redelivery → same result, so idempotency is not a one-shot.

**Proof 7 — keep-local does not re-raise; a new value does.**
1. From proof 5's state, resolve the exception with `keep_local` and a valid rationale, as an entitled
   human through the API.
2. Assert the resolution recorded `resolved_source: 'manual_override'`, `rejected_cmecf_value` equal to
   the CM/ECF value, the field still in `locally_modified_fields`, the live value still the clerk's, the
   linked task now `completed`, and one audit event carrying both values.
3. `drivePoll('conflict')` again with the **same** value → **zero** new conflicts, **zero** new
   exceptions, and a `cmecf_delivery_log` row recording the no-op. This is the loop breaker.
4. Append a record with a **genuinely new** `party_name` through the mock's control API and poll → exactly
   one new open conflict and one new exception. Resolution does not become permanent deafness.
5. Resolve that one with `accept_cmecf` → the live value is now the CM/ECF value, `party_name` is gone
   from `locally_modified_fields`, and **another locally modified field on the same row is still
   flagged** — field granularity, proven at the assurance level.
6. Poll once more with the accepted value → no conflict, because the field is no longer locally modified.

**Proof 8 — both absence semantics, asserted together.** CONTEXT: *the assurance suite asserts both —
partial is loud, excluded is invisible.*
1. **Silent.** As a clerk **without** the sealed designation entitlement, `GET /cases/{id}/timeline` for
   the seeded case holding a sealed docket entry: the entry is absent; `providers[docket].entry_count`
   equals the number of entries actually returned; the serialised body contains none of `sealed`,
   `restricted`, `excluded`, `redacted`, `withheld`, nor the excluded entry's id; the status is **200**
   and `partial` is **false**.
2. The same request as a clerk **with** the entitlement returns the entry and a higher `entry_count`.
   **Assert the two `entry_count` values differ** — this is what proves the count is post-exclusion
   rather than a constant.
3. **Loud.** With a deliberately failing provider registered, the same request returns **206**,
   `error_code: TIMELINE_PARTIAL_DATA`, `partial: true`, and a `providers` entry with
   `status: "unavailable"` and a `reason` containing no exception text.
4. **Both at once.** The unentitled clerk, with the failing provider registered: 206 and the failing
   module named, **and** the sealed entry still absent, **and** the docket provider's `entry_count` still
   the post-exclusion number. The two mechanisms are independent.
5. The byte-identical empty state: a case with no entries and a case whose only entries are excluded from
   this viewer produce **identical** response bodies apart from the case id.

**Proof 9 — reporting de-identification, all four claims.** CONTEXT: *the reporting role gets a Postgres
permission error on any base table; the payload carries no identifier; small cells are suppressed; the
label is present in exported **bytes**.*
1. `rawAppReporting("SELECT * FROM platform.exceptions LIMIT 1")` → **Postgres permission denied**.
   Repeat for `platform.cases`, `platform.tasks`, `platform.parties`, `platform.audit_events`,
   `platform.sync_conflicts`. Assert each is a database error.
2. `rawAppReporting("SELECT * FROM reporting.backlog_age($1,$2,$3,$4)")` → succeeds.
3. `GET /reporting/dashboard` with all four v1 metric sets: the serialised payload matches no UUID,

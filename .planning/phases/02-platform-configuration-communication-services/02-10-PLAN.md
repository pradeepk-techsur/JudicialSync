<objective>
Make the Notifications Service real end to end: resolve court-configured recipients and channels
through `ConfigResolver`, render through the closed-context templates, persist notification and
delivery rows, deliver through the channel registry, expose the user inbox and acknowledgement, and
apply the locked audit boundary.

Purpose: ROADMAP criterion 2 — *"A recipient receives a notification whose body/preview never contains
party names, exhibit descriptions, or sealed-case detail — only a generic description plus a secure
deep link — with delivery status (sent/failed/acknowledged) tracked."* Plan 02-03 made the content side
structurally safe; this plan makes delivery happen and makes its status queryable. CONTEXT locks the
audit boundary: *"Audit any acknowledgment where `severity = critical`, UNION every `threshold_crossed`
acknowledgment regardless of tier… All other delivery lifecycle events remain operational records."*
Severity-driven coverage means alert types introduced in Phases 5–8 are captured automatically, with no
list for someone to forget to update, and the `threshold_crossed` union closes the warning-tier gap
`FRD/F04`'s literal wording misses.

Output: a working trigger-to-inbox pipeline. Retry, backoff, escalation and exception emission are plan
02-11.
</objective>

`RecipientResolverService.resolve(courtId, notificationType, explicit)`:
1. Read `configResolver.get(courtId, 'notification_recipients')` — **configuration, never a hardcoded list**. Keep the returned `rule_package_version_id`; it stamps the notification row.
2. Select the entries whose `notification_type` matches. If `explicit.recipient_user_id` was supplied, that user is a recipient on the configured channels for the type; if `explicit.recipient_role` was supplied, it narrows the configured entries to that role.
3. **Expand each role to every holder in that court.** Claude's-discretion decision, resolved: **all holders**, not round-robin and not a single designee. Round-robin makes "who was told?" depend on invisible rotation state, and a single designee makes one person's absence a silent single point of failure — criterion 3 is about alerts never being silently dropped. Resolve holders through plan 01-06's entitlement resolution, not by reading `user_roles` directly. Per-user channel preferences are **not** built in Phase 2; the court-level configuration is the whole surface. Record both decisions in the SUMMARY.
4. Deduplicate `(user_id, channel)` so a user holding two matching roles gets one delivery per channel, not two.
5. Return `{recipients: [{user_id, email, display_name, channel, escalation_cadence_minutes, escalation_recipient_role}], rule_package_version_id}`.
6. **No configured recipient** → throw `ApiException(422, 'NOTIFY_NO_RECIPIENT_CONFIGURED', 'No recipient is configured for this alert type in this court')` — the exact status, code and message from `FRD/F04` Error States. Plan 02-11 converts that into a durable `exceptions` row; `FRD/F04` Validation requires it "raise a configuration exception (F07), not silently fail to send."
7. A configured role that currently has **no holders** is the same failure — it is a configuration that cannot deliver. Raise the same error with the role in `detail`.

`NotificationsService.trigger(input)`:
1. Validate the DTO.
2. `resolve(...)`.
3. Load the court's `court_name` (one row read — the **only** record read this module performs, and it is not case content).
4. `buildRenderContext({notification_type, severity, object_reference, court_name})`.
5. For each distinct channel among the recipients: `templateRegistry.render(channel, ctx)`, then `assertContentPolicy(ctx, msg)`. A violation throws `500 NOTIFY_CONTENT_POLICY_VIOLATION` and **the whole trigger fails before any row is written** — nothing queued, nothing sent.
6. In **one transaction**: insert the `notifications` row (`notification_type`, `severity`, `object_type`, `object_id`, `court_id`, `rule_package_version_id`, `template_key`, `template_version`), then one `notification_deliveries` row per `(recipient, channel)` with `status='queued'`, `attempt_count=0`, `next_attempt_at=now()`, and `escalation_due_at = now() + escalation_cadence_minutes` when a cadence is configured (null otherwise).
7. After commit, enqueue one BullMQ delivery job per delivery id (plan 02-11 owns the worker; this plan only enqueues, using the queue plan 01-12 established).
8. Return `{notification_id, delivery_ids}`.

Setting `escalation_due_at` at insert time is what makes plan 02-11's sweeper a single indexed query
over durable state rather than a per-notification timer — CONTEXT's *"a sweeper's decision is derivable
from durable Postgres rows at any instant."*

Register everything in `NotificationsModule` and export `NotificationsService` so later phases inject
it rather than reimplementing delivery.

`DeliveryService.attempt(deliveryId)` performs exactly one send and advances one row's status. It owns
**no scheduling** — plan 02-11's worker decides when to call it, which keeps retry policy in one place:
1. Load the delivery with its notification; refuse if `status` is already `sent`, `delivered`, `acknowledged` or `failed` (idempotency — a redelivered BullMQ job must be a no-op, not a second email).
2. Re-render from the stored `template_key` and the notification's fields, and re-run `assertContentPolicy`. Re-checking at send time is cheap and closes the window where a template changed between enqueue and send.
3. `channelRegistry.get(delivery.channel).send(recipient, msg)`.
4. On success: `status='sent'`, `sent_at=now()`, `attempt_count += 1`. For the `in_app` channel, go straight to `sent` — the row's existence *is* the delivery, as plan 02-03 documented.
5. On failure: `attempt_count += 1`, `last_error` = the adapter's error, and return `{status:'queued', retryable}` leaving the row `queued` with `next_attempt_at` **unset** — plan 02-11 computes the next attempt time from the configured backoff. Do not compute it here; two places computing backoff is two policies.
6. `ChannelRegistry.get` throwing `502 NOTIFY_CHANNEL_UNAVAILABLE` is treated as a retryable failure, not a crash.

**The content-policy tripwire must itself be a critical alert.** CONTEXT locks the tripwire as
"defense in depth — a tripwire that should be unreachable, and whose **firing is itself a critical
alert**", and the standing Phase 1 pattern rejects log-only for exactly this situation: *"too easy to
miss and leaving no audit-visible trace of detection."* As written so far, the one Phase 2 failure
CONTEXT singles out as alert-worthy would be the only one with no durable record.

Wrap **both** `assertContentPolicy` call sites — the trigger-time check in
`notifications.service.ts` (task 1) and the send-time re-check in `delivery.service.ts` — so a
`NOTIFY_CONTENT_POLICY_VIOLATION` raises a durable exception **before** the 500 propagates:

```typescript
try {
  assertContentPolicy(ctx, msg);
} catch (err) {
  await this.exceptions.raise(null, {              // null: no caller transaction; the alert must
    exception_type: "notification_content_policy_violation",   // survive the caller's rollback
    severity: "critical",
    object_type: "notification_template",
    object_id: notificationIdOrNil,
    court_id: input.court_id,
    source_module: "notifications",
    detail: { template_key: templateKey, template_version: TEMPLATE_VERSION,
              notification_type: ctx.notification_type, channel },
    dedupe_key: templateKey,                       // one open row per offending template, not per send
  });
  throw err;                                        // the 500 still blocks the send
}
```

Three properties matter and must be preserved. The `raise` passes `null` rather than the caller's
transaction, because the trigger's transaction is about to roll back and the alert must outlive it.
The `detail` carries the **template** identity and nothing record-derived — this is the one code path
where a leaking value is known to be in scope, so writing it into an exceptions row an administrator
reads would be the leak repeating itself. And `dedupe_key` is the template key, so a broken template
firing on every send produces one open row with a rising `occurrence_count`, not a flood.

Import `ExceptionsModule` into `NotificationsModule` here; plan 02-11 then uses the same injected
service without re-wiring it.

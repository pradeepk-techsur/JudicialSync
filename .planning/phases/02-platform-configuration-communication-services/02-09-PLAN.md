<objective>
Ship `GET /search`: the full `FRD/F05` filter surface, a `SearchProvider` interface sized so OpenSearch
drops in by configuration, a Postgres FTS + `pg_trgm` implementation that applies the scope predicate
**before** ranking, a machine-readable `unsupported_filters[]` notice, and an operational
`search_query` record per search.

Purpose: ROADMAP criterion 4 — *"A user searching by identifier/party/witness/status/date/proceeding
receives zero hits for a record outside their access scope (not a redacted placeholder result)."*
`FRD/F05` Validation forbids a relevance-ranked-then-filtered design by name because it "risks
information leakage through ranking side effects (e.g., result count hints)", and
`TechArch/04-security.md` §7.6 extends that to response timing. CONTEXT adds the second half of the
ambiguity problem: *"a clerk filtering by `witness_name` and receiving zero hits would reasonably
conclude 'no such witness' rather than 'that filter isn't wired up yet.' A zero-result set must never
be ambiguous between 'nothing matched' and 'not implemented.'"* Hence the locked deviation — the API
always accepts the complete documented filter set, and reports the unsupported ones explicitly.

Output: the query path. The UI is plan 02-15.
</objective>

Enables: F5 (plan 02-15's search screen); Phases 5–8 consume the same endpoint once they register their object types
</feature_dependencies>

`postgres-search.provider.ts` — `PostgresSearchProvider.search(q)` builds **one** `$queryRaw` statement
over `platform.search_index`:

```sql
SELECT object_type, object_id, last_updated, rank, snippet, count(*) OVER () AS total_count
FROM (
  SELECT si.object_type, si.object_id, si.source_updated_at AS last_updated,
         ts_rank_cd(si.search_vector, q.tsq) AS rank,
         ts_headline('english', coalesce(si.summary,''), q.tsq,
                     'MaxFragments=1,MaxWords=25,MinWords=8') AS snippet
  FROM platform.search_index si, plainto_tsquery('english', $1) AS q(tsq)
  WHERE <SCOPE PREDICATE>            -- mandatory, first
    AND si.object_type = ANY($2)
    AND (<text match or $1 is empty>)
    AND <structured filter terms>
) ranked
ORDER BY rank DESC, last_updated DESC, object_id ASC
LIMIT $n OFFSET $m;
```

Rules the implementation must hold:
1. **The scope predicate is a `WHERE` term in the same statement that ranks.** It is never applied to a result set after ranking, and the ranked subquery is never materialized without it. `scope.always_false` short-circuits to an empty result **without executing a query**, which also keeps the timing profile of "denied" close to "no match".
2. `ORDER BY` includes `object_id ASC` as the final tiebreak so ranking is deterministic — a nondeterministic order across identical queries is itself a weak side channel and makes cursor pagination incorrect.
3. **Ranking and snippets.** `ts_rank_cd` over `search_vector`; `ts_headline` over `summary` **only**. Never over a column the projection did not already deem summary-safe — the snippet must not become a path to content the projection deliberately excluded.
4. **Trigram filters.** `identifier`, `party_name` and `witness_name` are fuzzy: `identifier % $k` and `array_to_string(party_names,' ') % $k` using the `pg_trgm` similarity operator against the GIN indexes plan 02-01 created. Combine with `similarity()` added to the rank so a close identifier match outranks a loose text match.
5. **Structured filters.** `status = $k`; `event_date >= $from`; `event_date <= $to`; `proceeding_id = $k`. Every value parameterised — no interpolation anywhere, same rule plan 02-07's translator holds.
6. **`total_count` is the count of authorized matches**, produced by the window function inside the scoped subquery. It can never include an excluded row, which is precisely the `FRD/F05` "result count hints" leak.
7. **Pagination.** Claude's-discretion decision: **offset pagination with an opaque base64 cursor** encoding `{offset, query_fingerprint}`. A cursor whose fingerprint does not match the current query is `400 SEARCH_INVALID_QUERY` — resuming a different query from an old cursor would silently mix result sets. `limit` defaults to `SEARCH_DEFAULT_PAGE_SIZE` (25) and is capped at `SEARCH_MAX_PAGE_SIZE` (100). Keyset pagination was considered and rejected: the sort key is a computed rank, so a keyset cursor would need the rank value, which changes as the index updates.
8. **Response-timing uniformity** (Claude's-discretion, §7.6). Do what is honest and cheap, and claim no more: a single query shape for every request, the scope predicate always present, `LIMIT` always applied, no early-exit branch that depends on whether rows matched, and `always_false` returning without a query so a denied scope does not take *longer* than a match. **Do not claim constant time** — record the residual as an assumption for plan 02-12's register, because full constant-time response behaviour over a shared database is not achievable here and asserting it would be false.
9. `healthy()` runs `SELECT 1 FROM platform.search_index LIMIT 1` plus an `EXISTS` check on the `pg_trgm` extension. `SearchService` maps a false result or a query failure to `503 SEARCH_INDEX_UNAVAILABLE` — which resolves the Claude's-discretion question *"what does `SEARCH_INDEX_UNAVAILABLE` mean now that Postgres is the primary provider"*: it means **this provider cannot serve queries** (table missing, extension missing, statement error), not that a separate cluster is down. Document that definition in the file and in the SUMMARY. It is deliberately distinct from `503 SECURITY_POLICY_UNAVAILABLE`, which means the scope could not be computed.

Register the provider in `SearchModule` behind a factory keyed on `SEARCH_PROVIDER` (`postgres` in
Phase 2). An unknown value must **throw at boot**, not fall back — a typo that silently selects a
different engine is the kind of failure the context-boot test exists to catch.

`SearchService.search(principal, dto)`:
1. `objectTypes = registry.activeObjectTypes()`.
2. `supported = registry.supportedFilters()`; `unsupported_filters = requestedFilterKeys.filter(k => !supported.has(k))`, sorted for determinism. 3. **Drop the unsupported filters from the provider query** rather than letting them match nothing. A filter the index cannot evaluate must not narrow the result set; narrowing on it would turn "not implemented" into "no results", which is the exact ambiguity CONTEXT forbids.
4. `scope = await scopePredicateService.predicateFor(principal, objectTypes)` — this call may throw `503 SECURITY_POLICY_UNAVAILABLE`; let it propagate unchanged.
5. `provider.search({...})`.
6. Build the response `{results, total_count, next_cursor?, unsupported_filters}` where each result is `{object_type, object_id, summary_snippet, deep_link, last_updated}` per `TechArch/03a-api-shared.md` §6.5, with `deep_link` built by the **same** `buildDeepLink` helper plan 02-03 wrote — one URL shape for notifications and search, not two.

8. Log the search through `SearchQueryLogService`.

**The empty-state identity rule**, which is ROADMAP criterion 4's teeth and must be written as a
comment on the response builder: *the response for a search that matched nothing and the response for
a search whose every match was scope-excluded are produced by the same code path with the same keys and
the same `total_count: 0`.* There is no "some results hidden" flag, no differing wording, no count
discrepancy, and no branch anywhere in this service that tests whether exclusion occurred — the service
cannot know, because the predicate was applied inside the provider's query. Plan 02-16 proof 2 asserts
byte identity.

`SearchQueryLogService.record(...)` inserts one `platform.search_queries` row per search:

`search-api.e2e-spec.ts` — US-5.1:

6. `unsupported_filters` is `[]` — present, not absent — when every requested filter is supported.
7. Pagination: 30 seeded matches with `limit=10` yields three pages whose union is the full set with no duplicates and no omissions; `total_count` is 30 on every page; reusing a page-2 cursor against a *different* query returns `400 SEARCH_INVALID_QUERY`.

11. Drop the `pg_trgm` extension (as `app_dba`), issue a search, and assert `503 SEARCH_INDEX_UNAVAILABLE`; restore it.

`search-existence-hiding.e2e-spec.ts` — assurance proofs 2 and 3, and ROADMAP criterion 4:
1. **The sealed-record proof.** A user **holding** the `sealed` entitlement searches for the seeded sealed case's distinctive caption term and gets exactly one hit. A user **without** it issues the identical query and gets `total_count: 0` and `results: []`.
2. **Indistinguishability.** Capture the unauthorized user's response body and the same user's response for a term that genuinely matches nothing (`"Zzzyzxqq"`). Assert the two bodies are **deeply equal after removing nothing** — same keys in the same order, same `total_count`, same `unsupported_filters`, same absence of `next_cursor`. Serialize both with `JSON.stringify` and assert string equality. This is the byte-identity requirement CONTEXT demands be "asserted by the assurance suite"; plan 02-16 reuses this assertion verbatim.
3. **No placeholder.** Assert the unauthorized response contains no object whose `object_id` equals the sealed case's id, and that no field anywhere in the body contains the string `"restricted"`, `"sealed"`, `"withheld"` or `"hidden"`.
4. **Count non-leak.** Seed five additional sealed cases matching the same term, re-issue the unauthorized query, and assert `total_count` is still exactly 0 — the count does not drift with the quantity of hidden matter.
5. **Multi-designation.** A user holding `sealed` but not `grand_jury` gets zero hits for a record tagged both, and one hit for a record tagged only `sealed`.

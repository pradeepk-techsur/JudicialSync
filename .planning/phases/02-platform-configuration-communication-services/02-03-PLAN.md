<objective>
Build the notification render and transport layer: a Mailpit container in the Compose stack, a real
`nodemailer` SMTP channel, an extensible channel registry, versioned code-asset templates, and the
content policy enforced **structurally first with a runtime tripwire behind it**.

Purpose: ROADMAP criterion 2 requires a notification "whose body/preview never contains party names,
exhibit descriptions, or sealed-case detail — only a generic description plus a secure deep link."
CONTEXT locks the method: *"Make the leak structurally impossible first; keep a runtime tripwire
behind it."* The Notifications Service never dereferences `object_reference` and has no read path to
case, party or exhibit content, so there is no sensitive data in the process to leak; templates render
against a closed, typed context, so a sensitive field is not merely discouraged but **will not
compile**; a CI check asserts no template escapes that context; and the runtime assertion raising
`NOTIFY_CONTENT_POLICY_VIOLATION` stays as defense in depth, a tripwire that should be unreachable.
Mailpit is the MinIO-for-S3 pattern Phase 1 established — a genuine SMTP path whose final hop is
local, inspectable by eye, and **inducibly broken**, so plan 02-11's retry/backoff/escalation is
proven rather than asserted.

Output: everything needed to render and send a policy-compliant message. Persistence, recipient
resolution, delivery-status tracking and retry are plans 02-10 and 02-11.
</objective>

`email.channel.ts` — a real `nodemailer` transport, created once at module init from

throw out of `send()`** — a throw would bypass plan 02-11's status machine and lose the delivery row's

stub — there is genuinely no transport. Marking the row `sent` is plan 02-10's job.

`deep-link.ts` exports `buildDeepLink(objectType, objectId): string` returning
`${PUBLIC_BASE_URL}/go/${objectType}/${objectId}` — **a plain application URL carrying zero authority.**
Comment the file with CONTEXT's reasoning: clicking it enters the normal authenticated flow; Phase 1's
session check plus the global OPA guard decide everything; an unauthenticated click goes to Keycloak
login with TOTP; an unauthorized click is denied and audited as an `access_attempt`. *"Requiring
re-authentication"* is satisfied because the link conveys no access by itself, and **a forwarded or
intercepted email grants nothing.** Signed single-use token links were considered and rejected: they
place a bearer credential in an email inbox, the one place content policy says sensitive things must
not go. Assert in code that the function never receives or emits a query string, fragment or token —
`buildDeepLink` throws if `objectType` or `objectId` is not a plain slug/UUID.

The `/go/:objectType/:objectId` route itself belongs to the web application (plan 02-14 wires it);

Templates. CONTEXT: **templates are versioned code assets in the repo, reviewed through normal code
review and released with the application, identical across courts.** Courts configure recipients,
channels, cadence and thresholds via F3 — not wording.

Each `templates/email/{type}.ts` exports a single function:

```typescript
import type { NotificationRenderContext } from "../../content/render-context";
import type { RenderedMessage } from "../../channels/channel.types";

export function render(ctx: NotificationRenderContext): RenderedMessage {
  const subject = `[${ctx.court_name}] Action may be required (${ctx.severity})`;
  const body_text = [ctx.type_description, "", `Open the record: ${ctx.deep_link}`,
                     "", "You must sign in to view any detail."].join("\n");
  return { subject, body_text, body_html: /* same content, minimal USWDS-free HTML */, preview_text: ctx.type_description };
}
```

Three rules bind every template and must be stated in a comment in each file:
1. The parameter type is `NotificationRenderContext`. Any other field is a compile error.
2. `preview_text` is set explicitly and is always the generic `type_description` — never the subject and never a body excerpt. Mail clients render the preview from the first body bytes otherwise, which is precisely where criterion 2's "or preview" bites.
3. No template may interpolate `object_type` or `object_id`; they exist only inside `deep_link`.

`templates/in-app/all-types.ts` renders the in-app variant for all six types from the same context.

`registry.ts` exports `TEMPLATE_VERSION = 1` and a `TemplateRegistry` whose `render(channel, ctx)`
dispatches on `(channel, ctx.notification_type)` through a `Record` typed so a missing combination is a
compile error, and whose `templateKey(channel, type)` returns `"{channel}:{type}:v{TEMPLATE_VERSION}"` —
the value plan 02-10 stores in `notifications.template_key` / `template_version`, so any rendered
message is attributable to an exact reviewed asset. Bumping `TEMPLATE_VERSION` is a code-review
decision; note that in a comment.

**Build-time check.** `apps/api/scripts/check-template-scope.ts` is the CI assertion CONTEXT requires
("A CI check asserts no template references anything outside that context"). Implement it with the
TypeScript compiler API rather than a regular expression — a regex over source text would miss
`ctx["body"]` and would false-positive on comments:

1. Create a `ts.Program` over `apps/api/src/modules/notifications/templates/**/*.ts`.
2. For every exported `render` function, assert its single parameter's type resolves to `NotificationRenderContext`.
3. Walk each function body collecting every `PropertyAccessExpression` and `ElementAccessExpression` whose base identifier is the parameter; assert each accessed property name is in `CLOSED_CONTEXT_FIELDS`.
4. Assert no template file imports anything outside `../../content/*` and `../../channels/channel.types` — in particular no Prisma client, no HTTP client, no repository.
5. Assert every template sets `preview_text` from `type_description` (an `ObjectLiteralExpression` property whose initializer is `ctx.type_description`).
6. Exit non-zero listing every violation with file and line.

`.github/workflows/content-policy.yml` is a new sibling workflow (plan 01-01 established that pattern
so each gate's failure is self-describing in the checks list). Node 20, `npm ci`, then
`npx tsx apps/api/scripts/check-template-scope.ts`. It is **release-blocking** — do not mark it
`continue-on-error`.

**Runtime tripwire.** `content-policy.guard.ts` exports
`assertContentPolicy(ctx: NotificationRenderContext, msg: RenderedMessage): void`. CONTEXT keeps this
"as defense in depth — a tripwire that should be unreachable, and whose firing is itself a critical
alert." Implement it as a **closed-set check, not a pattern scanner**, which is the distinction CONTEXT
drew when it rejected a runtime content scanner as the primary control:

- Build the set of strings the closed context legitimately permits: the five context values plus the fixed template chrome (the literal non-interpolated text of the selected template, obtained by rendering the same template against a sentinel context).
- Assert every interpolated region of `subject`, `body_text`, `body_html` and `preview_text` is accounted for by that set. Concretely: render the template a second time with each context field replaced by a unique sentinel, diff the two renders, and assert the differing regions correspond one-to-one to context fields. Anything that varies and is not a context field means a value entered the message from outside the closed context.
- On violation throw `ApiException(500, 'NOTIFY_CONTENT_POLICY_VIOLATION', 'Notification blocked: content policy violation detected')` — the exact status, code and message from `FRD/F04` Error States, which `FRD/Y2-errors.md` classifies as "reserved for internal-guard violations that should structurally never occur … must be alerted to system administrators." **Plan 02-10 catches this throw at both `assertContentPolicy` call sites and raises a `critical` `exceptions` record before re-throwing**, so the tripwire's firing is itself a durable alert as CONTEXT requires — this function does not write the record itself, because it is a pure assertion with no database access, which is the same property that keeps the whole module free of a read path to case content.
- Additionally assert `preview_text === ctx.type_description` and that `deep_link` appears at most once and carries no query string.

This is the only control that *could* fail open on an unrecognised value, and that is why it is second,
behind the type system and the CI check, not first.

`apps/api/test/notification-content-policy.e2e-spec.ts` — the proof, against the running stack:

For **every one of the six notification types and both channels**, render with a context whose `court_name` is a distinctive token, send through `EmailChannel`, and assert via `mailpitLatestFor` that the received `subject`, `text`, `html` and `snippet` contain the generic `type_description` and the deep link and **nothing else variable**. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| service→email recipient | Rendered message content crossing into an email inbox — an unsecured, forwardable, previewable destination outside the system's access control. |
| db→render | Record-derived values crossing into a template's output. |
| template author→build | Developer-authored template source crossing into the shipped delivery pipeline. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-10 | Information disclosure | A party name, exhibit description or sealed-case identifier reaching an email body or push preview | mitigate | Structural: `NotificationRenderContext` in `apps/api/src/modules/notifications/content/render-context.ts` is a closed five-field readonly interface and every template's single parameter is typed to it, so a record field will not compile; the module has no Prisma or HTTP read path (asserted by task 2's `grep`). Build-time: `apps/api/scripts/check-template-scope.ts` walks each template's AST and rejects any access outside `CLOSED_CONTEXT_FIELDS`, gated by `.github/workflows/content-policy.yml`. Runtime: `assertContentPolicy` in `content/content-policy.guard.ts` sentinel-diffs the render and throws `500 NOTIFY_CONTENT_POLICY_VIOLATION` before send. |
| T-02-11 | Information disclosure | The *preview* leaking even when the body is clean, because a mail client derives the preview from the first body bytes | mitigate | Every template sets `preview_text` explicitly to `ctx.type_description`; `check-template-scope.ts` assertion 5 enforces it at build time; `notification-content-policy.e2e-spec.ts` asserts Mailpit's `snippet` for all six types on both channels. |
| T-02-12 | Elevation of privilege | A bearer credential placed in an email inbox, granting whoever forwards or intercepts the message access to the record | mitigate | `content/deep-link.ts` emits `${PUBLIC_BASE_URL}/go/{type}/{id}` only, throws on non-slug input, and task 2's `<verify>` greps for `token`/`signature`/`hmac`/`jwt` in the file. Authorization is decided entirely by Phase 1's session check and global OPA guard when the link is followed. Signed single-use tokens were considered and rejected. |
| T-02-13 | Denial of service | An undeliverable address retried forever, or a transient SMTP outage abandoned after one attempt | mitigate | `ChannelSendResult.retryable` is derived in `channels/email.channel.ts` from the nodemailer error class and `responseCode` band, with the mapping documented on the field; `send()` never throws, so plan 02-11's status machine always receives a decision. |
| T-02-14 | Spoofing | A court's production deployment silently continuing to send through a local test relay | accept | Mailpit is selected purely by `SMTP_HOST`/`SMTP_PORT`; no code path references it. Residual risk is a deployment-configuration error, owned by the deployment target and recorded alongside Phase 1's ASM-07 in `docs/ASSUMPTIONS.md` by plan 02-12. |

<objective>
Fill and maintain the access-tagged search index: register the five Phase 2 object types, project each
into `search_index`, propagate security-designation changes **synchronously and fail-closed**, let
content changes ride the existing durable event stream, and provide an idempotent backfill.

Purpose: CONTEXT splits index staleness by risk, and the split is the whole design. *"Security-designation
and scope changes update the index access tags in the SAME transaction as the source change, and fail
closed — if the tag write fails, the designation change fails. The index can therefore never be more
permissive than reality."* Content staleness means a slightly out-of-date result; designation staleness
means a just-sealed record is still discoverable by someone who must not know it exists, which
`TechArch/04-security.md` §7.6 treats as a hard existence-hiding violation. CONTEXT also locks the
registry so Phases 5–8 add `exhibit` and `defendant_tracker` *"as an addition, with no schema migration
and no reindex of existing records."*

Output: the index is populated and stays correct. Querying it — scope pre-filter, ranking,
`unsupported_filters[]` — is plans 02-07 and 02-09.
</objective>

Implements: F5: Search Service (process step 5 — incremental index updates within a bounded staleness window; the access-tagged index itself)
Depends on: F1: Core Case and Docket Data Model (the five source tables and `security_designations`), F2: Audit Trail (the durable event stream the projector consumes)
Enables: F5 (plans 02-07 and 02-09 query what this plan maintains); Phases 5–8 register `exhibit` and `defendant_tracker` against this registry
</feature_dependencies>

`SearchIndexerService` is the only writer to `platform.search_index`:
- `upsertRows(tx, rows)` issues one `INSERT … ON CONFLICT (object_type, object_id, projection_key) DO UPDATE` per row, setting `search_vector = to_tsvector('english', coalesce(summary,'') || ' ' || coalesce(identifier,'') || ' ' || array_to_string(party_names,' ') || ' ' || array_to_string(witness_names,' '))` and `indexed_at = now()`. Upsert, never delete-then-insert — a concurrent query must never observe a missing row.
- `removeRows(tx, objectType, objectId)` deletes every projection of an object. Used only when a source row leaves scope; Phase 1 permits no hard deletes, so in practice this is unused in Phase 2. Keep it, and note why it exists.
- `reproject(tx, objectType, objectId)` resolves the projection from the registry, calls `project`, and upserts. When `tx` is null it opens its own transaction.

`DesignationTagsService.applyDesignationTags(tx, objectType, objectId)` is the fail-closed path:
1. Recompute the designation tag set for the changed object.
2. `UPDATE platform.search_index SET designation_tags = $tags WHERE …` for **every row whose visibility derives from this object** — for a `case`, that is every index row with `case_id = $caseId` across all object types, because the inheritance rule makes a case's designations flow to its parties, proceedings, docket events and document references.
3. Return the number of rows updated.
4. On **any** failure — including zero rows updated when the registry says rows should exist — throw `ApiException(500, 'SEARCH_TAG_SYNC_FAILED', 'Security designation change could not be applied to the search index')`. Because the call runs inside the caller's transaction, the throw rolls the designation change back.

Comment the method with CONTEXT's reasoning verbatim: *"if the tag write fails, the designation change
fails. The index can therefore never be more permissive than reality."* Add: **this method must never
be made async-fire-and-forget, and must never swallow an error.** A future refactor that moves it onto
the projector queue silently reintroduces the §7.6 violation.

Modify `apps/api/src/modules/case-context/designations.service.ts` (plan 01-09) so the

not touch the controller, the ABAC descriptor, or the `case_security_admin` check. Add a comment at the
call site naming this plan and the §7.6 requirement, so the coupling reads as intentional.

  <name>Task 3: Incremental projector over the durable event stream, plus an idempotent backfill</name>
  <files>apps/api/src/modules/search/indexer/projector.service.ts, apps/api/src/modules/search/indexer/projector.processor.ts, apps/api/src/modules/search/indexer/backfill.service.ts, apps/api/src/modules/search/indexer/indexer.controller.ts, apps/api/src/modules/search/search.module.ts, apps/api/test/search-projection.e2e-spec.ts</files>
  <action>
`SearchProjectorService.runOnce()` is the content-staleness half — asynchronous, bounded, and built on
the stream Phase 1 already has. **Do not create a new events table.**

1. Read `platform.search_index_cursor` (single row, id = 1) for `(last_occurred_at, last_audit_event_id)`.
2. Select the next `SEARCH_PROJECTOR_BATCH_SIZE` rows from `platform.audit_events` ordered by `(occurred_at, id)` strictly after the cursor, whose `object_type` is in `registry.sourceObjectTypes()`.
3. Reduce the batch to a distinct set of `(object_type, object_id)` — a row edited five times in one batch is reprojected once.
4. In **one transaction**: call `SearchIndexerService.reproject` for each pair, then advance the cursor to the batch's last `(occurred_at, id)`. Advancing inside the same transaction is what makes the projector crash-safe: a worker that dies mid-batch re-runs the whole batch, and `reproject` is an upsert, so re-running is a no-op.
5. Return `{processed, reprojected, lagSeconds}` where `lagSeconds` is `now() - last_occurred_at`.
6. If a single pair's projection throws, log it, raise a durable exception **through plan 02-01's `ExceptionsService`** — never a raw insert — **and continue the batch**; one malformed record must not stall the whole index. Advance the cursor past it. The durable exception is what makes the skip recoverable; a log line would not be, which is the Phase 1 reasoning that rejected log-only.

```typescript
await this.exceptions.raise(tx, {
  exception_type: "search_projection_failed",
  severity: "medium",
  object_type: objectType,
  object_id: objectId,
  court_id: null,                      // not reliably known for a failed projection
  source_module: "search",
  detail: { error: String(err), batch_cursor: cursor },
  dedupe_key: `${objectType}:${objectId}`,
});
```

`dedupe_key` is load-bearing here, not decorative: the projector runs every
`SEARCH_PROJECTOR_INTERVAL_SECONDS` (default 10), so a persistently-malformed record without
deduplication would write six rows a minute forever. `ExceptionsService` merges into the open row and
increments `occurrence_count` instead. Import `ExceptionsModule` into `SearchModule`; **do not** write
to `platform.exceptions` directly from this module, and **do not** create a second exception helper —
CONTEXT's narrow service-internal write path is a single function, and plan 02-01 already shipped it.

`projector.processor.ts` is a BullMQ repeatable job on `SEARCH_PROJECTOR_INTERVAL_SECONDS` (default 10),
registered exactly like plan 01-12's chain-verification job — same queue infrastructure, same Redis.
Guard against overlap with a job id derived from the interval so a slow run does not stack.

`SearchBackfillService.run({objectTypes?, courtId?, batchSize})` is the rebuild path, and
Claude's-discretion decision **"safe to run against live data"** resolves to: it never truncates, it

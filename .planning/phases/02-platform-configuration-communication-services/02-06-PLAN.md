<objective>
Make the immutable published snapshot the single source of truth for configuration: build
`ConfigResolver` as the only read path, materialize Phase 1's seeded defaults into published version 1
packages of both package types for both courts, and demote Phase 1's `CourtConfigService` onto the
resolver so no independently-writable second representation survives.

Purpose: CONTEXT locks all three. *"A single `ConfigResolver` service is the only read path.
`configResolver.get(courtId, key)` returns `{ value, rule_package_version_id }`."* *"The immutable
published snapshot is the single source of truth. Phase 1's flat config tables are either dropped or
demoted to resolver-owned internals — they must not remain an independently writable second
representation."* *"Phase 2 migrates Phase 1's seeded defaults into a published v1 package per court
per package type. The seed script must produce this state idempotently."* The alternative — a
denormalized "currently effective" projection written alongside the snapshot — was rejected because
two representations can silently diverge, and consumers reading the snapshot JSONB directly was
rejected because it copy-pastes effective-version logic, the same failure shape Phase 1 refused when it
kept ABAC out of per-module code.

Output: one read path, one representation, and a seed that produces the published v1 state every time
it runs. The draft/publish *write* path is plan 02-08.
</objective>

`ConfigResolver`:
- `getPackage(courtId, type)` selects the `rule_package_versions` row for `(court_id, package_type)` with `status='published'`, `published_at IS NOT NULL` and the greatest `effective_from <= now()`, tie-broken on the greatest `version_number`. This is the Claude's-discretion `effective_from` decision resolved: **future-dated publishes are permitted and simply are not yet effective** — the resolver's `<= now()` predicate is the whole mechanism, and a future-dated package becomes effective on its own without a job.
- It parses `config_snapshot` through `validateRulePackage(type, snapshot)` from `@judicialsync/config-schema`, so a malformed snapshot fails loudly at read time. Parse failure → `500 CONFIG_INVALID_SNAPSHOT`; no published package → `500 CONFIG_NOT_FOUND`. Both are internal guards per `FRD/Y2-errors.md`. **Do not fall back to defaults** — plan 01-11 already established that a silent default reintroduces hardcoded constants invisibly.
- `get(courtId, key)` looks the owning package type up in `CONFIG_KEY_OWNER`, calls `getPackage`, and returns `{value: snapshot[key], rule_package_version_id, version_number, package_type}`. Returning the version id with every read is what makes stamping "a one-liner at every call site."
- `getVersion(id)` returns any package by id, published or not — this is what keeps a **prior version retrievable** after a new publish (ROADMAP criterion 1, US-3.2).
- Caching: reuse plan 01-11's Redis pattern, keyed `config:{courtId}:{packageType}` with the same short TTL. `invalidate(courtId, type?)` clears one or both keys and **also** calls `CourtConfigService.invalidate(courtId)` so the two caches cannot disagree. Plan 02-08's publish transaction calls `invalidate` after commit.

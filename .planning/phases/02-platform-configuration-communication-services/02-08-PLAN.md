<objective>
Build the configuration write path: draft, validate, submit for approval, and publish — with the
approver derived **solely from the authenticated session** and an `approving_user_id` in the request
body **rejected**.

Purpose: this is ROADMAP criterion 1 and the locked CONTEXT deviation. `Y1a-api-shared.md` documents
`POST /config/rule-packages/{id}/publish` with body `{approving_user_id}`. CONTEXT rejects that
signature with a reason worth restating: *"That signature permits a single person to publish by naming
a colleague — attestation, not separation — leaving an audit entry crediting someone who never acted.
It contradicts `Screen-16`'s 'enabled only for the selected distinct approver's own session' and
'structurally blocked, not just rejected after click.' Phase 1's stance was 'prefer the API refuses
over the audit catches it.'"* The deviation is deliberate and must be **recorded, not silent** — plan
02-12 corrects the OpenAPI contract and the register.

Output: the full draft-to-publish lifecycle, the eligible-approver list `Screen-16`'s Select binds to,
and the separation-of-duties proof.
</objective>

DTOs use the shared schemas from `@judicialsync/config-schema` — the server does not define a second
shape. `CreateDraftDto` is `{court_id, package_type, config_snapshot?}`; when `config_snapshot` is
omitted the draft is seeded from the **currently effective package of that type**, which is how
`Screen-16` opens as "Draft v4.3" against the published v4.2.

`RulePackageService.createDraft`:
- Requires the drafter's entitlement for the package type: `config_admin` for `operational`, `security_officer` for `security_retention`, read from `APPROVER_ENTITLEMENT_BY_PACKAGE_TYPE`. Denied → `403 CONFIG_EDIT_DENIED` with `FRD/F03`'s message "You do not have configuration administration access".
- Allocates `version_number = max(version_number for (court, package_type)) + 1`.
- Inserts with `status='draft'`, `drafted_by = principal.user_id`, `published_at = NULL`, `approved_by = NULL`, `supersedes_version_id` = the currently effective version's id.
- A second concurrent draft hits plan 02-01's `uq_rule_package_single_draft` unique index. Catch `23505` and return `409 CONFIG_DRAFT_EXISTS` with the existing draft's id in `detail`, so the editor can offer to open it. **Do not** delete the other draft, and do not work around the index.
- Wrapped in `withAudit` emitting `action_type: 'config_change'`, `object_type: 'rule_package_version'`, `after_state` = the draft metadata (not the whole snapshot — a draft create is not yet a configuration change), stamped with the *currently effective* `rule_package_version_id` from `ConfigResolver`.

`saveDraft(id, {config_snapshot, expected_updated_at})` — optimistic concurrency, the
Claude's-discretion draft-lifecycle decision made explicit: the `PUT` carries the `updated_at` the
client last read; a mismatch is `409 CONFIG_DRAFT_CONFLICT` carrying the server's current
`updated_at`. Two admins editing the same draft must not silently overwrite each other, and
`Screen-16`'s autosave indicator makes that otherwise easy. Only the draft's own row is written; no
definition tables, no `notification_recipients_config` — **materialization happens at publish only**,
which is what keeps CONTEXT's "no unversioned, non-maker-checkered path" true.

`validateDraft(id)` returns `validateRulePackage(package_type, config_snapshot)` as
`{ok, issues[]}` with **HTTP 200 even when invalid**. This endpoint is the editor asking "is this
draft valid?"; a 422 would be the wrong shape for a question. Publish is where invalidity becomes an
error. Say so in a comment, because the asymmetry is deliberate.

`discardDraft(id)` deletes the draft row — permitted by plan 02-01's trigger precisely because
`status='draft'`. A publish-status row returns `403 CONFIG_IMMUTABLE`. Audit the discard.

Controller routes per the `provides` contract. Every route carries
`@Resource({type:'court_config', action:'create'|'update'})` with the route's `court_id`/`id` param
named, so Phase 1's global guard performs the court-scope check — **no per-route authorization code**.
`GET /config/rule-packages/{court_id}/draft?package_type=` returns the open draft or `404`.

Register `RulePackageService` and the controller in `ConfigModule`.

  <files>apps/api/src/modules/config/rule-package.service.ts, apps/api/src/modules/config/rule-package.controller.ts, apps/api/src/modules/config/approver-lookup.service.ts, policy/judicialsync/authz/rbac.rego, policy/judicialsync/authz/sod.rego, policy/judicialsync/authz/config_publish_test.rego</files>

`submitForApproval(id, approverUserId)` records **who may approve**, mirroring `Screen-16`'s approver
Select. It sets `submitted_by = principal.user_id`, `submitted_for_approval_at = now()` and stores the
nominated approver. It does **not** approve anything. Reject `approverUserId === drafted_by` here with
`422 CONFIG_SOD_VIOLATION` so the editor cannot even nominate the drafter — `Screen-16`'s Select
"excludes current user", and the server must not depend on the client honouring that.

`publish(id, effectiveFrom?)` is the heart of the plan. The signature takes **no user id**, and that is
the whole point:

1. **Reject an approver in the body.** Before anything else, if the request body contains
   `approving_user_id` (or any key matching `/approv(er|ing)_user_id/`), return
   `400 CONFIG_APPROVER_IN_BODY` with message *"The approver is determined by the authenticated
   session; approving_user_id is not accepted."* `Y1a-api-shared.md` documents that field; Phase 2
   deliberately refuses it, and refusing loudly is what makes the deviation discoverable rather than a
   silently ignored field. Implement the check in the controller against the raw body, not the parsed
   DTO — a DTO that strips unknown keys would make the rejection unreachable.
2. **Approver = `principal.user_id`, always.** There is no other source.
3. **Self-approval → `403 CONFIG_SOD_VIOLATION`** with `FRD/F03`'s message "A second approver is
   required to publish this configuration". The decision comes from the OPA policy (below); the
   service applies it.
4. **Entitlement for the package type** — `config_admin` for operational, `security_officer` for
   security/retention, from `APPROVER_ENTITLEMENT_BY_PACKAGE_TYPE`. Denied → `403 CONFIG_EDIT_DENIED`.
5. **Re-validate the snapshot server-side** with `validateRulePackage`, regardless of what the client
   reported. Issues map to `422` with the issue's own `error_code` (`CONFIG_THRESHOLD_GAP`,
   `CONFIG_AMBIGUOUS_MAPPING`, `CONFIG_INVALID_STRUCTURE`) and the full `issues[]` in `detail`.
6. **One transaction** containing, in order: flip `status` to `'published'`, set `approved_by`,
   `published_at = now()` and `effective_from = effectiveFrom ?? now()`; insert the
   `rule_package_approvals` row with `drafted_by`, `approved_by` and `approver_session_id = principal.session_id`;
   call `SnapshotMaterializerService.materialize(tx, id)`; and write the audit row through `withAudit`
   with `action_type: 'config_change'`, `before_state` = the superseded version's snapshot,
   `after_state` = the new snapshot, and `rule_package_version_id` = the **new** version's id. The
   before/after diff and both identities are US-3.2's third acceptance criterion; `approved_by` plus the
   approval row supply the second identity.
7. **After commit** (never inside the transaction), call `ConfigResolver.invalidate(court_id, package_type)`.
8. Return the published version.

Add a comment at the top of `publish` stating, in one sentence, that **nothing in this method
recalculates anything**: `FRD/F03` step 7 and `Screen-16`'s note require that in-flight calculations
referencing a prior version are not retroactively recalculated, and the way that is guaranteed is that
publish touches no artifact outside the configuration tables. A future contributor adding a
"recalculate affected trackers" call here would break criterion 1.

`ApproverLookupService.eligibleApprovers(courtId, packageType, excludeUserId)` returns users holding
the required entitlement **in that court**, excluding `excludeUserId`, resolved through plan 01-06's
entitlement resolution rather than by reading `user_roles` directly. Exposed as
`GET /config/rule-packages/{id}/eligible-approvers`, which `Screen-16`'s Select binds to.

`config-draft-publish.e2e-spec.ts` — ROADMAP criterion 1 as a sequence:
1. `court_admin` creates an operational draft seeded from the effective package; the response has `status: 'draft'`, `version_number: 2`, and `supersedes_version_id` equal to v1's id.
2. Saving a draft whose thresholds carry the `Screen-16` gap, then calling `POST …/validate`, returns `200 {ok:false}` with one `CONFIG_THRESHOLD_GAP` issue whose `path` addresses the offending row.
3. Attempting to publish that draft returns `422 CONFIG_THRESHOLD_GAP` — validation is enforced server-side at publish regardless of the client.
4. Correcting the thresholds, submitting to a distinct `system_admin` holding `config_admin`, and publishing **in that user's own session** returns 200; the response has `status:'published'`, a `published_at`, an `effective_from`, and `approved_by` equal to the approver.
5. **The prior version remains retrievable**: `GET /config/rule-packages/{v1Id}` returns v1 with its original snapshot, and `GET …/versions` lists both newest-first. This is criterion 1's second clause and assurance proof 5.
6. `GET …/effective?package_type=operational` now returns v2, and `ConfigResolver.get(court,'thresholds')` returns the corrected tiers with v2's id.
7. **No retroactive recalculation**: write an artifact stamped with v1 before publishing (an `audit_events` row with `rule_package_version_id = v1`), publish v2, and assert the artifact's stamp is still v1 and no new row references it. This is the other half of assurance proof 5.
8. `notification_recipients_config` and `threshold_defs` now carry v2's `rule_package_version_id`; the v1-derived recipient rows are gone while v1's snapshot still contains them.
9. A `PUT` with a stale `expected_updated_at` returns `409 CONFIG_DRAFT_CONFLICT`.
10. A second `POST /config/rule-packages` for the same court and package type while a draft is open returns `409 CONFIG_DRAFT_EXISTS` naming the open draft.
11. Attempting to `PUT` or `DELETE` the **published** v2 returns `403 CONFIG_IMMUTABLE`.
12. A security/retention draft published by a `config_admin` who is not a `security_officer` returns `403 CONFIG_EDIT_DENIED`; the same draft published by the seeded `security_officer` succeeds.

`config-sod.e2e-spec.ts` — assurance proof 4, four assertions and nothing else, so the file reads as the
evidence it is:
1. The drafter publishing their own draft returns **403 `CONFIG_SOD_VIOLATION`**, and the draft's `status` is still `'draft'` afterwards.
2. Publishing with a body containing `{"approving_user_id": "<the approver's id>"}` **while authenticated as the drafter** returns `400 CONFIG_APPROVER_IN_BODY` — the field is rejected, not honoured, and certainly not used to credit the named user.
3. Publishing with the same body **while authenticated as the approver** also returns `400 CONFIG_APPROVER_IN_BODY` — the field is refused regardless of who sends it, so no client can come to depend on it.
4. Publishing with no body field, authenticated as the distinct approver, succeeds; the resulting `rule_package_approvals` row has `approved_by` equal to that user and `approver_session_id` equal to that user's live session id. Assert the session id matches a row in `platform.sessions` with `revoked_at IS NULL` at publish time — this is what "acted in their own authenticated session" means operationally, and it is the clause `Y1a`'s signature cannot express.

Add a file-header comment in `config-sod.e2e-spec.ts` naming it as the evidence for ROADMAP criterion 1's
"requiring a second approver" clause and for assurance proof 4, and citing the deviation from

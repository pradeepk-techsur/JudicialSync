<objective>
Create `@judicialsync/config-schema`, the one place structural configuration validation lives, and
declare the complete Phase 2 dependency surface in a single plan so no two later plans edit a
`package.json` at the same time.

Purpose: `UX-Mockup/Screen-16` asks for "client-side pre-validation [that] mirrors server rules."
"Mirrors" is the two-implementations-that-drift shape Phase 1 refused when it kept ABAC out of
per-module code, and CONTEXT locks the alternative: **structural validation lives once, in a shared
`zod` package in the monorepo, imported by both the NestJS server and the React client.** The editor
then gives immediate inline feedback with no possibility of disagreeing with the server at publish
time. Error codes are defined alongside the rule that raises them, so a new rule cannot ship without
its code.

Output: a dependency-free, browser-safe validation package with its own unit tests, wired into the
npm workspace and declared as a dependency of both applications.
</objective>

Enables: F3 (plans 02-06, 02-08 server-side; plan 02-13 client-side)
</feature_dependencies>

`thresholds.ts`. `Screen-16`'s Thresholds tab is tiered — `Tier | Min (days) | Max (days) | Severity` —
while `ThresholdDef` is flat `{threshold_type, value, unit}`. Model a tier set as the authoring shape
and keep the flat `ThresholdDef[]` as the stored projection:

```typescript
export const thresholdTierSchema = z.object({
  threshold_type: z.string().min(1),           // e.g. "speedy_trial_remaining_days"
  tier_name: z.string().min(1),                // "Safe" | "Approaching" | "Critical" — court-chosen
  min_value: z.number().nonnegative(),         // FRD: thresholds must be non-negative
  max_value: z.number().nonnegative().nullable(),  // null = unbounded (Screen-16 shows ∞)
  unit: z.string().min(1),
  severity: z.enum(["info", "warning", "critical"]),
});
```

`thresholdSetSchema` is `z.array(thresholdTierSchema).superRefine(...)` implementing **contiguity and
non-overlap per `threshold_type`**, which is `FRD/F03` Validation ("where tiered … must be internally
ordered without gaps that would leave a value range unclassified") and US-3.3:
1. Group by `threshold_type`; sort each group by `min_value`.
2. Exactly one tier per group may have `max_value === null`, and it must be the highest.
3. For consecutive tiers, `previous.max_value` must equal `next.min_value` — no gap, no overlap. The `Screen-16` example (`Approaching` max 30, `Safe` min 31) is a **gap of 30–31**, exactly as the mockup's warning says; use half-open `[min, max)` semantics so adjacency means equality, and state that choice in a comment and in the package README section of `index.ts`.
4. Any violation emits `{ error_code: CONFIG_THRESHOLD_GAP, message: "Threshold tiers must be contiguous and non-overlapping", path: ["thresholds", index] }`.

`workflow-states.ts`. `workflowStateSetSchema` groups by `object_type` and refines, per `FRD/F03`
Validation and US-3.1:
1. **At least one terminal state** — a state whose `allowed_transitions` is empty. None → `CONFIG_INVALID_STRUCTURE` with message "Workflow state sets must have at least one terminal state and no unreachable states".
2. **No unreachable states** — walk the transition graph from the declared `initial_state` (add an `initial_state` field per object type group; it is part of the authoring shape, not of `WorkflowStateDef`). Any state not reached emits `CONFIG_INVALID_STRUCTURE` with its own `path` pointing at the offending row.
3. Every name in `allowed_transitions` must name a declared state; a dangling transition is `CONFIG_INVALID_STRUCTURE`.

`event-mappings.ts`. `eventMappingSetSchema` refines per `FRD/F03` and US-3.3: **no `source_event_code`
may appear with two different `internal_category` values within the same package.** Duplicate code with
the *same* category is allowed (it is redundant, not ambiguous). Violation emits
`{ error_code: CONFIG_AMBIGUOUS_MAPPING, message: "Event code {code} is mapped to multiple categories", path: ["event_mappings", index] }`
with `{code}` substituted. Also require at least one of `source_event_code` or
`source_event_description_pattern` to be present, and validate that a supplied pattern compiles as a
regular expression — an uncompilable pattern is `CONFIG_INVALID_STRUCTURE`, not a runtime crash in
Phase 7's ingestion.

`numbering.ts` validates `{ prefix_pattern, sequence_reset_rule }`: a non-empty prefix pattern whose
placeholders are drawn from a closed set (`{court_code}`, `{case_number}`, `{party_initials}`,
`{sequence}`), and `sequence_reset_rule` from `z.enum(["never","per_case","per_proceeding","annually"])`.
An unknown placeholder is `CONFIG_INVALID_STRUCTURE`.

`security-retention.ts` covers the second package type — the tables Phase 1 created and seeded:
`security_policies` (`{designation, required_entitlement}` over the five designations from
`Y0a-schema-shared.md`), `retention_schedules`
(`{record_category, retention_period_days (positive int), disposition_action}`), `file_type_allowlist`
(non-empty array of lowercase extensions), and `session`
(`{access_token_ttl_seconds, refresh_token_ttl_seconds, idle_timeout_minutes, claim_cache_seconds, concurrent_session_limit}`)
plus `max_upload_bytes` — the exact field names in plan 01-11's `EffectiveCourtConfig` contract, so
plan 02-06 can demote `CourtConfigService` onto the resolver without reshaping anything.

`notification-recipients.ts` covers the F4 surface courts configure through F3 (CONTEXT: "Courts
configure recipients, channels, cadence and thresholds via F3 — not wording"):

```typescript
export const notificationRecipientSchema = z.object({
  notification_type: z.enum(["exception_raised","reconciliation_discrepancy","custody_unacknowledged",
                             "threshold_crossed","approval_needed","config_changed"]),  // TechArch 03a §6.5
```

with `max_attempts ≥ 4` because `FRD/F04` requires "retried at least 3 times … before being marked
`failed`" and the first send is attempt 1.

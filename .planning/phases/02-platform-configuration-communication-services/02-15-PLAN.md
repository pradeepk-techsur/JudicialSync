<objective>
Add the persistent USWDS header search input and the dedicated results page with the full documented
filter panel — and make the zero-results empty state **identical** whether a search matched nothing or
matched only records outside the requester's scope.

Purpose: ROADMAP criterion 4 is about what a user *sees*, so it has to be true in the browser, not only
in the API. CONTEXT locks both halves of the presentation: *"The zero-results empty state renders
identical text, layout and count regardless of whether records were scope-excluded. No 'some results
hidden', no count discrepancy, no differing wording. This identity is asserted by the assurance suite,
per §7.6."* And, pointed the opposite way: *"Entirely separate from it, a USWDS Alert states which
requested filters are not searchable in this deployment. This leaks nothing — it is a property of the
query shape, not of the data. The two notices must be visually distinct enough that nobody reads the
capability notice as 'results were withheld.'"* `UX-Mockup/00-overview.md` principle 5 states the same
rule for lists: *"Sealed/restricted records the viewer cannot access are omitted entirely from lists and
search — never shown as a greyed-out or 'restricted' placeholder row."*

Output: the search surface, with Playwright coverage that asserts the empty-state identity in a real
browser and the axe gate extended to the third and final Phase 2 screen.
</objective>

`HeaderSearch.tsx` — a USWDS Search component (`usa-search`) in the shell header, with a labelled input
(`aria-label="Search cases, parties, proceedings and docket events"`) and a submit button. On submit it
navigates to `/search?query_text={value}`. **No type-ahead, no suggestion dropdown, no on-change
request** — write a comment stating that CONTEXT rejected type-ahead on §7.6 timing-side-channel and
per-keystroke-OPA-cost grounds, so a future contributor does not "improve" it back in. Place it in
`AppShell.tsx` beside the notification bell so it is present on every authenticated screen.

`useSearch(params)` — a TanStack Query against the generated `GET /search` operation, keyed on the full
parameter set, with `keepPreviousData` so paging does not blank the list. It returns
`{results, totalCount, nextCursor, unsupportedFilters, isLoading, error}`. It performs **no client-side
filtering, sorting or deduplication of results** — every one of those would be a post-filter over a
pre-filtered set, and the server already guarantees the ordering and the count. Write that as a comment;
it is the client-side echo of `FRD/F05`'s ranked-then-filtered prohibition.

`SearchFilterPanel.tsx` — the **complete documented filter set**, always rendered regardless of what
this deployment can evaluate: `identifier`, `party_name`, `witness_name`, `status`, `date_from`,
`date_to`, `proceeding_id`, alongside `query_text`. CONTEXT: the API always accepts the full set *"so
the request contract never changes across phases and generated clients never disagree with the server"* —
and the panel follows, so a clerk's muscle memory does not change when Phases 5–8 land. A filter the
deployment cannot evaluate is **not** hidden and **not** disabled; it is submitted, and the response's
`unsupported_filters` explains it. Hiding it would substitute one ambiguity for another.
Use USWDS form components with explicit labels and a date-range fieldset with a legend.

Submitting the panel updates the URL query string so a search is linkable and the back button works.

`SearchResultList.tsx` renders each result as a USWDS row: an object-type `Tag` (`case`, `party`,
`proceeding`, `docket event`, `document`), the `summary_snippet` with its `ts_headline` emphasis
rendered as `<mark>` (sanitised — see the threat model; never `dangerouslySetInnerHTML`), a relative
`last_updated`, and a link to `deep_link`, which resolves through plan 02-14's `/go/` route so search
and notifications share one link shape. Above the list, render the count as
`{total_count} results` — the server's count, unmodified.

**No placeholder rows, ever.** Add a comment on the list component: a result the viewer may not see is
simply absent from `results`; there is no "restricted" row type in this component, and adding one would
violate `UX-Mockup/00-overview.md` principle 5 and `FRD/F05` step 4.

Paging uses `next_cursor`; a "Load more" button appends. `400 SEARCH_INVALID_QUERY`,
`400 SEARCH_PAGINATION_REQUIRED`, `503 SEARCH_INDEX_UNAVAILABLE` and `503 SECURITY_POLICY_UNAVAILABLE`
each render through `ApiErrorAlert` with the server's message. The two `503`s must render as **errors**,
never as an empty result — an empty list on policy failure would silently hide everything.

`routes.tsx` gains `/search` → `SearchPage` inside `AppShell` behind `RequireSession`. The inbound path
is the persistent header input, present on every authenticated screen, which satisfies the Navigation
Map invariant without a side-nav item; add one only if the header input is not rendered on some screen.

`SearchEmptyState.tsx` is the component ROADMAP criterion 4 ultimately rests on. Its contract is a
**negative** one, and the component signature enforces it:

```tsx
// This component takes NO prop derived from scope exclusion. It cannot know whether records were
// excluded, and it must not become able to know. The server cannot tell the client either: the scope
// predicate is applied inside the ranking query, so "nothing matched" and "everything that matched was
// outside your scope" are the same response.
//
// TechArch/04-security.md 7.6 and UX-Mockup/00-overview.md principle 5. Asserted byte-for-byte by
// apps/web/e2e/search.spec.ts and by the plan 02-16 assurance suite.
export function SearchEmptyState({ queryText }: { queryText?: string }) { ... }
```

It renders one informational USWDS Alert: a fixed heading ("No results"), one fixed sentence, and a
short list of fixed suggestions (check spelling, broaden the date range, remove a filter). The only
variable is the echoed `queryText`. There is no branch, no conditional sentence and no count other
than the zero the page already renders. A reviewer must be able to see at a glance that this component
cannot say two different things.

`SearchPage.tsx` renders `SearchEmptyState` **whenever `total_count === 0`**, with no other condition
and no other empty rendering path anywhere in the page.

`UnsupportedFiltersNotice.tsx` is the deliberately-different one. It renders only when
`unsupported_filters.length > 0`, as a USWDS **warning** Alert (distinct variant, distinct icon,
distinct heading) placed **above the result region** — not inside it and not adjacent to the empty
state — reading:

> **Some filters are not searchable in this deployment.** `{Witness name}` was not applied. Results
> below reflect your other criteria.

Map each machine code to a human label from a frozen table. The wording must make the cause
unmistakably the *query shape*, never the data; the mapping and the "was not applied" phrasing are what
stop a clerk reading it as "results were withheld". Put that reasoning in a comment.

Both notices can appear together — an unsupported filter *and* zero results — and in that case the page
reads "Some filters are not searchable… / No results", which is exactly the truthful combination.
Assert that composition in the Playwright spec rather than special-casing it in code.

Add to `SearchPage.tsx` a single place where both notices and the result list are composed, so a reader
can verify the full set of rendering outcomes in one function: `{error}` → `ApiErrorAlert`;
`{unsupportedFilters.length > 0}` → notice; `{totalCount === 0}` → empty state; otherwise the list.
Nothing else.

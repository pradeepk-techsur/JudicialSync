<objective>
Build the **named Phase 2 assurance suite** — seven proofs, separately runnable, release-blocking,
mirroring Phase 1's negative-path suite.

Purpose: CONTEXT makes this an explicit deliverable rather than developer discretion, and gives the
reason: *"Phase 2's guarantees are all negative ones, and negative guarantees are precisely what quietly
stop being true."* A content policy that leaks nothing, a search that reveals nothing, an approval that
cannot be self-granted, an alert that is never dropped — none of these produce a visible symptom when
they break. A feature test asserts that a feature works; an assurance proof asserts that a guarantee
still holds, and it is the only thing standing between a silent regression in Phase 5 and a sealed
matter appearing in a clerk's search results.

Output: the seven enumerated proofs, a machine-checked traceability matrix, and a blocking CI gate.
</objective>

<feature_dependencies>
Implements: F3: Configuration Engine, F4: Notifications Service, F5: Search Service — the evidence that each one's negative guarantees hold
Depends on: F3, F4, F5 (every Phase 2 plan)
Enables: None — this is the phase's terminal deliverable; Phases 3–8 keep it green
</feature_dependencies>

**Proof 1 — content policy.** CONTEXT: *"every notification type, rendered for a case with a
distinctive party name, leaks none of it. Asserted against **the message Mailpit actually received**,
not the in-memory render, and covering subject, body and preview text for every channel."*

Build it as a table-driven test over **the cross product of all six `notification_type` values and both
channels** — twelve cases, generated from the enum, so a seventh type added in Phase 5 without a
template fails here:
1. Purge Mailpit. Trigger the notification with `object_reference` pointing at the case carrying `seedIds.distinctivePartyName`, at severity `critical` (the widest template path).
2. Run the delivery worker.
3. For the email channel, `mailpitLatestFor(recipient.email)` and assert `subject`, `text`, `html` and `snippet` each contain **none** of: the distinctive party name, the case caption, the case number, the sealed caption term, the raw `object_id`, or the string `"sealed"`.
4. Assert each **does** contain the generic `type_description` for that type and a deep link matching `^https?://[^?#]+/go/[a-z_]+/[0-9a-f-]{36}$`.
5. For the in-app channel, fetch `GET /notifications/my` as the recipient and apply the identical assertions to `type_description`, `deep_link` and every string field of the item — the inbox is a channel and is bound by the same policy.
6. A final case: trigger for the **sealed** case and assert the same, since the sealed matter is where a leak would matter most.

**Proof 2 — search existence hiding.** CONTEXT: *"an unauthorized user searching for a sealed record's
distinctive term returns zero hits, with result count, response shape and empty-state text
indistinguishable from a genuinely empty search."*
1. As a user **holding** the `sealed` entitlement, search `seedIds.sealedCaptionTerm`; assert exactly one hit.
2. As a user **without** it, the identical request returns `200` with `total_count: 0`, `results: []`, `unsupported_filters: []` and **no** `next_cursor`.
3. Issue a search for a term matching nothing (`"Zzzyzxqq"`) as the same unauthorized user; assert `JSON.stringify` of both response bodies is **exactly equal**, and that the HTTP status and the set of response header names are equal too.
4. Seed five more sealed cases matching the term as `app_dba`, reindex, and assert the unauthorized `total_count` is still exactly 0 — the count does not drift with hidden volume.
5. Search the party name and the docket-event description belonging to the sealed case; assert zero hits for the unauthorized user — the matter's children are hidden with it.
6. A record tagged `sealed` **and** `grand_jury` returns zero hits for a user holding only `sealed`.
7. Assert **no** `audit_events` row with `action_type='access_attempt'` was created by any search in this proof — the operational `search_queries` record is the trail, and a per-search `access_attempt` would itself materialize a count of sealed matter.
8. Assert the unauthorized response body contains none of `"restricted"`, `"sealed"`, `"withheld"`, `"hidden"`, or the case id.
9. Stop OPA, flush Redis, search: assert `503 SECURITY_POLICY_UNAVAILABLE`, **not** an empty result. Restart OPA. An empty result on policy failure would be the indistinguishability guarantee working against us.

**Proof 3 — cross-court isolation**, using Phase 1's two seeded courts:
1. As a court-A user, search `seedIds.crossCourtTerm`; assert every hit's resolved record belongs to court A and the court-B record's id appears nowhere in the body.
2. The mirror assertion as a court-B user.
3. Repeat for each registered object type — `case`, `party`, `proceeding`, `docket_event`, `document_reference` — by filtering to each type, so isolation is proven per projection rather than only on the aggregate.
4. A court-A user requesting `GET /config/rule-packages/{courtB}/effective` is denied, and `GET /notifications/{id}/deliveries` for a court-B notification is denied — isolation is not only a search property.
5. A court-A user's `search_queries` rows carry `court_id` = court A; none carries court B.

**Proof 4 — configuration separation of duties.** CONTEXT: *"a drafter cannot publish their own draft
(`403 CONFIG_SOD_VIOLATION`), and publication succeeds only when a second user acts in their own
authenticated session. An `approving_user_id` in the request body is rejected, not honoured."*

2. Publishing with `{"approving_user_id": "<approver id>"}` **as the drafter** returns `400 CONFIG_APPROVER_IN_BODY`; the draft is still unpublished and **no** `rule_package_approvals` row exists.
3. The same body **as the approver** also returns `400` — the field is refused regardless of sender, so no integration can come to rely on it.
4. Publishing with no such field, as the distinct approver, returns `200`; the `rule_package_approvals` row's `approved_by` is that user and its `approver_session_id` matches a `platform.sessions` row that was unrevoked at publish time. Assert the session row directly with `appRwClient` — this is what "acted in their own authenticated session" means operationally, and it is the clause the documented `Y1a` signature cannot express.
5. **Database backstop.** As `app_rw`, attempt a direct `INSERT INTO platform.rule_package_approvals` with `drafted_by = approved_by`; assert SQLSTATE `23514`. The guarantee survives the API being bypassed.
6. A `config_admin` who is not a `security_officer` publishing a **security/retention** package returns `403 CONFIG_EDIT_DENIED`; the seeded `security_officer` succeeds. Two package types, two approver entitlements.
7. The `config_change` audit row for the successful publish carries both identities and a before/after snapshot, and is stamped with the **new** `rule_package_version_id`.

**Proof 5 — configuration immutability and no silent recalculation.** CONTEXT: *"a prior rule package
version remains retrievable after a new publish, and in-flight artifacts referencing it are not
retroactively recalculated."*
1. Capture v1's snapshot. Publish v2 with different thresholds.
2. `GET /config/rule-packages/{v1Id}` still returns v1 with its **original** snapshot, byte-identical to the capture.
3. `GET /config/rule-packages/{court}/versions` lists both, newest first, each with its drafter and approver.
4. **In-flight artifacts.** Before publishing v2, create an artifact stamped with v1 — an `audit_events` row written through a real audited action carrying `rule_package_version_id = v1`. After publishing v2, assert that row's stamp is **still** v1, its `row_hash` is unchanged, and no new row references it.
5. `ConfigResolver.get(court,'thresholds')` now returns v2's values with v2's id, while the v1-stamped artifact remains explainable through `getVersion(v1Id)`.
6. **Database backstop.** As `app_rw`, attempt `UPDATE platform.rule_package_versions SET config_snapshot='{}' WHERE id = v1Id` and a `DELETE` of the same row; assert both raise SQLSTATE `42501`.
7. The chain-verification job reports `verified: true` after all of the above — the provenance stamping did not disturb the audit chain.

**Proof 6 — delivery failure handling.** CONTEXT: *"an induced SMTP failure retries with the configured
backoff, transitions to `failed`, writes an `exceptions` record, and escalates to a secondary recipient
once the cadence is backdated past its window."* Run it as **one continuous scenario**, because that is
the chain criterion 3 describes:
1. `mailpitSetFailureMode(true)`. Trigger a `threshold_crossed`/`critical` notification whose court configuration carries both an `escalation_cadence_minutes` and an `escalation_recipient_role`.
2. Drive the delivery worker through the configured attempts, advancing the clock between them. Assert `attempt_count` increases by one per run, that each `next_attempt_at` gap grows per the configured multiplier (within the jitter band), and that at least three retries occur after the first failure — `FRD/F04`'s minimum.
3. At exhaustion assert `status='failed'` with `failed_at` set.
4. Assert exactly one `platform.exceptions` row with `exception_type='notification_delivery_failed'`, `status='open'`, severity mapped from `critical`, `source_module='notifications'`, and a `detail` containing `attempt_count` and `last_error` and **not** the distinctive party name.
5. `mailpitSetFailureMode(false)`. `backdateEscalation(deliveryId, cadence + 1)`. `runSweep()`.
6. Assert a new `notification_deliveries` row exists for the configured secondary recipient with `is_escalation=true` and `escalation_source_delivery_id` pointing at the failed one, and that the original now has `escalated_at` set.
7. Run the worker; assert `mailpitLatestFor(secondaryRecipient.email)` returns a message, and apply proof 1's full content-policy assertions to it — **an escalation must not leak what the original could not**, and the secondary recipient may hold different entitlements.
8. `runSweep()` twice more; assert no further escalation rows — idempotent.
9. Assert the escalation row's own `escalation_due_at` is null, so chains terminate.
10. **A failed delivery still escalates.** State that explicitly in a test title: the alert is not dropped merely because the primary channel broke. That is the sentence criterion 3 is made of.

<objective>
Carry the `rule_package_version_id` provenance stamp through the TypeScript audit write path, and make
the canonical hashed field list explicit and versioned on the application side so Phase 1's
integrity-verification job keeps reporting a verified chain across the migration boundary.

Purpose: CONTEXT locks the stamp — *"Every durable derived artifact also carries the stamp as later
phases create them… The resolver returns the version ID, so stamping is a one-liner at every call
site"* — and names the constraint the implementer must solve: *"`audit_events` is hash-chained. The
canonical hashed field list must be made explicit and itself versioned, rather than implicitly 'all
columns', or the Phase 1 integrity-verification job will report a false chain break across the
migration boundary. Pre-existing rows must continue to verify under the field list in force when they
were written."* Plan 02-01 shipped the SQL half; this plan ships the TypeScript half and the parity
proof that the two agree byte-for-byte, which is the only thing standing between a provenance column
and a system-wide false `integrity_alert`.

Output: a versioned canonical payload builder, a stamped write path, a verifier that dispatches per
row, and tests that prove a mixed-version chain verifies.
</objective>

```typescript
export type HashFieldListVersion = 1 | 2;
export const CURRENT_HASH_FIELD_LIST_VERSION: HashFieldListVersion = 2;

// Order is the hash definition. Never reorder.
export const HASH_FIELD_LIST_V1 = [
  "actor_id", "action_type", "object_type", "object_id",
  "before_state", "after_state", "rule_version_ref", "calculation_version_ref",
  "client_ip", "session_id", "occurred_at",
] as const;

// v2 is a STRICT EXTENSION of v1: the same fields in the same order, then the two new ones,
// then prev_hash — mirroring platform.compute_audit_row_hash_v2 exactly.
export const HASH_FIELD_LIST_V2 = [
  ...HASH_FIELD_LIST_V1, "rule_package_version_id", "hash_field_list_version",
] as const;
```

`ChainVerifierService.verify()` currently recomputes every row with one payload builder. Change it to
read each row's `hash_field_list_version` and dispatch:

```typescript
const expected = computeRowHash(row, row.prev_hash, row.hash_field_list_version as HashFieldListVersion);
```

Three behaviours matter and must be explicit:
1. A row whose `hash_field_list_version` is neither 1 nor 2 produces a break of a **new kind**, `'unknown_hash_field_list'`, added to the `ChainVerificationResult.breaks[].kind` union alongside `'row_hash_mismatch'`, `'prev_hash_mismatch'` and `'chain_head_mismatch'`. It must never be skipped or treated as verified — an unrecognised version is exactly how a tamper would try to make itself unverifiable.
2. The `prev_hash` linkage check is **version-independent**: row *n*'s `prev_hash` must equal row *n−1*'s stored `row_hash` regardless of which field list either used. This is what makes the chain survive the migration boundary at all.
3. The `integrity_alerts` record written on a break now includes the offending row's `hash_field_list_version` in its detail, so an operator can tell a genuine tamper from a version-dispatch defect.

Write `apps/api/test/audit-field-list-migration.e2e-spec.ts` against a Testcontainers Postgres:

1. **Mixed-chain verification.** Build a chain of six rows: three written with `hash_field_list_version = 1` and v1 hashes (insert them with the trigger's insert-version check temporarily satisfied by seeding them as `app_dba` before the v2 requirement applies, mirroring how real pre-migration rows exist), then three written normally through `AuditService` at version 2 — the fourth row's `prev_hash` being the third row's `row_hash`. Run `ChainVerifierService.verify()` and assert `verified === true` and `breaks.length === 0`. **This is the test that proves CONTEXT's "false chain break" does not occur.**
2. **Genuine tamper still detected.** As `app_dba`, overwrite one v1 row's `before_state`. Re-run `verify()` and assert exactly one break of kind `'row_hash_mismatch'` naming that row — the v1 path must still be a real check, not a pass-through.
3. **Genuine tamper in the v2 region** likewise produces exactly one `'row_hash_mismatch'`.
4. **Unknown version.** As `app_dba`, set one row's `hash_field_list_version` to 99. Assert `verify()` returns `verified === false` with a break of kind `'unknown_hash_field_list'`, and that an `integrity_alerts` row at `critical` severity is written carrying the version in its detail.
5. **Stamp round-trip.** Write an audit row through `withAudit` with a real `rule_package_version_id`, read it back through the Audit Explorer, and assert the version id and resolved `version_number` appear — proving the stamp is both hashed and queryable.

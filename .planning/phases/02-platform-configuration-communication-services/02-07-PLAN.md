<objective>
Derive the search scope pre-filter from OPA partial evaluation of the same Rego policy the Phase 1
global guard uses, compile the returned residual into a parameterised SQL predicate, cache it in Redis
without weakening Phase 1's immediate-revocation guarantee, and fail closed when policy is unavailable.

Purpose: CONTEXT locks this and explains the cost it accepted. *"The pre-filter predicate comes from
OPA partial evaluation. Call OPA's Compile API (`POST /v1/compile`) with the resource attributes
declared as unknowns; OPA partially evaluates the same Rego policy the Phase 1 global guard uses and
returns residual conditions, which the `SearchProvider` compiles into a query predicate."* The simpler
option — resolving the scope set from Identity and filtering on tags — was rejected despite being
easier, because **one policy source of truth** is the Phase 1 constraint applied to search, and a
second ABAC implementation in TypeScript or SQL is a second thing that can be wrong. `FRD/F05` step 3
and its Validation section require the scope be a mandatory pre-filter "before relevance ranking, not
after", because a ranked-then-filtered design leaks through result counts and ranking positions —
the `TechArch/04-security.md` §7.6 side channel. CONTEXT also names the risk concentration: *"The
residual-AST-to-query translator needs its own dedicated test suite. It is the single most
security-critical new component in this phase."*

Output: a scope predicate service, its cache, its invalidation wiring, and the translator's own test
suite. Querying with the predicate is plan 02-09.
</objective>

Implements: F5: Search Service (access-scoped result filtering; mandatory pre-filter before ranking)

Enables: F5 (plan 02-09 queries through the predicate this plan produces)

  <name>Task 2: Translate the residual AST into a parameterised SQL predicate, with its own dedicated test suite</name>
  <files>apps/api/src/modules/search/scope/residual-translator.ts, apps/api/src/modules/search/scope/scope-predicate.service.ts, apps/api/test/residual-translator.spec.ts</files>
  <action>
`translateResidual(queries, support, columnMap): ScopePredicate` compiles OPA's residual into SQL over
`platform.search_index`. This is the component CONTEXT singles out as the most security-critical in the
phase, so it is built **allowlist-first and reject-by-default**:

1. **Column map.** A frozen `Record<string, {column: string; kind: 'uuid'|'text'|'text[]'}>` mapping
   `input.resource.*` references to `search_index` columns: `court_id`, `division_id`, `case_id`,
   `proceeding_id`, `designations → designation_tags`, `type → object_type`. A reference outside the
   map is a **translation failure**, never a skipped condition.
2. **Operator allowlist.** Only `eq`/`equal`, `neq`, `internal.member_2` (set membership), and the
   array/set forms OPA emits for `in`. Anything else — arithmetic, `contains`, `regex.match`, a
   function call, a comprehension — is a translation failure.
3. **Parameterisation.** Every literal becomes a `$n` parameter in `params`. The returned `sql` string
   must contain **no interpolated value of any kind**. Add a final assertion inside `translateResidual`
   that the produced `sql` matches `/^[A-Za-z0-9_.,()$ '"=<>!\[\]@&|+-]*$/` and contains no quote
   character adjacent to a parameter marker; throw `ResidualTranslationError` if not. The input is
   OPA-derived rather than user-derived, but a residual is still a program fragment compiled into SQL,
   and the whole guarantee rests on it.
4. **Disjunction semantics.** OPA returns `queries: Expr[][]` — an OR of ANDs. Translate to
   `((a AND b) OR (c AND d))`. An **empty `queries` array means "never true"**, which must compile to
   `always_false: true` and `sql: 'false'`. A single empty query body means "always true"; that is
   legitimate only for a principal OPA determined is unconditionally allowed, so set
   `always_true: true` and emit `'true'` — and log it at warn level with the scope fingerprint, because
   an unconditionally-visible principal is worth noticing.
5. **Support rules.** If `support` is non-empty, OPA could not fully reduce the policy. Do **not**
   attempt partial handling — throw `ResidualTranslationError`, which `ScopePredicateService` converts
   to `503 SECURITY_POLICY_UNAVAILABLE`. Failing closed on an un-reduced policy is correct; guessing is
   not.
6. **Designation tags.** A residual condition over `input.resource.designations` must compile to the
   **superset** form `search_index.designation_tags <@ $n::text[]` — the row's tag set must be contained
   in the entitlements the requester holds — not `&&` (overlap) and not `@>`. Getting this operator
   wrong is the single most likely way a sealed record becomes visible, so give it a named helper, a
   comment stating the three operators and why `<@` is the right one, and dedicated tests.

`ResidualTranslationError` carries the offending AST node so a failure is diagnosable without replaying
the request.

`ScopePredicateService.predicateFor(principal, objectTypes)`:
1. Compute the `ResidualCacheKey` (task 3) and try the cache.
2. On miss, `PartialEvalClient.compile` then `translateResidual`, cache, return.
3. `ResidualTranslationError` → `503 SECURITY_POLICY_UNAVAILABLE`. `PartialEvalClient` already throws it on its own failures.
4. **Never** return `{sql: 'true'}` as an error fallback. The only route to `always_true` is an explicit empty-body residual from OPA.

`apps/api/test/residual-translator.spec.ts` is the dedicated suite — pure unit tests over fixture ASTs,
no database, no OPA, so it runs in milliseconds and can afford to be exhaustive:
- A single-court residual compiles to `court_id = $1` with `params: [courtId]`.
- A court-or-division disjunction compiles to `((court_id = $1) OR (division_id = $2))`.
- A case-list membership compiles to `case_id = ANY($1)` with the array parameter.
- A designation condition compiles to `designation_tags <@ $1::text[]`, and tests assert the generated SQL does **not** contain `&&` or `@>`.
- Empty `queries` → `always_false`, `sql: 'false'`.
- A single empty body → `always_true`, `sql: 'true'`.
- Non-empty `support` → throws.
- An unmapped reference (`input.resource.secret_field`) → throws.
- A disallowed operator (`regex.match`, `plus`, a comprehension) → throws, one test each.
- A literal containing `'; DROP TABLE platform.search_index; --` lands **entirely** in `params` and leaves `sql` unchanged from the benign case — assert the two `sql` strings are identical.
- A literal containing `$1` as text does not disturb parameter numbering.
- A deeply nested 200-term disjunction compiles without stack overflow and produces 200 parameters.
- **Round-trip property test.** For twenty randomly generated principals (varying court, division, case-list and designation entitlements), assert that for every row in a fixture row-set, `translateResidual`'s predicate evaluated in SQL agrees with a direct `data.judicialsync.authz.decision` evaluation for that `(principal, row)` pair. This is the test that proves the translator and the guard cannot disagree — run it in the e2e spec (task 3) where both OPA and Postgres are available, and reference it from here.

`ResidualCacheService` over the Redis connection plan 01-06 already established.

**Key**: `searchresidual:{scope_fingerprint}:{bundle_revision}:{object_types}` where
`scope_fingerprint` is `sha256` over the principal's *resolved* roles, scopes and entitlements
(canonically sorted) — not the user id, so two users with identical entitlements share a residual and a
user whose entitlements change gets a different key automatically. Keep a secondary index
`searchresidual:user:{user_id}` (a Redis set of the keys that user's fingerprints produced) so
`invalidateForUser` can delete precisely rather than scanning.

**TTL**: `min(SEARCH_RESIDUAL_CACHE_TTL_SECONDS, session.claim_cache_seconds)` read through
`ConfigResolver` — CONTEXT: *"do not invent a new staleness budget."* Read it per `set`, not at boot,
so a published security/retention package changing the window takes effect.

**Invalidation**, every path CONTEXT names:
- `invalidateForUser(userId)` — called from `GrantsService.approve`, `.deny`, `.revoke` and from wherever plan 01-06's `EntitlementResolverService.invalidate(userId)` is already called. **Call it at exactly those sites**, immediately after the existing invalidate, inside the same transaction's success path. CONTEXT: *"Every entitlement mutation path must be wired to invalidation; a missed hook is a silent over-permission, so this needs test coverage, not just care."*
- `invalidateForCase(caseId)` — called from `designations.service.ts` alongside plan 02-05's `applyDesignationTags`. A designation change alters which rows match, not which residual a principal gets, so this is belt-and-braces; implement it as a targeted delete of residuals whose cached predicate referenced that case id, or, if that is not cheaply determinable, as `invalidateAll('designation_change')`. Choose the simpler correct option and say which in the SUMMARY.
- `invalidateAll(reason)` — called when the OPA bundle revision observed by `PartialEvalClient` differs from the last one seen. Because the revision is part of the key, a bundle update already produces a miss; `invalidateAll` additionally reclaims the stale keys. Log the reason.

**Fail-closed on Redis**: if Redis is unavailable, `get` returns `null` (a miss, so OPA is consulted) and
`set` is a no-op — a cache outage must degrade to *slower*, never to *unscoped*. But if Redis is
unavailable **and** OPA is unreachable, `ScopePredicateService` still raises `503`. Add a comment
stating this ordering.

Register everything in `SearchModule` and export `ScopePredicateService`.

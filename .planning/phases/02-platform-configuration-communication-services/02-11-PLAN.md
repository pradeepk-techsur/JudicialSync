<objective>
Make ROADMAP criterion 3 true: retry a failed delivery per the court-configured backoff, mark it
`failed` after the configured attempts, write a durable `exceptions` record, and escalate an
unacknowledged delivery past its cadence to the configured secondary recipient — with the escalation
decision derived from durable Postgres rows, not from a timer held in Redis.

Purpose: criterion 3 says *"an alert is never silently dropped on persistent failure."* CONTEXT turns
that into an architecture: *"A periodic BullMQ sweeper over durable Postgres state — the same shape as
Phase 1's hash-chain verification job… A sweeper's decision is derivable from durable Postgres rows at
any instant, so a Redis flush, worker crash or multi-hour outage loses nothing — the next sweep catches
every overdue alert. A per-notification delayed BullMQ job would hold the pending escalation only in
Redis, where losing it is precisely the 'silently dropped' outcome."* And Phase 1's rejection of
log-only carries forward: *"too easy to miss and leaving no audit-visible trace of detection."*

Output: retry, escalation, and the narrow `exceptions` write path. The F07 queue — UI, triage, aging,
auto-close prohibition, rationale-gated resolution — is **Phase 3** and must not appear here.
</objective>

`backoff.ts` is pure and has no dependencies, so it is unit-testable without a database:

```typescript
export function nextAttemptAt(now: Date, attempt: number, p: BackoffPolicy, rand = Math.random): Date | null {
  if (attempt >= p.max_attempts) return null;                 // exhausted — caller marks failed
  const raw   = p.base_delay_seconds * Math.pow(p.multiplier, attempt - 1);
  const capped= Math.min(raw, p.max_delay_seconds);
  const jitter= capped * p.jitter_ratio * (rand() * 2 - 1);   // full-range symmetric jitter
  return new Date(now.getTime() + Math.max(1, capped + jitter) * 1000);
}
```

**Claude's-discretion decision, resolved: the backoff parameters are configuration, owned by the
operational rule package** (plan 02-02's `notification_delivery` schema, plan 02-06's seeded defaults:
`max_attempts: 4`, `base_delay_seconds: 30`, `multiplier: 2`, `jitter_ratio: 0.2`,
`max_delay_seconds: 900`). A court that needs a gentler relay cadence should not need a deployment, and
every other court-variable behaviour in this system already lives in F3. The `.env` values plan 02-01
declared are **ceilings only** — clamp the configured policy to them so a misconfigured package cannot
produce a 30-day retry window; log a warning when clamping.

`delivery.processor.ts` — a BullMQ worker on the notification delivery queue, on the infrastructure plan
01-12 established:
1. Call `DeliveryService.attempt(deliveryId)`.
2. On `sent`: nothing more.
3. On a **retryable** failure: read `configResolver.get(court_id, 'notification_delivery')`, clamp it, and compute `nextAttemptAt(clock.now(), attempt_count, policy)`.
   - Non-null → set `next_attempt_at` and re-enqueue with that delay. The row stays `queued`.
   - Null → **terminal**: set `status='failed'`, `failed_at=now()`, and in the **same transaction** raise an exception via `ExceptionsService` with `exception_type:'notification_delivery_failed'`, `severity` mirroring the notification's severity mapped to the exception scale (`critical → critical`, `warning → high`, `info → medium`), `object_type:'notification_delivery'`, `object_id` = the delivery id, `source_module:'notifications'`, `dedupe_key` = the delivery id, and `detail` carrying `attempt_count`, `last_error`, `channel`, `notification_type` — **and no case, party or recipient-identifying content beyond the user id**, because the exception record is read by admins who may not hold the matter's entitlements.
4. On a **non-retryable** failure (permanent SMTP rejection): go terminal immediately, same exception path, with `detail.terminal_reason: 'non_retryable'`. Retrying a permanently rejected address four times only delays the human discovering a bad address.
5. Leave `escalation_due_at` untouched. A failed delivery is still escalatable — that is the point of criterion 3 — and the sweeper handles it.

Also wire the **no-recipient** case: `NotificationsService.trigger` throws
`422 NOTIFY_NO_RECIPIENT_CONFIGURED` (plan 02-10). Catch it at the trigger boundary, raise an exception

`object_type:'notification_type'`, `object_id` derived from the court and type, `dedupe_key` = `${court_id}:${notification_type}`),
and **re-throw** so the caller still sees the 422. `FRD/F04` Validation requires it "raise a
configuration exception (F07), not silently fail to send" — both, not either.

  <action>
`EscalationSweeperService.sweep()` is one indexed query and a bounded loop:

```sql
SELECT d.* FROM platform.notification_deliveries d
WHERE d.escalation_due_at IS NOT NULL
  AND d.escalation_due_at <= $now
  AND d.acknowledged_at IS NULL
  AND d.escalated_at IS NULL
  AND d.is_escalation = false
ORDER BY d.escalation_due_at ASC
LIMIT $batch
FOR UPDATE SKIP LOCKED;
```

`$now` comes from `ClockService`, so a test can move time instead of sleeping. The partial index plan
02-01 created backs exactly this predicate. `FOR UPDATE SKIP LOCKED` makes concurrent sweepers safe.

Write the design rationale as a header comment, because the obvious alternative is tempting:

> This is a **sweeper over durable Postgres state**, not a per-notification delayed BullMQ job.
> Criterion 3 requires that an alert is never silently dropped. A sweeper's decision is derivable from
> durable rows at any instant, so a Redis flush, a worker crash or a multi-hour outage loses nothing —
> the next sweep catches every overdue alert. A delayed job would hold the pending escalation only in
> Redis, where losing it is precisely the "silently dropped" outcome. Escalation fires within one sweep
> interval rather than exactly on the second, which is immaterial against minute-to-hour cadences.
> **Do not replace this with a delayed job.**

For each overdue row, inside **one transaction per row**:
1. Resolve the escalation target: `escalation_recipient_role` from the court's configured entry for that `notification_type`, expanded to its holders exactly as plan 02-10's resolver does (reuse `RecipientResolverService`, do not re-resolve by hand).
2. **No escalation recipient configured** → do not retry forever: set `escalated_at = now()` to stop re-sweeping, and raise an exception `exception_type:'notification_escalation_unconfigured'`, `severity:'high'`, `dedupe_key = ${court_id}:${notification_type}`. A cadence configured with nowhere to escalate is a configuration defect, and it must surface rather than loop.
3. Otherwise insert **new** `notification_deliveries` rows for the escalation recipients with `is_escalation = true`, `escalation_source_delivery_id` = the overdue row's id, `status='queued'`, `attempt_count=0`, `next_attempt_at=now()`, and `escalation_due_at = NULL` — an escalation does not itself escalate, which is what stops an infinite chain.
4. Set the overdue row's `escalated_at = now()`. Because the sweep predicate excludes `escalated_at IS NOT NULL`, this makes the operation **idempotent**: a second sweep over the same row does nothing.
5. Raise an exception for the escalation itself when the notification's `severity` is `critical` — a critical alert that went unacknowledged long enough to escalate is worth a durable record, and Phase 3's queue will want it.
6. Enqueue delivery jobs for the new rows after commit.

`escalation.processor.ts` — a BullMQ repeatable job on `NOTIFY_SWEEP_INTERVAL_SECONDS`
(**Claude's-discretion decision: default 60 seconds**, which is an order of magnitude finer than the
minute-to-hour cadences courts configure, and cheap because the query is a partial-index range scan).
Same registration shape as plan 01-12's chain-verification job; a fixed job id so slow runs do not stack.
Expose `sweep()` directly too, so tests drive it deterministically rather than waiting for the schedule.

`notification-escalation-sweeper.e2e-spec.ts` — assurance proof 6, end to end:
1. Trigger a `threshold_crossed`/`warning` notification whose configured cadence is 60 minutes; assert the delivery row has `escalation_due_at` ≈ 60 minutes ahead.
2. Run `sweep()` immediately: nothing escalates.
3. **Backdate** `escalation_due_at` by one hour (direct SQL, the mechanism CONTEXT names) and run `sweep()`: a new delivery row exists for the configured `escalation_recipient_role`'s holder with `is_escalation=true` and `escalation_source_delivery_id` pointing at the original; the original now has `escalated_at` set.
4. Run `sweep()` twice more: no further rows are created — **idempotency**.
5. Run the delivery worker; `mailpitLatestFor(secondaryRecipient.email)` returns a policy-compliant message — the escalation actually reached a human, and it leaked nothing.
6. The escalation row's own `escalation_due_at` is null; backdating cannot make it escalate again.
7. **Acknowledging stops escalation**: trigger a second notification, acknowledge it, backdate its `escalation_due_at`, sweep, and assert nothing escalated — plan 02-10 clears `escalation_due_at` on acknowledge and the predicate also checks `acknowledged_at`.
8. **Failure plus escalation, the full criterion 3 chain**: with `mailpitSetFailureMode` on, trigger a `critical` notification; drive the retries to exhaustion so it is `failed` with its `exceptions` row; clear failure mode; backdate `escalation_due_at`; sweep; assert the escalation delivery is created and, after the worker runs, actually received by the secondary recipient. **A failed delivery still escalates** — the alert is not dropped merely because the primary channel broke.
9. **Durability**: flush Redis entirely (simulating the loss CONTEXT names), then run `sweep()`; the overdue rows still escalate, because the decision lives in Postgres.
10. A court whose configured entry has a cadence but no `escalation_recipient_role` produces one `notification_escalation_unconfigured` exception and stops re-sweeping that row.

Add a file-header comment naming this spec as the evidence for ROADMAP criterion 3 and assurance proof 6.

<objective>
Build `UX-Mockup/Screen-16` inside Phase 1's generic USWDS shell: tabbed editable tables for numbering,
workflow states, thresholds and event mappings; inline validation driven by the shared `zod` package;
an approver Select that excludes the current user; a Publish control that is **structurally blocked**
for the drafter; and version history stating that existing calculations are not retroactively
recalculated.

Purpose: ROADMAP criterion 1 names a *court admin* doing this, so the flow has to exist as a screen, not
only as an endpoint. CONTEXT locks the placement — *"Three screens are added to Phase 1's existing
generic USWDS shell, gated by entitlement rather than by role layout… Phase 4 builds the workspaces;
Phase 2 builds screens inside the generic shell"* — and the validation approach: *"Structural validation
lives once, in a shared `zod` schema package in the monorepo, imported by both the NestJS server and
the React client,"* because `Screen-16`'s "client-side pre-validation mirrors server rules" is the
two-implementations-that-drift shape Phase 1 refused.

Output: the Configuration Engine screen, wired into the side navigation, with Playwright coverage and
the axe-core gate extended to it.
</objective>

  <action>
`useRulePackageDraft(courtId, packageType)` is the data hook: a TanStack Query for
`GET /config/rule-packages/{court_id}/draft` falling back to
`GET /config/rule-packages/{court_id}/effective` when no draft exists, a mutation for
`POST /config/rule-packages` (create draft from effective), and a mutation for
`PUT /config/rule-packages/{id}` carrying `expected_updated_at`. On `409 CONFIG_DRAFT_CONFLICT` it
surfaces a blocking USWDS Alert — "This draft was changed by someone else. Reload to continue." — and
**does not** auto-merge. On `409 CONFIG_DRAFT_EXISTS` it offers to open the existing draft.

Validation runs **locally in the hook** through `validateRulePackage` from
`@judicialsync/config-schema` on every edit, producing `ConfigValidationIssue[]` whose `path` each tab
uses to place its inline Alert. The client **imports** the rules; it never restates one. A tab that
needs a new rule adds it to the package, not to the component.

`ConfigurationPage.tsx` — USWDS `Tabs` with the four `Screen-16` panels in the mockup's order
(Numbering, Workflow States, Thresholds, Event Mappings), a header `Tag` showing
`Draft v{n}` or `Published v{n} — effective {date}` exactly as the mockup's States table specifies, a
`Save Draft` button, the always-visible Publish panel (task 2), and the version-history panel (task 2).
A package-type switch (operational / security/retention) sits beside the tabs; the security/retention
package shows its own panels for security policies, retention schedules, allowlist and session, since
those are the tables Phase 1 seeded and CONTEXT moved under versioning.

Information hierarchy, per the mockup's table: **structural validation errors are Primary** — rendered
inline, directly under the offending row, as a red USWDS `Alert` with `role="alert"`; the Publish
control and its SoD state are Primary and always visible at the bottom; tab content is Secondary; the
draft version Tag is Tertiary.

`ThresholdsTab.tsx` — the editable tier table from the mockup: `Tier | Min (days) | Max (days) |
Severity`, with `∞` rendered for a null `max_value` and an add/remove row control. A
`CONFIG_THRESHOLD_GAP` issue renders under the offending row with the FRD message "Threshold tiers must
be contiguous and non-overlapping", plus the mockup's concrete hint pattern — "Gap detected:
{a}–{b} unclassified" — derived from the issue's own values, not hardcoded.

`WorkflowStatesTab.tsx` — grouped by `object_type`, each group with an initial-state selector and rows
of `state_name` plus a multi-select of `allowed_transitions`. A terminal state is visibly tagged.
`CONFIG_INVALID_STRUCTURE` issues render per row for an unreachable state or a dangling transition, and
once at the group level for "no terminal state", matching the mockup's "Red Alert on Workflow States
tab".

`EventMappingsTab.tsx` — rows of `source_event_code`, `source_event_description_pattern`,
`internal_category`. A `CONFIG_AMBIGUOUS_MAPPING` issue renders on the duplicate row with the FRD
message carrying the interpolated code.

`NumberingTab.tsx` — `prefix_pattern` with the closed placeholder set shown as help text, and
`sequence_reset_rule` as a USWDS Select.

Accessibility, per `UX-Mockup/Y2-accessibility.md`: every editable cell has a programmatic label; each
inline Alert is associated with its row's inputs via `aria-describedby`; the tab set uses the USWDS
Tabs pattern with correct roles; nothing conveys state by colour alone — a row in error also carries a
text marker. Use `@trussworks/react-uswds` components rather than hand-rolled markup.

Read-only surface: when `hasEntitlement('config_admin')` is false for an operational package (or
`security_officer` for the other), render every control disabled and show the mockup's
`CONFIG_EDIT_DENIED` text — "You do not have configuration administration access" — in an informational
Alert. **Not an empty page**: plan 01-15 established that pattern for the Audit Explorer and it carries
forward. The client gate is UI-only; the server re-validates every call.

`PublishPanel.tsx` reproduces the mockup's bottom panel and its central rule — **"structurally blocked,
not just rejected after click."**

- Shows `Drafted by: {display_name}{ (you) if self }`.
- The approver `Select` is populated from `GET /config/rule-packages/{id}/eligible-approvers`, which already excludes the drafter server-side. Render it exactly as the mockup's "Select a different user to approve"; if the list is empty, show an Alert explaining that no second holder of the required entitlement exists in this court — a court with one admin cannot publish, and that is a real operational condition, not an error to hide.
- `Submit for approval` calls `POST /config/rule-packages/{id}/submit` with the chosen approver.
- The `Publish` button is **disabled whenever the signed-in user is the drafter**, with a USWDS `Tooltip` carrying the FRD message "A second approver is required to publish this configuration". It is also disabled while any validation issue exists, with a tooltip naming the blocking issue count. Disabled is the primary control; the server's `403 CONFIG_SOD_VIOLATION` is the backstop, and the two must agree.
- When the signed-in user **is** the nominated approver, the button is enabled and calls `POST /config/rule-packages/{id}/publish` with a body containing **only** an optional `effective_from`. The generated client cannot express `approving_user_id` — plan 02-12 removed it from the schema — and this component must not add it back. Write that as a comment citing `docs/SPEC-DEVIATIONS.md` DEV-01.
- Server errors render through plan 01-15's `ApiErrorAlert` keyed on `error_code`, so `CONFIG_SOD_VIOLATION`, `CONFIG_THRESHOLD_GAP`, `CONFIG_AMBIGUOUS_MAPPING` and `CONFIG_INVALID_STRUCTURE` each display their FRD message.
- On success the header Tag flips to `Published v{n} — effective {date}` and the draft controls disappear.

`VersionHistoryPanel.tsx` lists `GET /config/rule-packages/{court_id}/versions` newest-first with
version number, published date, drafter and approver, each linking to
`GET /config/rule-packages/{id}` rendered read-only. Beneath it, render the mockup's explicit note
**verbatim**: *"Existing calculations referencing v{prior} are not retroactively recalculated."* This
sentence is a user-facing statement of `FRD/F03` process step 7, and `Screen-16` lists it as a required

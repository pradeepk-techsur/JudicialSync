<objective>
Build the notification inbox inside Phase 1's generic USWDS shell — list, severity, delivery status and
acknowledge — behind a thin transport abstraction, plus the `/go/:objectType/:objectId` landing route
that every notification deep link points at.

Purpose: ROADMAP criterion 2 requires delivery status be tracked and visible, and a notification a
recipient can see and acknowledge is how an escalation gets stopped. CONTEXT locks the transport:
*"Polling via TanStack Query (already in the stack from Phase 1), behind a thin transport abstraction.
No new infrastructure, no connection lifecycle, no sticky-session or proxy concerns. §9.4 names
poll-based as a sanctioned option. WebSocket push is deferred to Phase 5, where 'chambers sees the live
status update during the same session' is a genuine requirement. The abstraction means Phase 5
introduces push without rewriting the inbox."* It also locks the deep link: *"a plain application URL
carrying zero authority. Clicking it enters the normal authenticated flow… A forwarded or intercepted
email grants nothing."* Plan 02-03 emits `${PUBLIC_BASE_URL}/go/{type}/{id}`; this plan is where that
URL becomes a real route, so an emailed link resolves instead of 404ing.

Output: the inbox screen, the header bell, the deep-link landing route, Playwright coverage and the
extended axe gate.
</objective>

  <name>Task 1: The transport abstraction and its polling implementation</name>
  <files>apps/web/src/notifications/transport.ts, apps/web/src/notifications/polling-transport.ts, apps/web/src/notifications/useNotifications.ts</files>
  <action>
`transport.ts` declares `InboxItem`, `NotificationTransportEvent`
(`{type:'items-changed'} | {type:'unack-count-changed', count:number}`) and `NotificationTransport`
exactly as in the `provides` contract. Write the purpose as a header comment:

> Phase 2 ships `PollingNotificationTransport`. Phase 5 adds a WebSocket implementation behind this
> same interface for live courtroom status, and **the inbox is not rewritten**. Nothing above this
> interface may know whether updates arrive by poll or by push: no `refetchInterval` in a component, no
> `setInterval` in a page, no socket in a hook. If a component needs to know, the interface is wrong.

`InboxItem` carries **only** the closed-context fields plan 02-10's `GET /notifications/my` returns —
`notification_type`, `severity`, `type_description`, `deep_link`, `court_name` — plus status and
timestamps. There is deliberately **no** `object_id`, no `case_id`, no caption. The inbox is a channel,
and it is bound by the same content policy as email; a field that is not in the type cannot be rendered
by accident.

`polling-transport.ts` — `PollingNotificationTransport` built on TanStack Query:
- `fetchPage(cursor)` → `GET /notifications/my` through the generated client.
- `acknowledge(deliveryId)` → `POST /notifications/{id}/acknowledge`, returning the updated item.
- `subscribe(onEvent)` sets a `refetchInterval` on the inbox query (default 30 s; 10 s while the inbox page is focused) and emits `items-changed` / `unack-count-changed`. Returns an unsubscribe function that clears the interval. Pause polling when `document.visibilityState === 'hidden'` — a background tab polling a court's API every ten seconds for a day is avoidable load, and `TechArch/06-integrations.md` §9.4 names poll-based delivery without promising a cadence.
- Poll latency is irrelevant against minute-scale escalation cadences; say so in a comment so nobody "optimises" it into a socket.

`useNotifications()` is the single hook components use: it holds the transport instance from context,
exposes `{items, unackCount, isLoading, error, acknowledge, loadMore}`, and performs the acknowledge as
an optimistic update that rolls back on error, surfacing `409 NOTIFY_INVALID_TRANSITION` and
`404 NOTIFY_NOT_FOUND` through `ApiErrorAlert`. Provide the transport through a small React context so
Phase 5 swaps the implementation in one place.

`DeepLinkPage.tsx` is the route `${PUBLIC_BASE_URL}/go/:objectType/:objectId` resolves to — the URL plan
02-03 puts in every email. It must behave exactly as CONTEXT describes, and the component's header
comment should say so:

> This link carries **zero authority**. It is a plain application URL. An unauthenticated visit is
> redirected to Keycloak login with TOTP by `RequireSession`; an authenticated visit resolves the object
> and navigates to its canonical screen; an unauthorized visit is denied by the server's global OPA
> guard and audited as an `access_attempt` like any other request. A forwarded or intercepted email
> grants nothing. **Never add a token, signature or step-up parameter to this route.**

Behaviour:
- Wrapped in `RequireSession`, so an unauthenticated visit goes to login and returns here afterwards.
- Maps `objectType` to its canonical route through a small frozen table. Phase 2 knows `case` → `/cases/{id}` (plan 01-15's case list detail route, if one exists; otherwise the case list filtered to that id). `party`, `proceeding`, `docket_event`, `document_reference` resolve to their owning case's route. - A server `403`/`404` while resolving renders through `ApiErrorAlert` with the server's message — the client must not translate a `404` into "you lack access", because the `404` is deliberately indistinguishable from a non-existent record.

Routing and navigation, honouring the Navigation Map invariant:
- `routes.tsx` gains `/notifications` → `NotificationsPage` and `/go/:objectType/:objectId` → `DeepLinkPage`, both inside `AppShell` behind `RequireSession`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| db→render | Notification and delivery data crossing into rendered markup in a shared browser session. |
| email→browser | An emailed URL crossing into the application as a navigation, from an inbox outside the system's control. |
| client→API | Acknowledgement requests addressed by delivery id. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-69 | Information disclosure | The in-app inbox leaking case or party detail the email channel is forbidden to carry | mitigate | `InboxItem` in `apps/web/src/notifications/transport.ts` declares only the closed-context fields plan 02-10's endpoint returns, with no `object_id` or caption; task 1's `<verify>` greps the inbox tree for record field names and `notifications.spec.ts` test 3 asserts the party name and caption are absent from the rendered page. |
| T-02-70 | Elevation of privilege | An emailed deep link granting access to whoever holds the message | mitigate | `apps/web/src/pages/DeepLinkPage.tsx` is a plain route wrapped in `RequireSession`, carrying no token or signature; `notifications.spec.ts` test 10 asserts an unauthenticated visit reaches Keycloak login and test 11 asserts an unauthorized visit is denied by the server. |
| T-02-71 | Information disclosure | The deep-link page translating a deliberate existence-hiding `404` into "you lack access", confirming a sealed matter exists | mitigate | `DeepLinkPage` renders the server's message unchanged through `ApiErrorAlert` and composes no explanatory text of its own; test 11 asserts the page contains neither the caption nor the words "sealed" or "restricted". |
| T-02-72 | Information disclosure | Acknowledging or viewing another user's delivery by guessing a delivery id | mitigate | `GET /notifications/my` and the acknowledge route are scoped to `principal.user_id` server-side and return `404 NOTIFY_NOT_FOUND` for a foreign delivery (plan 02-10); the client holds no id the server did not give it. |

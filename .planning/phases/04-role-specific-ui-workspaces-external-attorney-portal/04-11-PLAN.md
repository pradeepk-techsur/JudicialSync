<objective>
Turn Phase 1's generic shell into two route-selected workspace shells, move every navigation entry
into the registry, delete Phase 3's nav aggregator, and give each of the four roles a home to land
on — including the two homes that are, today, legitimately empty.

Purpose: CONTEXT locks the shell decision and its reasoning. **"Two shell variants, not four
bespoke ones. Chrome density is the distinguishing axis."** And: **"The variant is selected by
ROUTE, not by user. Why: if the variant were per-user, a deputy following a notification deep link
to `/exceptions` would land in full-bleed chrome with no navigation and no way out. Dead-ending the
role most likely to be working under time pressure."**

It locks the migration and its single risk: **"`phase3-nav.tsx` is deleted, its entries migrating
into registrations; `SideNav.tsx` renders purely from the registry … This is the one genuinely
migratory act in an otherwise additive phase, so the assurance suite must assert every pre-Phase-4
nav entry is still reachable afterwards."**

And it locks what must *not* move: **"Routes and components are unchanged … Phase 2 locked that
notification deep links are plain application URLs, already potentially in recipients' inboxes, and
Phase 3 built timeline deep links into underlying records. Re-parenting routes would break links
already emitted."**

Output: `AppShell` as the side-nav workspace shell, `FullBleedShell`, the switcher, the registry-fed
`SideNav`, the four workspace homes with their genuine empty states, the `UI_NO_WORKSPACE_ASSIGNED`
page, and the extended axe gate.
</objective>

applies in full: the six-step spacing scale, the type tokens, the colour budget with accent reserved
for the listed four uses, the **one-primary-per-page-level-region** rule, the copywriting contract,

outcome:
- **D-1** — USWDS 3.x and `@trussworks/react-uswds` ship **no Tabs component**; the contract resolves

  stacks per Screen-04/10/15. If a layout pressure toward tabs emerges, reuse that same decision;
  do not invent a second approach, and record the dependency rather than assuming D-1's outcome.
- **D-2 / D-11** — a conditionally-blocked control uses `aria-disabled` plus a no-op handler plus
  **permanent visible helper text**, never the `disabled` attribute. Apply it to any control this
  plan gates on a condition.
- **D-9** is scoped to plan 02-15 and does not touch Phase 4.

**Do not build here:** any panel component (plan 04-12), any portal screen, any change to an
existing page component or its route.

keyboard-shortcut registry, focus-management harness, or touch-target system. That is interaction
machinery for a task that does not exist … Phase 5 designs the keyboard model against real

notification bell, sign out — must be keyboard reachable, which is `Y2-accessibility.md`'s baseline
and not a harness. No `aria-keyshortcuts`, no shortcut registry, no touch-target sizing rule.

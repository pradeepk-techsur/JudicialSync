<objective>
Put the external portal's two refusals — not-a-party and security-designated — into Rego, in the
order that makes them safe, and compose them into the one expression the global guard reads.

Purpose: CONTEXT corrects F12's error table and then states why the correction is not really about
status codes: **"THE CHECK ORDER IS LOAD-BEARING. Party-of-record is evaluated first — fail it and
the response is 404. Only if that passes is designation evaluated. Reversing the order would leak
sealed-case existence to non-parties, the worst outcome available here."** Expressing the ordering
as policy precedence — not as the sequence of two `if` statements in a handler — is what makes it
survive a refactor.

CONTEXT also locks the third use of *"build the refusal, not the capability"*:
**"Security-designation default-deny is ABSOLUTE in v1. The per-case override is NOT built. No
entitlement, flag or endpoint can lift the deny."** In policy terms that means there is no input
field a widened configuration, a granted entitlement, or a future endpoint could set to produce an
allow — and assurance proof 4 greps the whole codebase to confirm none exists.

Finally, Phase 3 learned the hard way that **"a new deny rule must be composed into `decision.rego`'s
`all_denials` union or it is inert."** That composition is a first-class deliverable here, with its
own test.

Output: `portal.rego`, its unit tests, the extended `all_denials` union and precedence ordering, the
Phase 4 `action_entitlement_map` rows, and the route-reconciliation test.
</objective>

**Rule 1 — realm confinement.** A portal principal may only reach declared portal resource types:

```rego
portal_resource_types := {"portal_case", "portal_submission", "portal_speedy_trial_summary"}

portal_deny contains "PORTAL_WRITE_DENIED" if {
  input.principal.realm == "portal"
  not input.resource.type in portal_resource_types
  input.action != "read"
}

portal_deny contains "AUTH_AUDIENCE_MISMATCH" if {
  input.principal.realm == "portal"
  not input.resource.type in portal_resource_types
  input.action == "read"
}
```

The split exists so F12's error table is honoured literally on the case it names — *"Attorney
attempts write to ledger/docket/calculation endpoint → 403 `PORTAL_WRITE_DENIED`"* — while a
non-mutating probe gets the broader `AUTH_AUDIENCE_MISMATCH`. Both are 403; neither leaks anything.
`AUTH_AUDIENCE_MISMATCH` is a new Phase 4 code, registered by plan 04-10.

This rule is **deliberately a whitelist, not a blacklist.** CONTEXT rejected explicit deny lists on
ledger/docket/calculation endpoints by name, quoting Phase 1: *"a route that forgets the decorator is
silently open."* Phase 5's ledger and Phase 7's calculations inherit this deny the moment they are
written, because they will not be in `portal_resource_types`.

**Rule 2 — party of record, evaluated first.**

```rego
portal_deny contains "PORTAL_NOT_PARTY_OF_RECORD" if {
  input.principal.realm == "portal"
  input.resource.type in portal_resource_types
  not input.resource.attributes.party_of_record == true
}
```

Written as `not … == true` rather than `input.… == false` so that a **missing** attribute denies.

**Rule 3 — designation, absolute.**

```rego
portal_deny contains "PORTAL_DESIGNATION_DENIED" if {
  input.principal.realm == "portal"
  input.resource.type in portal_resource_types
  count(input.resource.designations) > 0
}
```

Note what is **not** here: no entitlement check, no `input.resource.attributes.portal_authorized`
escape, no court-configuration input, no scope attribute. Put a comment above the rule quoting F12
and CONTEXT: the *"unless explicitly and individually authorized by the court"* escape hatch is
**deferred**, and *"no entitlement, flag or endpoint can lift the deny."* The comment matters —
assurance proof 4 greps for any override mechanism anywhere in the codebase, and the next engineer
who reads this rule must find the reason here rather than infer an oversight.

Phase 3 recorded the failure mode this task exists to prevent: a deny rule in a new file is **not
evaluated** unless it is named in `decision.rego`'s `all_denials` union, because that union is the
only expression the global guard reads.

Extend the union, preserving the Phase 1 and Phase 3 terms:

```rego
all_denials := rbac_deny | abac_deny | entitlement_deny | sod_deny | outbound_deny | portal_deny
```

Extend `highest_precedence_reason` so the Phase 4 codes sit **above** everything already there, with
`PORTAL_NOT_PARTY_OF_RECORD` above `PORTAL_DESIGNATION_DENIED`:

```
PORTAL_NOT_PARTY_OF_RECORD > PORTAL_DESIGNATION_DENIED > CMECF_OUTBOUND_DENIED
  > AUTH_SOD_VIOLATION > AUTH_DESIGNATION_DENIED > AUTH_MFA_FAILED > AUTH_SCOPE_DENIED
```

**This ordering is the security control, and it needs the comment to say so.** When a non-party
requests a sealed case, *both* `PORTAL_NOT_PARTY_OF_RECORD` and `PORTAL_DESIGNATION_DENIED` are in
the denial set simultaneously — Rego evaluates rules as a set, not as a sequence. Precedence is what
picks the one the caller sees. If `PORTAL_DESIGNATION_DENIED` won, a non-party probing identifiers
would receive 403 on exactly the sealed cases and 404 on everything else: a perfect existence
oracle for the most adversarial population in the system. Write that paragraph into the file.

Extend `hide_existence` so it is true when the selected reason is in
`portal_hide_existence_reasons`, keeping plan 01-02's existing `designation.rego`-driven term
intact.

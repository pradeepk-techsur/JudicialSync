<objective>
Build everything the external attorney can actually do — see their cases, submit exhibit metadata,
read a Speedy Trial summary — with the access-control path that makes each of those safe, in the
order that makes it safe.

Purpose: CONTEXT corrects F12's error table and explains that the correction is really about
ordering: **"THE CHECK ORDER IS LOAD-BEARING. Party-of-record is evaluated first — fail it and the
response is 404. Only if that passes is designation evaluated."** It locks the staging table as the
fourth use of *"write the durable record now, the consumer arrives later"*, with
**"Phase 5's F15 DRAINS it"**. It locks the upload half: *"reuses Phase 1's existing pipeline:
allowlist → ClamAV → encrypted storage. Screen-19's 'malware-scanned, allowlisted types only'
messaging is therefore truthful."* And it locks the Speedy Trial endpoint shipping **for real**:
*"with the full access-control path live and provable now … with no tracker data it returns empty
and renders 'No deadline information is available for this case' — literally true"*, explicitly
rejecting a 503 because *"503 means temporarily unavailable, and this is not temporary — it is
unbuilt, a different fact. It would also park the access rules behind an error path so the one
genuinely risky part of this endpoint goes unexercised for three phases."*

This plan owns the portal's Nest module file. Plan 04-09 owns the composition root and imports it
behind the audience guard; the integration tests here therefore run against a dedicated testing
module, and the full-stack boundary proofs belong to 04-09 and the assurance suite.

Output: the party-of-record decision, the case list, the submission endpoint, the Speedy Trial
summary with its Phase 7 registration seam, and the portal module that declares them all.
</objective>

**`party-of-record.service.ts` — the heart of this plan.**

`assertAccess(principal, caseId)` runs exactly two steps, and the file must open with the comment
block naming the order and the reason:

```
// THE CHECK ORDER IS THE SECURITY CONTROL — not the status codes.
//   1. party of record  -> fail = 404 PORTAL_NOT_PARTY_OF_RECORD
//   2. designation      -> fail = 403 PORTAL_DESIGNATION_DENIED
// Reversing these would hand a non-party a 403 on exactly the sealed cases and a 404 on
// everything else: a perfect existence oracle for the one population in this system with no
// court employment, no training and no audit relationship.
// DEVIATION from F12's error table, which gives both as 403. Registered by plan 04-10.
```

**Step 1 — party of record.** One query, and the single-query shape is itself the mitigation:

```sql
SELECT 1
  FROM platform.parties p
 WHERE p.case_id = $1
   AND p.party_role = 'counsel'
   AND p.external_id = $2
   AND p.source_system <> 'manual'
 LIMIT 1
```

Three properties to comment:
- It **never** checks whether the case exists first. A nonexistent `caseId` and an unassociated
  `caseId` both produce zero rows through the identical code path, which is what makes the two 404s
  indistinguishable in shape *and* in work done.
- `source_system <> 'manual'` is F12's *"not self-asserted by the attorney"* enforced in the query.
  CONTEXT: *"No manual portal grant in v1 — there is no path by which a human can assert an
  association the docket does not record."*
- `principal.cmecf_party_external_id` null → **return the 404 without querying at all**… no. Query
  anyway with a value that cannot match, so the timing of the unbound-attorney case matches the
  unassociated-case case. An early return would make "this attorney has no identity binding"
  distinguishable by latency from "this attorney is not on this case". Comment the choice.
- **No cache, no TTL.** CONTEXT rejected caching by name: *"a cached association outlives the docket
  change that should end it, which is the stale-permission failure Phase 1's immediate-revocation
  requirement exists to prevent."* Say so in a comment so nobody adds one for performance.

Zero rows → throw `ApiException(404, 'PORTAL_NOT_PARTY_OF_RECORD', 'Case not found or not accessible')`.
The message is `Y2-errors.md`'s generic 404 wording, **identical** to what a genuinely nonexistent
case returns, because F12's *"You are not associated with this case"* would itself confirm the case
exists. Register that message change as part of the same deviation.

**Step 2 — designation.** Only if step 1 passed:

```sql
SELECT 1 FROM platform.security_designations
 WHERE object_type = 'case' AND object_id = $1 LIMIT 1
```

Any row → throw `ApiException(403, 'PORTAL_DESIGNATION_DENIED',
'This case is not available through the external portal')` (F12's wording, unchanged). **All five
designation values deny**; there is no carve-out and no parameter that could add one.

Both denials write an `access_attempt` audit event through plan 01-05's `AuditService`, with
`actor_external_principal_id` set (plan 04-01's widened column) —
`TechArch/04-security.md` §7.6: *"Every such denied/hidden attempt is itself logged as an
`access_attempt` audit event."* The attorney sees nothing of it; an authorized auditor sees all of
it, which is exactly the asymmetry the portal needs.

`listAssociatedCases(principal)` — join `parties` to `cases` on the same predicate, returning case
number, caption, the attorney's `party_role` and the court name, **excluding any case carrying a
`security_designations` row**. Screen-19: a designated case *"is never shown in degraded/greyed
form — it is absent from the attorney's case list entirely"*. Exclude it in the query, not after
fetching, so no count anywhere includes it.

**`portal-cases.controller.ts`** — `@PortalRoute()`, `@Resource({ type: 'portal_case', action:
'read' })`, `GET /portal/v1/cases` returning `{ cases, last_successful_sync_at }`. The sync time
comes from `platform.adapter_health_log`'s latest `last_successful_sync_at` for the court; CONTEXT:

**There is deliberately no search endpoint and no by-identifier lookup on the case list.** Flow-08

<objective>
Build the third instance of the project's registry pattern: workspaces declare named slots, modules
register panels into them **together with the entitlement required to see them**, and nothing in
Phase 4 has to be edited when Phases 5 to 8 fill their slots.

Purpose: CONTEXT is explicit about both the mechanism and the reason. **"A workspace slot registry,
following the same inversion-of-control pattern as Phase 2's search object-type registry and Phase
3's timeline provider registry … a module registers a panel component into a slot together with the
entitlement required to see it."** And: *"This is the whole reason for the registry: the four
workspace files must not become a merge point four later phases all have to touch."*

The entitlement half is the structural answer to F11's validation clause — *"component visibility
reflects entitlement, not just role label"* — which CONTEXT says is *"satisfied structurally rather
than by discipline"* precisely because the gate lives on the registration rather than inside each
component.

CONTEXT also requires that **"a later phase registering an UNDECLARED slot is a detectable
deviation rather than silent drift"**, and that coverage is *"a build-time report"* rather than a
"coming soon" box. This plan provides all three detection layers: the type, the runtime throw, and
the report.

Output: the registry, its contracts, the coverage script, and the CI step that runs it.
</objective>

`workspace.types.ts` — the two registration interfaces exactly as in the integration contract.

Three design points that need comments in the file, because each one is a decision a later reader
could otherwise reverse:

1. **`requiredEntitlement` is required, and `null` is a deliberate value, not a default.** Make it
   `string | null` rather than optional. An author who has not thought about the gate has to type
   `null` and will be asked why in review. This is the field that makes F11's entitlement-not-role
   rule structural.

2. **`component` is a `React.LazyExoticComponent`.** Two reasons, both worth stating:
   `TechArch/05-tech-stack.md` §8.1 calls for *"per-workspace bundle splitting"* so the Deputy
   interface ships a minimal bundle; and the build-time coverage script must be able to import the
   registration modules in plain Node without pulling React components, USWDS CSS or the generated
   API client into the process. Lazy references keep the registration file a data file.

3. **`SurfaceKind`.** CONTEXT: *"'Workspace panel' vs 'global chrome' becomes an explicit property
   each surface declares, rather than an accident of where it was built."* `global_chrome` surfaces
   — the header search input, the notification inbox, account/session — are reachable from **every**
   workspace regardless of role, and are rendered by the header, never by a workspace home. Write
   that sentence next to the type.

`panel.registry.ts` — a module-scoped store, two maps keyed by registration id plus an index by
slot. Behaviour:

- **`registerPanel(r)`**
  - Looks `r.slot` up in `WORKSPACE_SLOT_CATALOGUE`. Not found → `throw new Error('REGISTRY_UNDECLARED_SLOT: ' + r.slot + ' …')` naming the catalogue file and telling the caller to declare the slot there first. This is detection layer two; the `SlotId` type is layer one and the coverage script is layer three. Belt, braces and a second belt, because CONTEXT asks specifically that an undeclared slot be *detectable*.
  - Slot found but `state === 'v2_excluded'` → throw. A v2-excluded slot *"never renders and never counts as missing coverage"*; registering into one is a scope breach, and the throw says so by name.
  - Duplicate `id`, or a second panel at the same `(slot, order)` → throw `REGISTRY_DUPLICATE`.
  - Multiple panels in one slot at **different** orders is permitted — CONTEXT leaves *"whether a slot may hold more than one panel"* to judgment, and permitting it costs nothing while forbidding it would force a later phase to invent a sibling slot.

- **`registerNavEntry(r)`** — duplicate id throws. No slot involvement: navigation and panel
  registration are orthogonal facets of the registry, and a surface that is both (the Exception
  Queue is a Clerk panel *and* a Clerk nav entry) registers once in each, sharing an `id`. Comment
  why they are separate calls: they are owned by different Phase 4 plans and a single combined
  registration file would be edited by two plans at once, which is the file-ownership defect that
  blocked Phases 2 and 3.

- **`panelsForSlot(slot, hasEntitlement)`** — returns registrations whose
  `requiredEntitlement` is `null` **or** satisfied, sorted by `order`. The entitlement filter is
  **inside** the registry, not left to the caller, so a caller cannot forget it. Add the comment
  plan 01-13 put on `hasEntitlement`: this is UI gating only; the server re-validates every call and
  is the authority.

- **`slotsForWorkspace(w)`** — the catalogue's slots for that workspace in `order`, **including**
  unfilled and v2-excluded ones. The caller needs the full list to iterate; it renders nothing for a
  slot with no panels, which is how *"an unfilled slot renders no DOM at all"* is achieved without
  the renderer knowing anything about phases.

- **`navEntriesFor(w, hasEntitlement)`** — entries whose `workspace` is `w`, sorted by `order`,
  entitlement-filtered. Entries with `workspace: "all"` are **excluded** here: global chrome is the
  header's business, and returning it from a side-nav query is how a cross-role surface ends up
  duplicated in the nav.

- **`allRegistrations()`** and **`resetRegistryForTest()`** — the latter exists for the coverage
  script and for tests; mark it clearly as not for production use.

`apps/web/src/workspaces/README.md` — the document a Phase 5 author reads. Keep it short and
concrete: how to declare nothing (the slot is already in the catalogue), how to write a
`panel-registrations` module in your own phase's file, the three failure modes and their error
codes, the rule that **no Phase 4 file is edited**, and the rule that an unfilled slot renders no
DOM and must not be given a placeholder. Quote CONTEXT on the placeholder point —
*"No 'coming soon', no greyed box, no phase numbers. This is a federal judiciary application and
developer roadmap language has no place in its UI, even pre-release"* — because that is the
instruction most likely to be well-meaningly violated.

CONTEXT: *"The registry still holds the full catalogue, so a build-time coverage report answers
'which slots are empty' for the team"*, and the report must distinguish three states because
*"'empty because v2' and 'empty because Phase 5 hasn't run' are completely different facts, and a

`apps/web/scripts/workspace-coverage.ts`, run with `tsx`:

1. Import `WORKSPACE_SLOT_CATALOGUE` and `WorkspaceId` from `@judicialsync/config-schema`.
2. **Discover registration modules by glob**, not by a shared import list:
   `apps/web/src/workspaces/*-registrations.ts(x)`. This is the whole reason the discovery is a
   glob: `nav-registrations` is owned by plan 04-11 and `panel-registrations` by plan 04-12, and a
   hand-maintained import list would be a file two plans must edit. Dynamically `await import()`
   each match, in sorted order for determinism. Zero matches is **valid** — at this plan's wave
   there are none, and the report correctly says every slot is unfilled.
3. Read the registry with `allRegistrations()`.
4. Classify every catalogue slot:
   - `filled` — at least one panel registered;
   - `awaiting_phase_N` — `state: "awaiting_phase"` and no panel, reported with the expected phase;
   - `v2_excluded` — reported separately and **never counted as missing coverage**;
   - `UNFILLED_BUT_EXPECTED` — `state: "expected_filled"` and no panel registered. This is the state
     that means Phase 4 did not finish its own job.
5. Print a table grouped by workspace: slot id, title, owning feature, state, registering phase.
   Then a summary line per workspace and a totals line.
6. Write the same data as JSON to `apps/web/.workspace-coverage.json` so the assurance suite
   (proof 7) can assert the expected empty set against a machine-readable artifact rather than by
   scraping stdout. Add the file to `.gitignore` if the repository's convention is to ignore build
   outputs; otherwise commit it and let CI diff it — pick one and say which in the SUMMARY.
7. **Exit non-zero** on any of: an `UNFILLED_BUT_EXPECTED` slot; a registration naming a slot absent
   from the catalogue (caught by the registry's throw, re-reported here with the file that caused
   it); a duplicate id; a panel registered into a `v2_excluded` slot.
8. **Exit zero** when the only empty slots are `awaiting_phase` or `v2_excluded`. That is the normal,
   healthy state of this project between Phase 4 and Phase 8, and a script that failed on it would
   be turned off within a week.

Keep the script free of React, USWDS and the generated API client — the lazy `component` references
guarantee that, and the script must not defeat it by awaiting them.

`apps/web/package.json`: add `tsx` as a dev dependency and
`"workspace:coverage": "tsx scripts/workspace-coverage.ts"`. Do not add any other dependency.

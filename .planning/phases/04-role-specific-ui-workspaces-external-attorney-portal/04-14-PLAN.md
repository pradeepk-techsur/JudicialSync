<objective>
Ship the named Phase 4 assurance suite: fourteen proofs, separately runnable, build-blocking, each
traced to a success criterion or a CONTEXT guarantee.

Purpose: CONTEXT makes it **"an explicit, named deliverable — fourth in the series after `01-14`,
`02-16` (7 proofs) and `03-18` (11 proofs)"**, and gives the reason bluntly: **"Two of Phase 4's
three criteria are *rejection* claims, which is exactly what quietly stops being true."** A feature
that regresses announces itself; a refusal that regresses does not.

The suite's hardest requirements are the ones that make the proofs resistant to rot:
**proof 1 enumerates the application's live route table at runtime rather than a maintained list**,
so Phase 5's ledger and Phase 7's calculations are covered the moment they are written;
**proof 3 asserts shape *and timing* indistinguishability and that the check order holds**; and
**proof 4 asserts not only the 403 but that no override mechanism exists anywhere in the codebase**,
which is the only way to prove a capability was not built.

Output: the harness, fourteen proof specs, the traceability spec, the criterion matrix, and the
assurance CI job.
</objective>

**Follow plans 02-16 and 03-18 exactly in structure**: a `phase4-harness.ts`, one spec file per
proof named `proof-N-{slug}.assurance-spec.ts`, a traceability spec, a dedicated
`jest.assurance.config.js` project entry, and a separate `assurance.yml` workflow. The suite is
**separately runnable** and is not folded into the feature test suites — that separation is what
makes it a deliverable a reviewer can point at.

**Proofs must not re-test what the feature specs already cover.** Each one targets a *claim*, and
most of them target a claim that is only interesting when someone has tried to break it. Where a
feature spec already asserts the behaviour, the assurance proof asserts the **structural property**
that keeps it true — the route table is enumerated rather than listed, the override is grepped for
rather than assumed absent, the timing distribution is sampled rather than eyeballed.

**Do not build here:** any feature, any fix. If a proof fails, the fix belongs in the plan that owns
the file, and that is a finding worth surfacing rather than patching from this plan.
</context>

**`phase4-harness.ts`** — the shape is in the integration contract. Four pieces need care:

- `portalToken()` / `internalToken()` obtain **real tokens from the two Keycloak realms** using the
  seeded credentials. Never hand-mint a JWT: a hand-minted token proves the guard rejects a token
  the guard itself defined, which is circular.
- `enumerateLiveRoutes()` reads the **running application's router** through the Nest HTTP adapter
  (`app.getHttpAdapter().getInstance()`), the same mechanism plan 04-09 used. Resolve it in one
  place and comment that it is adapter-internal, so a framework upgrade breaks one function rather
  than fourteen specs.
- `sampleTimings(fn, n)` returns raw per-call durations so a proof can compare distributions rather
  than single measurements.
- `repoGrep(pattern, globs)` searches **tracked source files** (use `git ls-files` so build output
  and `node_modules` are excluded). This is the mechanism for "this mechanism does not exist"
  proofs, and it must be a real search over the repository, not over an allowlist of files.

`jest.assurance.config.js` — add the Phase 4 specs to the existing project configuration; keep the
Phase 2 and Phase 3 entries intact.

**Proof 1 — a portal token is rejected by EVERY internal route.** Criterion 3.
- Enumerate the live route table; partition into portal (`/portal/v1/*`) and internal.
- **Assert the enumeration is non-trivial**: the internal count is at least the number of paths in
  `openapi/openapi.json` minus the portal ones, and above an absolute floor. A proof that silently
  enumerates zero routes passes vacuously, and that is the failure mode that would make the whole
  suite worthless.
- Fire a real portal token at every internal route with a method-appropriate request. Assert 403 on
  **all**, never 200, never 401, never 500.
- Fire a real internal token at every portal route except the public authentication routes. Assert
  403 — the boundary is symmetric.
- **Control:** the same internal routes with a valid internal token do not all 403; at least one
  returns a non-403. Without the control, a guard that denied everything would pass.
- **Forward-looking assertion:** if any enumerated route matches
  `/ledger|/exhibits|/calculation|/trackers|/integrations\/cmecf\/outbound/i`, assert it was in the
  internal partition and was covered. Today that matches only the CM/ECF outbound route; as Phases 5
  to 8 land, the proof strengthens with no edit. Print the matched set so a reviewer sees it grow.

**Proof 2 — a portal write against ledger, docket and calculation endpoints is refused at the API
layer, not merely absent from navigation.** Criterion 2.
- For every enumerated internal route with a mutating verb, a real portal token yields
  **403 `PORTAL_WRITE_DENIED`** — F12's own code and message.
- Specifically exercise the three classes F12 names, using whichever representatives exist today:
  docket (`POST /integrations/cmecf/outbound`, `POST /integrations/cmecf/sync`), calculation (none
  yet — assert explicitly that none exists and that the forward-looking assertion in proof 1 covers
  it), and ledger (none yet — same).
  **Record the absences in the test output rather than skipping them**, so the proof reads as "these
  do not exist yet and are covered structurally" rather than as silent partial coverage.
- Assert the refusal is at the API layer by driving it with `fetch`/supertest, **never through the
  portal UI** — CONTEXT: *"rejected at the API layer — not merely absent from the portal's
  navigation."*

**Proof 3 — not-party-of-record is a 404 indistinguishable from a nonexistent case, and the check
order holds.** Criterion 2 and `Y2` Principle 3.
- For each of the three portal `caseId` endpoints, compare the response to `unassociatedCaseId`
  against the response to `nonexistentCaseId`: identical status, identical application-set headers,
  and **identical raw body strings**.
- **Timing:** `sampleTimings` at least 40 interleaved calls of each kind, discard a warm-up window,
  and assert the medians differ by less than a documented tolerance and the distributions overlap at
  the p90. Document the tolerance and the reasoning inside the test — a flaky timing assertion that
  gets skipped is worse than none, so choose a band stable on a two-core sandbox yet tight enough to
  catch an extra database round trip.
- **The check order:** `sealedCaseId` requested by an attorney who is **not** a party returns 404,
  byte-identical to the nonexistent case — never 403. CONTEXT: *"Reversing the order would leak
  sealed-case existence to non-parties, the worst outcome available here."* Title the test so it
  cannot be mistaken for a duplicate.
- Assert at the **policy** layer too: evaluate the PDP input directly and confirm
  `PORTAL_NOT_PARTY_OF_RECORD` outranks `PORTAL_DESIGNATION_DENIED` in the returned
  `reason_code`, with `hide_existence: true`. The ordering must hold in Rego as well as in the
  service, because either one changing alone is the regression.

**Proof 4 — a party-of-record attorney on a sealed case receives 403, and no override mechanism
exists anywhere.**
- The attorney who **is** a recorded party on `sealedCaseId` receives `403
  PORTAL_DESIGNATION_DENIED` on all three portal endpoints.
- Granting that attorney's principal every entitlement in the catalogue changes nothing — attempt it
  through the real grant path and assert either that the grant is refused or that the 403 still
  holds.
- Publishing the widest legal `portal_visibility` changes nothing.
- All five designation values deny.
- **The mechanism does not exist:** `repoGrep` over tracked sources for
  `/portal_authorized|designation_override|individually_authoriz|portal_exempt|bypass_designation/i`
  returns **only** matches inside comments, documentation and this proof itself — assert there is no
  match in an executable position in `apps/api/src/`, `policy/`, `apps/web/src/` or
  `apps/portal/src/`. CONTEXT: *"no override mechanism exists anywhere in the codebase."* This is the
  only way to prove a capability was not built, and it is why the grep is over the repository rather
  than over a list.

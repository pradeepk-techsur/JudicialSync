<objective>
Answer one question for the browser — *where does this user land, and what else may they switch to?*
— from the same role map the browser itself imports, and persist a preference that can never point
somewhere the user cannot reach.

Purpose: CONTEXT locks the behaviour precisely. *"On login: route to the stored
`workspace_preference` if set AND still mapped to one of the user's current roles; otherwise fall
back to the default for their primary role, **silently rather than erroring**."* And:
*"**The validate-on-read step is the load-bearing part** — without it, a user whose roles change is
stranded on a workspace they can no longer use, and the stale value needs an administrator to clear."*

It also locks the one role that lands nowhere: *"`jury_admin` → **NO v1 workspace**… The API returns
F11's `403 UI_NO_WORKSPACE_ASSIGNED`, but **the user gets a properly rendered page** carrying the
'contact an administrator' path — not a raw error."* That split of responsibilities is why the API
returns the FRD's exact message string: the client renders it, rather than composing its own.

And it locks what this endpoint is **not**: *"Role selects the frame; entitlement fills it. Role
grants NOTHING."* This endpoint hands back a layout choice. It confers no access, and the comment
saying so belongs in the service.

Output: `GET /users/me/workspace`, `PATCH /users/me/workspace-preference`, and the tests that pin
the fallback rule.
</objective>

<feature_dependencies>

**`Y1a-api-shared.md` §UI Workspaces** specifies exactly one endpoint:
`PATCH /users/me/workspace-preference` with body `{workspace_preference}` returning `200`.
`GET /users/me/workspace` is a **Phase 4 addition** — the client cannot apply the validate-on-read
rule without asking the server, and duplicating the rule in the browser would defeat the point of
the shared map. Plan 04-10 registers it as a deviation.

**`users.workspace_preference TEXT`** already exists (`Y0a-schema-shared.md` §Identity line 13,
`TechArch/02a-data-shared.md` §5.2). It is a nullable `TEXT` column with **no CHECK constraint** —
which is exactly why validate-on-read is required rather than optional, and why this plan does not
add one: a constraint would turn a role revocation into a database-level inconsistency rather than a
recoverable UI state.

**Court-configurability of the role map** is listed in CONTEXT's discretion items with the answer
embedded: *"fixed is the safe default and nobody has asked for it."* Ship it fixed, from
`@judicialsync/config-schema`. Note in the SUMMARY that making it configurable later is a
`ConfigResolver` key plus a merge, not a redesign.

**Do not build here:** any UI, any registry, any portal route.

**`resolveForUser(userId)`**:
1. Read the principal's current roles through plan 01-06's `EntitlementResolverService` — **not** by
   querying `user_roles` directly. The resolver is the one place that knows about Redis caching and
   invalidation on grant change, and CONTEXT's open question *"what happens to an open session when
   a role is revoked mid-session"* is already answered by Phase 1: a role or scope change revokes
   active sessions, so the next request re-authenticates and this endpoint sees the new roles. Write
   that as a comment so nobody adds a second staleness mechanism here.
2. Read `users.workspace_preference`.
3. Call `resolveWorkspace({ roles, storedPreference })` from `@judicialsync/config-schema`.
   **Import it; do not reimplement it.** The whole point of plan 04-03 is that the API and the
   browser cannot disagree about where a role lands.
4. On `{ workspace: null, source: "unmapped" }` return `null`; the controller turns that into 403.
5. Otherwise build the response: `workspace`, `home_route` from `WORKSPACE_HOME_ROUTE`,
   `shell_variant` from `WORKSPACE_SHELL_VARIANT`, `source`, and `available_workspaces` — each entry
   carrying its `workspace`, a human label, and its `home_route`, in `available` order.
6. **Do not rewrite a stale stored preference.** Add the comment plan 04-03 asks for: a role may be
   restored, and silently overwriting a user's expressed preference because of a temporary
   revocation is a worse failure than falling back for a while.

The workspace labels are UI copy and must follow `02-UI-SPEC.md`'s copywriting contract: sentence
case, no roadmap language, no abbreviations a court user would not use. Use the mockups' own names —
*Chambers Oversight*, *Clerk Console*, *Courtroom Deputy*, *Admin Dashboard* — so the switcher names
match the page titles a user already sees.

**`setPreference(principal, pref)`**:
1. Resolve the user's `available` workspaces as above.
2. `available` empty → throw `403 UI_NO_WORKSPACE_ASSIGNED`. A user with no workspace cannot have a
   preference.
3. `pref` non-null and not in `available` → throw `422 UI_WORKSPACE_NOT_MAPPED` with
   *"That workspace is not available for your roles"*. `Y2-errors.md` assigns 422 to
   *"validation/business-rule failures"*, which this is: the value is well-formed but not permitted
   for this subject. It is **not** 403 — the user is authorized to set their own preference; this
   particular value is simply invalid. Make that distinction a comment, because 403 is the lazy
   reach here and it would make the client show an authorization error for a UI choice.
   This is also the server-side half of CONTEXT's *"cross-workspace viewing not permitted in v1"*:
   the switcher only lists mapped workspaces, and the stored value can never become an unmapped one.
4. `pref` null → clear the preference. A user who wants the default back must be able to say so.
5. Write the update **through plan 01-05's `withAudit`**, so the `users` row change and its
   `audit_events` row commit atomically. `action_type: "config_change"` if that is the closest value
   in plan 01-05's `AuditActionType` union, otherwise the nearest existing member — **do not add a
   new action type** without recording it as a deviation; read the union before choosing.
   `object_type: "user_workspace_preference"`, `object_id`: the user id, `before_state` /
   `after_state`: the old and new values. A workspace preference is not legally significant, but it
   is a user-state change and F02's rule is that material actions are logged; logging it costs one
   line and makes "why did this user land here" answerable.
6. Return the freshly resolved workspace, so the client does not need a second round trip.

`identity.module.ts`: register `WorkspaceService` and (in Task 2) `WorkspaceController`. Do not
touch any other provider.

`dto/workspace.dto.ts`: zod schemas for the request body and both responses, following plan 01-06's
DTO conventions, plus the two error-code constants. `workspace_preference` validates against the
`WorkspaceId` union imported from the shared package — a typo in the body is a 400 from the pipe,
not a stored garbage value.

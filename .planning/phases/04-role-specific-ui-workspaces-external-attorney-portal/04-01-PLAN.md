<objective>
Create the durable record the external attorney portal writes into, and widen the two Phase 1 tables
that assume every actor is an internal court user.

Purpose: CONTEXT locks the fourth use of the project's *"write the durable record now, the consumer
arrives later"* pattern — **"Submissions land in a portal-local staging table with
`submitted_via='external_portal'`, status `pending_review`, submitting identity, full F02 audit
entry. Phase 5's F15 DRAINS it."** It equally locks the rejection: *"writing directly into Phase 5's
`exhibits` table — that table does not exist and Phase 5 owns its schema; defining it here is the
single-owner violation that produced blockers in both Phase 2 and Phase 3 planning."*

The actor widening is forced by F12's validation clause — *"All external submissions are immutably
logged with `submitted_via = 'external_portal'` and **the submitting attorney's identity**, feeding
the same audit trail (F02) as internal submissions"* — against
`TechArch/02a-data-shared.md` §5.4, which declares `actor_id UUID NOT NULL REFERENCES users(id)`.
A sentinel internal user would make the audit trail state something false about who acted, in a
record the PRD requires to be suitable for appellate review. This is the one place Phase 4 touches
Phase 1's immutability core, and it does so with both hash implementations moving together.

Output: `external_principals`, `portal_submissions`, the widened actor columns, the recomputed hash
function, and the re-run Phase 1 parity corpus.
</objective>

**`portal_submissions` — the Phase 4 staging table:**

```sql
CREATE TABLE platform.portal_submissions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  external_principal_id UUID NOT NULL REFERENCES platform.external_principals(id),
  case_id UUID NOT NULL REFERENCES platform.cases(id),
  submitted_via TEXT NOT NULL DEFAULT 'external_portal'
    CHECK (submitted_via = 'external_portal'),
  status TEXT NOT NULL DEFAULT 'pending_review'
    CHECK (status IN ('pending_review','drained')),
  exhibit_description TEXT NOT NULL,
  offering_party TEXT NOT NULL CHECK (offering_party IN ('government','defense')),
  exhibit_type TEXT NOT NULL,
  file_reference_id UUID REFERENCES platform.file_references(id),
  correction_of_submission_id UUID REFERENCES platform.portal_submissions(id),
  drained_at TIMESTAMPTZ,
  drained_into_object_type TEXT,
  drained_into_object_id UUID,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_portal_submissions_status ON platform.portal_submissions(status);
CREATE INDEX idx_portal_submissions_case ON platform.portal_submissions(case_id);
CREATE INDEX idx_portal_submissions_principal ON platform.portal_submissions(external_principal_id);

-- A submission is a durable record of what an external party asserted at a point in time.
-- The attorney cannot edit or withdraw it (CONTEXT defers tracking/withdrawal), and Phase 5's F15
-- intake DRAINS it rather than mutating its content.
REVOKE UPDATE, DELETE ON platform.portal_submissions FROM app_rw;
GRANT  SELECT, INSERT ON platform.portal_submissions TO app_rw;
GRANT  SELECT, INSERT, UPDATE ON platform.external_principals TO app_rw;
```

**`status` and the drain columns are a deliberate problem.** `REVOKE UPDATE` means `app_rw` cannot
set `status='drained'` either — which is correct for Phase 4 (nothing drains yet) but would block
Phase 5. Resolve it the way Phase 1 resolved audit immutability: keep `REVOKE UPDATE, DELETE` and
add a **narrowly-scoped `SECURITY DEFINER` function** owned by `app_dba`:

```sql
CREATE OR REPLACE FUNCTION platform.mark_portal_submission_drained(
  p_submission_id UUID, p_object_type TEXT, p_object_id UUID
) RETURNS void LANGUAGE plpgsql SECURITY DEFINER AS $$
BEGIN
  UPDATE platform.portal_submissions
     SET status = 'drained', drained_at = now(),
         drained_into_object_type = p_object_type, drained_into_object_id = p_object_id,
         updated_at = now()
   WHERE id = p_submission_id AND status = 'pending_review';
  IF NOT FOUND THEN
    RAISE EXCEPTION 'PORTAL_SUBMISSION_NOT_PENDING';
  END IF;
END; $$;
REVOKE ALL ON FUNCTION platform.mark_portal_submission_drained(UUID, TEXT, UUID) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION platform.mark_portal_submission_drained(UUID, TEXT, UUID) TO app_rw;
```

The function is the **only** way a submission's content changes, and it can only move
`pending_review → drained`. Phase 5 calls it; Phase 4 never does. Record in `docs/SCHEMA-NOTES.md`
that this is the drain seam and that no other write path exists.

Add the two Prisma models to `apps/api/prisma/schema.prisma` with `@@schema("platform")` (or the
mapping convention Phase 1 established — follow `docs/SCHEMA-NOTES.md`, do not invent a second
convention). Mark the generated model fields so Prisma does not attempt an `UPDATE` on
`portal_submissions`; a comment above the model naming the revoked grant is sufficient, because the
database is the enforcement point, not the ORM.

`<>` on two booleans is XOR: exactly one actor, never neither, never both. This is the structural
guarantee that replaces the dropped `NOT NULL` — the column is not merely nullable, it is
*alternatively* populated.

**The hash function must move with it.** Plan 01-03 created `platform.compute_audit_row_hash` and the
`BEFORE INSERT` trigger; plan 01-05 created the byte-identical TypeScript twin in
`canonical-payload.ts` with a parity fixture corpus. Both canonicalise a field list. Adding a column
changes that list.

In the same migration, `CREATE OR REPLACE` `platform.compute_audit_row_hash` with
`actor_external_principal_id` inserted into the canonical field order **immediately after
`actor_id`**, serialised as the empty string when null — exactly the null convention plan 01-05 chose
for the other nullable fields (read the existing function before writing; do not guess the
delimiter, the ordering, or the null encoding). Then update `buildCanonicalPayload` in
`apps/api/src/modules/audit/canonical-payload.ts` identically.

**Do not re-key existing rows and do not add a backfill.** `actor_external_principal_id` is null on
every pre-Phase-4 row, and the null encoding must be chosen so that a null column contributes the
same bytes it would have contributed had the field never existed — i.e. append it at a position and
with an encoding that leaves previously-computed hashes valid, or, if that is impossible with the
Phase 1 delimiter scheme, state so explicitly in `docs/SCHEMA-NOTES.md` and have the migration
**recompute and rewrite the whole chain** as `app_dba` in a single transaction, re-verifying the
result. Pick one, prove it with the parity corpus and the chain-integrity test, and record which.
Silently invalidating the chain is the one outcome that is not acceptable — the integrity
verification job raises a P0 on exactly this.

<objective>
Create the durable record the external attorney portal writes into, and widen the two Phase 1 tables
that assume every actor is an internal court user.

Purpose: CONTEXT locks the fourth use of the project's *"write the durable record now, the consumer
arrives later"* pattern — **"Submissions land in a portal-local staging table with
`submitted_via='external_portal'`, status `pending_review`, submitting identity, full F02 audit
entry. Phase 5's F15 DRAINS it."** It equally locks the rejection: *"writing directly into Phase 5's
`exhibits` table — that table does not exist and Phase 5 owns its schema; defining it here is the
single-owner violation that produced blockers in both Phase 2 and Phase 3 planning."*

The actor widening is forced by F12's validation clause — *"All external submissions are immutably
logged with `submitted_via = 'external_portal'` and **the submitting attorney's identity**, feeding
the same audit trail (F02) as internal submissions"* — against
`TechArch/02a-data-shared.md` §5.4, which declares `actor_id UUID NOT NULL REFERENCES users(id)`.
A sentinel internal user would make the audit trail state something false about who acted, in a
record the PRD requires to be suitable for appellate review.

This is the one place Phase 4 touches Phase 1's immutability core, and **Phase 2 already wrote the
rule for how to do it**: when a hashed field list must grow, you add a version — you never edit an
existing one. Plan 02-01 added `compute_audit_row_hash_v2` beside a frozen v1 and left a dispatcher
that routes each row to the function it was written under; plan 02-04 mirrored that in TypeScript
and put the instruction in a comment on v1: *"If a field must be added, add version 3; never edit 1
or 2."* **This task is that version 3.** Nothing is re-keyed, nothing is rewritten, and every
pre-Phase-4 row keeps verifying under the function it was hashed with.

The session widening rides along because it is the same shape of problem with none of the risk:
`platform.sessions` is not hash-chained, and one session table means Phase 1's
immediate-revocation guarantee extends to external principals through one mechanism rather than two
that can drift.

Output: `external_principals`, `portal_submissions`, hash field list version 3, the widened actor,
uploader and session columns, and the re-run parity corpus across all three versions.
</objective>

**`status` and the drain columns are a deliberate problem.** `REVOKE UPDATE` means `app_rw` cannot
set `status='drained'` either — which is correct for Phase 4 (nothing drains yet) but would block
Phase 5. Resolve it the way Phase 1 resolved audit immutability: keep `REVOKE UPDATE, DELETE` and
add a **narrowly-scoped `SECURITY DEFINER` function** owned by `app_dba`:

```sql
CREATE OR REPLACE FUNCTION platform.mark_portal_submission_drained(
  p_submission_id UUID, p_object_type TEXT, p_object_id UUID
) RETURNS void LANGUAGE plpgsql SECURITY DEFINER AS $$
BEGIN
  UPDATE platform.portal_submissions
     SET status = 'drained', drained_at = now(),
         drained_into_object_type = p_object_type, drained_into_object_id = p_object_id,
         updated_at = now()
   WHERE id = p_submission_id AND status = 'pending_review';
  IF NOT FOUND THEN
    RAISE EXCEPTION 'PORTAL_SUBMISSION_NOT_PENDING';
  END IF;
END; $$;
REVOKE ALL ON FUNCTION platform.mark_portal_submission_drained(UUID, TEXT, UUID) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION platform.mark_portal_submission_drained(UUID, TEXT, UUID) TO app_rw;
```

The function is the **only** way a submission's content changes, and it can only move
`pending_review → drained`. Phase 5 calls it; Phase 4 never does. Record in `docs/SCHEMA-NOTES.md`
that this is the drain seam and that no other write path exists.

Add the two Prisma models to `apps/api/prisma/schema.prisma` with `@@schema("platform")` (or the

convention). Mark the generated model fields so Prisma does not attempt an `UPDATE` on
`portal_submissions`; a comment above the model naming the revoked grant is sufficient, because the

**This task is that version 3.** Do **not** `CREATE OR REPLACE` `compute_audit_row_hash` or
`compute_audit_row_hash_v2`, and do **not** rename either. Editing either one retroactively changes
the expected hash of every row already written under it — the false chain break the integrity job

null-encoding trick that avoids this and there is no chain-rewrite fallback: Phase 1 revoked

**Add a version. That is the whole answer.**

`<>` on two booleans is XOR: exactly one subject, never neither, never both. That is the structural
guarantee replacing each dropped `NOT NULL` — the column is not merely nullable, it is
*alternatively* populated.

**2. Add hash field list version 3 — a strict extension of v2.** Read plan 02-01's migration
`20260201000100_audit_provenance_hash_v2` first and reproduce its delimiter, its NULL encoding and
its exact v2 argument order; the SQL is authoritative over any list written in a plan.

```sql
CREATE OR REPLACE FUNCTION platform.compute_audit_row_hash_v3(
  p_actor_id UUID, p_action_type TEXT, p_object_type TEXT, p_object_id UUID,
  p_before_state JSONB, p_after_state JSONB, p_rule_version_ref UUID,
  p_calculation_version_ref UUID, p_rule_package_version_id UUID,
  p_client_ip TEXT, p_session_id UUID, p_occurred_at TIMESTAMPTZ,
  p_hash_field_list_version SMALLINT,
  p_actor_external_principal_id UUID,
  p_prev_hash TEXT
) RETURNS TEXT LANGUAGE sql IMMUTABLE AS $$
  SELECT encode(digest(
    -- EXACT v2 field order and delimiter, copied from migration 20260201000100, then the one v3
    -- field APPENDED after hash_field_list_version and BEFORE prev_hash.
    ... || '|' || coalesce(p_actor_external_principal_id::text,'')
        || '|' || p_prev_hash,
    'sha256'), 'hex');
$$;
```

**Appended, not inserted mid-list.** The earlier draft of this plan placed the field "immediately
after `actor_id`", which would have changed every v2 digest as well and broken Phase 2's
"v2 is a strict extension of v1" invariant. Position matters as much as presence.

**3. Bump the insert floor and extend the dispatcher and the trigger.**

```sql

RETURNS SMALLINT LANGUAGE sql IMMUTABLE AS $$ SELECT 3::smallint $$;
```

Set the column default: `ALTER TABLE platform.audit_events ALTER COLUMN hash_field_list_version SET

**4. No backfill, no re-keying, no rewrite.** Every pre-Phase-4 row keeps the version it was written

<objective>
Build the thing an external attorney actually uses: a structurally separate application with its own
chrome, its own login against its own realm, a case list that can only contain cases they are a
party to, a submission form that enters the standard review path, and a read-only deadline summary
that tells the truth when there is nothing to show.

Purpose: CONTEXT locks the separation as a property of the artifact, not only the token — **"a
separate `apps/portal` build alongside `apps/web`, sharing the USWDS design system and the generated
OpenAPI client types through the monorepo — but shipping no internal shell, no internal routes and
no internal copy in the external bundle"** — so that *"'structurally separate' becomes true of the
artifact an external user can actually download and inspect."*

It locks the Speedy Trial screen shipping for real: *"With no tracker data in the system the
endpoint returns an empty result and the screen renders 'No deadline information is available for
this case' — which is **literally true**: the system holds no Speedy Trial calculation because none
has been created."*

And Screen-19 and Flow-08 lock the two structural absences: *"there is no search box that could be
used to probe for other cases' existence"*, and *"Attempt to self-accept own submission → No such
control exists anywhere in this portal."*

Output: the portal application, its Docker image, its Playwright suite with a real external-realm
login fixture, and the build-blocking accessibility gate.
</objective>

**`02-UI-SPEC.md` is the approved, binding design contract** and applies in full to the portal: the
six-step spacing scale, the type tokens, the colour budget with accent reserved for the listed uses,
**one primary button per page-level region and zero in repeating rows**, the copywriting contract,
and the prohibition on hand-entered hex and custom CSS. Two of its open findings matter here:
- **D-1** — USWDS 3.x ships no Tabs component. **No portal screen uses a tab strip**; Screen-19 is a
  card list plus an inline form and Screen-20 is a summary box plus a table. If a tab is ever
  wanted, reuse the contract's `ConfigSectionTabs` decision rather than inventing a second approach.
- **D-2 / D-11** — a conditionally-blocked control uses `aria-disabled` plus a no-op handler plus
  permanent visible helper text, never the `disabled` attribute. The submission form's submit button
  is exactly this case.

**Playwright pinned to 1.63.0.** The sandbox pre-installs Chromium for exactly that version at
`$PLAYWRIGHT_BROWSERS_PATH`. **Never add a `playwright install` step.** `workers: 1` — the sandbox
has two cores and each worker is a browser.

**Do not build here:** anything under `apps/web`, any internal route, any API change, any submission
tracking, withdrawal or outcome notification (CONTEXT defers all three), any case search.

**`AssociatedCaseList.tsx`** — `GET /portal/v1/cases` through the generated portal client with
TanStack Query. One USWDS `Card` per case: caption, case number, the attorney's `party_role`, and
two actions — **"Submit Exhibit Metadata"** (expands the form inline) and **"View Speedy Trial
Summary"** (links to Screen-20).

Per `02-UI-SPEC.md`'s one-primary rule, these are **repeating list rows**, so both card actions are
`usa-button--outline` or links. **Zero primary buttons in the card list.**

Render `last_successful_sync_at` as a plain line beneath the list — CONTEXT: *"The portal's case
list shows the last successful sync time, turning 'my new case is missing' from an opaque failure
into something the attorney and the clerk they call can both reason about."* When it is null, say so
honestly rather than hiding the field. Add the comment that sync freshness is operational state,
not case data, and therefore discloses nothing.

Empty state: Screen-19's own wording, *"No cases are currently associated with your account."* This
is a **legitimate state** — an attorney whose identity has not yet been bound to a CM/ECF party
record, or who has no open matters — not an error. Per `02-UI-SPEC.md`, a blank region is never
acceptable; render a real USWDS Alert with the next step (contact the clerk's office).

**There is no filter, no sort control and no identifier input.** The list is the complete, pre-scoped
set. Comment it.

**`SubmissionForm.tsx`** — Screen-19's form, expanded inline below the selected case:
- `Description` — USWDS `TextInput`, required.
- `Offering party` — USWDS `Radio` group, `Government` / `Defense`, required.
- `Exhibit type` — USWDS `Select`, required.
- `Attach file (optional)` — USWDS `FileInput` with Screen-19's helper text
  *"malware-scanned, allowlisted types only"*. That sentence is **truthful** because plan 04-08
  routes the upload through Phase 1's real allowlist and ClamAV pipeline; say so in a comment so
  nobody weakens the server side and leaves the claim behind.
- The **"enters standard review" disclosure**, always visible, never behind a tooltip:
  *"This submission enters standard clerk review before it becomes part of the official record. You
  will be notified of the outcome."* Screen-19 specifies it as an always-visible info note.
  **Check the second sentence against reality before shipping it**: CONTEXT defers *"attorney
  submission tracking, withdrawal, and outcome notification"*, so a promise of notification would be
  false. Ship the first sentence verbatim and replace the second with a true statement — the clerk's
  office is the contact point — and **record the wording change in the SUMMARY** as a Screen-19 copy
  correction, since the project's rule is that deviating silently is the only forbidden kind.
- **"Submit for Review"** is the page's one primary button — the home page's single page-level
  primary, which is what the one-primary budget is for.

**The blocked-submit state uses D-2/D-11's pattern**: until the required fields are complete, the
submit control renders with `aria-disabled="true"`, a **no-op** handler, and **permanent visible
helper text** naming what is missing, associated by `aria-describedby`. Never the `disabled`
attribute — a `disabled` button is not focusable, so a keyboard or screen-reader user would never
learn why the primary action is blocked. The server's 422 remains the independent backstop.

Error handling, all through `PortalErrorAlert` branching on `error_code`:
- `INTAKE_MISSING_METADATA` → inline field errors.
- `SECURITY_FILE_TYPE_DENIED` / `SECURITY_MALWARE_DETECTED` → an inline error on the file field
  carrying the server's reason. Screen-19: *"File rejected: {reason}" — never silently accepted.*
- `SECURITY_SCANNER_UNAVAILABLE` (503) → an explicit *"your submission was not accepted"* message.
  The Phase 2 lesson applies: a failure that reads like a success is the dangerous one.
- `PORTAL_SUBMISSION_DISABLED` → a court has narrowed submission off; render the server's message
  and **do not render the form at all** when the case list indicates it.
- `404` → the server's message unchanged, composed by nobody.

On success: the form collapses and a confirmation shows *"Submitted — pending clerk review"*.

**There is no accept, approve, withdraw or edit control anywhere in this component or this
application.** Screen-19: *"No such control exists anywhere in this portal. Structural prevention."*
Comment it, because the structural claim is only true while it stays true.

**File bytes go through the application's own API.** The form posts `multipart/form-data` to

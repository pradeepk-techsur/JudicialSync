<objective>
Make the realm boundary structural: one guard, evaluated before anything route-specific, that
rejects a portal token on every internal route that exists or will ever exist — and the portal
authentication flow that mints those tokens in the first place.

Purpose: CONTEXT locks the mechanism and the reason it is a guard rather than a decorator. **"The
internal guard validates the token's audience/issuer BEFORE any route-specific logic. A portal token
is therefore rejected from every internal endpoint that exists or will ever exist — Phase 5's ledger
and Phase 7's calculations inherit the rejection the moment they are written, with nobody needing to
remember."** The rejected alternative is named: *"explicit deny lists on ledger/docket/calculation
endpoints. That is per-route opt-in, which Phase 1 rejected by name: 'a route that forgets the
decorator is silently open.'"*

It locks the proof too: **"The proof enumerates the application's live internal route table at
runtime and fires a portal token at every route, asserting 403 on all. This makes criterion 2
provable now despite most of its named target endpoints not existing yet."**

And it locks session coexistence: *"Two separately-named session cookies; the portal's is
path-scoped to `/portal` so it is never transmitted to internal routes at all. The audience guard
remains authoritative regardless of what arrives — authorization never depends on which cookie was
sent, so coexistence weakens nothing."*

This plan also owns the composition root. Plan 04-08 built the portal surface deliberately
unmounted; here it is mounted, behind the guard.

Output: `AudienceGuard`, the portal OIDC flow and path-scoped session, the `app.module` wiring, and
the runtime route-table proof.
</objective>

**Binding** (`TechArch/04-security.md` §7.1): *"Internal realm and external attorney portal realm
use **distinct OIDC client IDs** … so a portal-issued token is structurally rejected (invalid
audience claim) by any internal-only endpoint, **independent of any role-check bug**."* The phrase
"independent of any role-check bug" is why this is a separate guard rather than a condition inside
`SessionAuthGuard`.

**Binding** (plan 01-13, carried forward): **no guard acquires a path-based exemption list.** Route
classification is metadata — plan 04-08's `@PortalRoute()` — because a path list is where a future
authenticated route quietly lands.

**Do not build here:** any portal controller other than authentication (plan 04-08 owns them), any
UI, any policy rule.

**`audience.guard.ts`.** A `CanActivate` that runs before everything else:

1. Read the route's `PORTAL_ROUTE_KEY` metadata via `Reflector` (handler then class). Present →
   portal route. Absent → **internal route**. Comment the asymmetry: absence defaulting to internal
   means a forgotten decorator makes a portal route unreachable, which is loud, and never makes an
   internal route externally reachable, which would be silent.
2. Extract a credential: the `Authorization: Bearer` header **or** either session cookie. No
   credential → `return true` and let `SessionAuthGuard` own the 401. A guard that invents its own
   401 would give unauthenticated callers a different error shape depending on guard order, which is
   itself a small information leak and a large debugging annoyance.
3. Determine the credential's realm **from the token's validated `iss` and `aud`**, verified against
   the corresponding realm's JWKS — never from a header, a cookie name, or a client-supplied field.
   The cookie name is a hint for *which* validator to try first, nothing more; a token presented as
   a bearer must still be classified correctly. Comment that.
4. Decide:
   - portal realm + internal route + mutating verb (`POST`/`PUT`/`PATCH`/`DELETE`) →
     **`403 PORTAL_WRITE_DENIED`**, *"External users cannot modify the official record"* — F12's
     exact row, which is what makes criterion 2's *"rejected at the API layer"* literal.
   - portal realm + internal route + safe verb → **`403 AUTH_AUDIENCE_MISMATCH`** (new Phase 4 code,
     registered by plan 04-10).
   - internal realm + portal route → **`403 AUTH_AUDIENCE_MISMATCH`**. The boundary is symmetric;
     an internal session must not reach portal endpoints either, or a court employee could file an
     external submission in an attorney's name.
   - realm matches route → `return true`.
   - token fails validation against **both** realms → `return true`, so the session guard produces
     the ordinary 401. Do not special-case a malformed token here.
5. Every rejection writes an `access_attempt` audit event. For a portal principal that means
   `actor_external_principal_id`; for an internal principal, `actor_id`. If the principal cannot be
   resolved (a validly-signed token for a deleted principal), log the subject claim in the audit
   detail rather than failing the audit write — a denial that cannot be recorded must still be a
   denial.
6. **403, not 404.** These are realm boundaries, not object lookups: the caller already knows the
   route exists (it is published in the OpenAPI contract), so `Y2` Principle 3 puts this in the 403
   column. Existence-hiding applies to *objects*, and plan 04-08 handles that. Comment the
   distinction so the two rules are not confused later.

**`session-auth.guard.ts`.** Teach it the `PORTAL_ROUTE_KEY` metadata: on a portal route, validate
the portal session through `PortalSessionService` and attach a `PortalPrincipal` with
`realm: "portal"`; on an internal route, behave exactly as plan 01-06 built it, attaching
`realm: "internal"`. **No path list.** Keep the existing revocation check on both paths — Phase 1's
immediate-revocation guarantee applies to external principals too.

**`app.module.ts`.** Register `AudienceGuard` as an `APP_GUARD` **before** `SessionAuthGuard` and
`AbacGuard` in the providers array, and import `PortalAuthModule` (Task 2) and plan 04-08's
`PortalCapabilityModule`. Nest evaluates `APP_GUARD` providers in registration order, so the array
order *is* the "before any route-specific logic" guarantee — add a comment above it saying exactly
that, because reordering a providers array looks harmless.

5. A **control**: the same internal routes with a valid internal token do **not** all 403 — at least

**`portal-session.service.ts`:**
- Issue a short-lived signed session token for the external principal and persist a revocable
  session row. Phase 1's `platform.sessions` table has `user_id UUID NOT NULL REFERENCES users(id)`,
  so it cannot hold an external principal. Choose one and record it as a deviation through plan
  04-10: either a sibling `platform.portal_sessions` table, or widening `sessions` with the same XOR
  pattern plan 04-01 applied to `audit_events`. **Prefer widening** — one session table means one
  revocation mechanism, and Phase 1's immediate-revocation guarantee stays a single implementation
  rather than two that can drift. Whichever is chosen, the revocation check must run on **every**
  portal request exactly as it does for internal ones.
- The cookie: name from `PORTAL_SESSION_COOKIE_NAME`, **`Path=/portal`**, `HttpOnly`, `Secure`,
  `SameSite=Lax`. Comment both halves of CONTEXT's reasoning: the path scope means the browser never
  transmits it to an internal route, **and** the audience guard is authoritative regardless of what
  arrives, so coexistence weakens nothing. `SameSite=Lax` rather than `Strict` because the OIDC
  redirect returns by top-level navigation.
- `HttpOnly` is deliberate and differs from `apps/web`'s bearer-token transport. State why: the
  portal is the surface exposed to an untrained, non-employed population, where an XSS-readable
  token is a materially worse outcome, and the portal has no cross-origin API to call.

**`portal-auth.service.ts` and `portal-auth.controller.ts`** — the four routes from the integration
contract. The controller carries `@PortalRoute()`; the three pre-session routes additionally carry
plan 01-01's `@Public()` so `SessionAuthGuard` lets them through.

On `POST /portal/v1/auth/login`:
1. Exchange the code; validate `state`, PKCE and the assertion server-side.
2. **Require MFA.** The portal realm requires TOTP; verify the assertion evidences it, exactly as
   plan 01-06 does for internal users. There is **no bypass flag and no second login path** — the
   same sentence Phase 1 wrote, applied here.
3. Resolve the `external_principals` row by `external_idp_subject`. Not found, or
   `status = 'disabled'` → **`401 PORTAL_AUTH_FAILED`** with F12's message *"Authentication failed;
   please sign in again"*. Do **not** auto-provision a principal on first login: enrolment is an
   administrative act, and an auto-created principal would have no `cmecf_party_external_id` and so
   no associations — a confusingly empty portal instead of a clear refusal. Record the no-auto-
   provision decision and the enrolment gap as an `[ASSUMPTION]` through plan 04-10, since the
   source material specifies no enrolment path.
4. Issue the session, set the cookie, `204`.
5. **Audit every outcome** — success, failed assertion, unknown principal, disabled principal,
   logout — through plan 01-05's `withAudit` with `actor_external_principal_id` where a principal
   resolved, mirroring plan 01-06's internal coverage.

`GET /portal/v1/auth/me` returns only `external_principal_id`, `display_name`, `bar_number`. **No
entitlements array, no roles array, no scopes.** An external principal holds none; returning an
empty array would invite a client to start gating on it. Comment that.

`docs/IDP-INTEGRATION.md` — add a portal section: the two realms, their issuers and audiences, why

and the no-auto-provision rule.

8. Each outcome in cases 1–4 and 6 produced an `audit_events` row.

<objective>
Stand up the structural half of the portal's separation: a second Keycloak realm with its own
issuer, audience, user store and MFA policy, and a separately-built `apps/portal` application served
behind the same TLS origin.

Purpose: CONTEXT locks **"A separate Keycloak realm for external principals. Different issuer as
well as audience, its own user store, its own password and MFA policy, no shared session or SSO
state with internal users."** The reasoning is F12's defence-in-depth clause — safe *"even if an
endpoint's authorization check were misconfigured"* — which *"is only fully true when a
misconfiguration inside one realm cannot mint a token the other accepts."* Criterion 3's wording is
literally *"cross-realm"*.

It equally locks the frontend half: **"A separate `apps/portal` build alongside `apps/web`, sharing
the USWDS design system and the generated OpenAPI client types through the monorepo — but shipping
no internal shell, no internal routes and no internal copy in the external bundle"** — so that
*"'structurally separate' becomes true of the artifact an external user can actually download and
inspect, not just of the token it carries."* And it locks the rejection of a separate domain:
Phase 1 *"deliberately put the whole stack behind one TLS origin, and no court has specified a
hostname."*

Output: the external realm definition, the `portal` Compose service and both proxy routes, the
`apps/portal` workspace build configuration and shared USWDS theme, the import firewall, and a smoke
check proving the two realms mint structurally distinct tokens.

**Scope boundary within the phase:** this plan ships the realm, the topology and the build
configuration. **Plan 04-13 owns every line of the portal application** — `index.html`,
`Dockerfile.portal` and all of `apps/portal/src/*.tsx` — so that no file in this phase has two
owners. A scaffold that writes a placeholder page which a later plan replaces is two owners of one
file, which is exactly the defect class that produced blockers in Phases 2 and 3.
</objective>

  rely on a default.

  internal realm's shape, with OTP **required** — `TechArch/04-security.md` §7.1 says
  court-configurable with default required for this realm, and default-required is what we ship.
  CONTEXT leaves *"attorney enrolment, credentialing and MFA policy in the external realm"* to
  planning judgment: ship required TOTP, a password policy at least as strict as the internal
  realm's, and record both choices in the SUMMARY.
- **Its own session policy.** Set `ssoSessionIdleTimeout` and `ssoSessionMaxLifespan` shorter than
  the internal realm's (external counsel are not court staff on a managed device) and
  `accessTokenLifespan` to the 5–15 minute band `TechArch/04-security.md` §7.1 specifies. There is
  no identity brokering, no `IdentityProvider` entry, and no shared SSO cookie with the internal
  realm — Keycloak realms are isolated by construction, which is exactly why CONTEXT chose a realm
  over a second client in the same realm.
- **At least two seeded attorney users**, each with a password and a pre-provisioned `otp`
  credential whose Base32 secret is a literal in this file, so plan 04-13's Playwright login fixture
  can compute a code the way plan 01-13's `totp.ts` does for internal users. Plan 04-05 creates the
  matching `external_principals` rows and documents the credentials; keep the usernames stable and
  name them in the SUMMARY so 04-05 can match them.
  - one attorney who is a party of record on an ordinary case,
  - one attorney who is a party of record on a **sealed** case (assurance proof 4 needs this user to
    exist with a real login).
- **No realm roles, no client roles, no groups.** An external principal's authority comes from the
  realm it authenticated against plus the CM/ECF-sourced party association — never from a claim. If
  a role existed here, someone would eventually read it.

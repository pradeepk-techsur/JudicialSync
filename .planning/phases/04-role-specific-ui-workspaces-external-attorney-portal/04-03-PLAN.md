package they already share: the role→workspace map, the complete workspace slot catalogue, and the
portal visibility policy with its unwaivable floor.

exactly this — `@judicialsync/config-schema`, *"a package both the NestJS server and the React client

the role map would be the drift bug that makes the API 403 a user the UI just offered a workspace to.

Output: three new modules in `@judicialsync/config-schema`, wired into the operational rule package
snapshot schema so the existing publish validation enforces the floor without a new mechanism.

**`PRIMARY_ROLE_PRECEDENCE`** resolves CONTEXT's open discretion item *"how 'primary role' is
determined when a user holds several."* Declare a fixed, documented ordering and explain the
reasoning in a comment: the ordering is **by narrowness of working pattern**, so a user who holds
both a specialised and a general role lands in the specialised one, where the narrower set of panels
is the one they actually came to use:

```ts
export const PRIMARY_ROLE_PRECEDENCE = [
  "courtroom_deputy", "judge", "law_clerk", "clerk_case_admin",
  "security_officer", "system_admin", "court_admin", "ao_program_manager",
] as const;
```

`courtroom_deputy` leads because a deputy holding a second role is overwhelmingly likely to be
mid-session when they log in, and the full-bleed shell is the one that is wrong to miss. Roles that
map to `null` are absent from the list; they can never be a primary role.

**`resolveWorkspace({ roles, storedPreference })`** — the validate-on-read rule CONTEXT calls *"the
load-bearing part"*:

1. Compute `available` = the distinct, non-null workspaces the user's roles map to, ordered by
   `PRIMARY_ROLE_PRECEDENCE`.
2. If `available` is empty → `{ workspace: null, source: "unmapped", available: [] }`. The caller
   turns this into `403 UI_NO_WORKSPACE_ASSIGNED`.
3. If `storedPreference` is a `WorkspaceId` **and** is in `available` →
   `{ workspace: storedPreference, source: "preference", available }`.
4. Otherwise → `{ workspace: available[0], source: "primary_role_default", available }`. **Silently.**
   A stale or unparseable preference is not an error; without this step *"a user whose roles change
   is stranded on a workspace they can no longer use, and the stale value needs an administrator to
   clear."* Comment that the function deliberately does **not** rewrite the stored value — a role may
   be restored, and overwriting a user's expressed preference because of a temporary revocation is a
   worse failure than falling back for a while.

The function is pure: no I/O, no clock, no randomness. That is what makes it a unit test rather than
an integration test, and why it can live in a package both runtimes import.
